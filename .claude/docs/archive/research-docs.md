# Исследование: хранить документацию проекта или хватит git

> Идея №5 из `MyIdeas.md`: стоит ли вести документы или достаточно git (тогда плагин похудеет); начать с лучших практик ведения проекта и сравнить с kit. Это исследование, а не доработка. 2026-10-19. Вывод — в разделе «Коротко», варианты — в конце, решение пользователя — в разделе «Рекомендация и решение».

## Коротко

- **Одного git мало.** git хранит прошлое: что сделано, когда, какими файлами. Он не хранит того, что агенту нужно в начале каждой сессии: этап, следующий шаг, чего ждём от заказчика. Не хранит и знаний вне кода: почему выбрали так, какие баги отложены, что ответил заказчик. Источники сходятся: агенту нужен короткий файл состояния **и** git. Так устроен и стенд Anthropic для долгой работы агента: в начале каждой сессии он читает файл прогресса и `git log`.
- **Но часть журнала kit дублирует git.** Строка шага «Что сделано / Как проверено» — это заголовок и тело коммита шага (CHECK уходит в коммит дословно). Перенос закрытых этапов в `journal/stages/` и реестр «Документы» — тоже учёт того, что видно по git и по папкам.
- **Замер (рабочие проекты, 23 сессии, 2026-09-23…10-19): пишется много, читается мало.** «Сейчас» работает постоянно — хук подставил его 111 раз. Решения, баги, справочник, закрытые этапы и архив агент открывал за знаниями в 9 сессиях из 23 и меньше чем в половине проектов — около 60 раз; примерно столько же раз он перечитывал их, только чтобы проверить свою же запись. Архивные спеки и планы — в 1 сессии из 23.
- **В git агенты ходят чаще, но за другим.** В git — за историей кода: старые версии файлов, история изменений, когда в коде появилась строка (около 120 раз в 12 сессиях из 23). В документы — за тем, что делать дальше («Сейчас», спек и план этапа) и почему так решили (решения, справочник, баги). По сообщениям коммитов искали 1 раз: «почему» в коммитах kit нет.
- **Редкие обращения к документам — по делу:** вопрос пользователя о прошлом решении, план нового раздела с опорой на прежние решения и факты, инструкция для заказчика по справочнику, отчёт заказчику.
- **От «только git» плагин похудел бы не сильно:** код документов — пятая часть скриптов (1 233 строки из 5 823) и десятая часть тестов. Основной вес kit — выкладка, сервер, снимки и `/kit:project-init`. После 3.0 журнал пишет скрипт: на закрытии шага он стоит 3–5 ходов модели и 6–8 тыс. токенов.
- **Рекомендация исследования была — вариант Б:** не отказываться от документов, а убрать дубли git — «история в git, в журнале только то, чего в git нет».
- **При обсуждении у Б нашёлся минус:** git на сервер не уезжает, а удалённый репозиторий есть у 8 проектов из 12. Таблица шагов в журнале — копия истории там, где git недоступен: на сервере (по FTP) и в проектах без GitHub. Полный Б в части сценариев терял бы историю шагов.
- **Решение пользователя (2026-10-19):** документы не менять — пока работаем на kit 3.1; в будущем лучше реализовать вариант Г (короткий контекст), в нём больше выигрыша. Вариант Б отвергнут.
- **Больше токенов экономит длина сессий:** на 23 сессии — 31 сжатие контекста, а качество модели падает с ростом контекста. Короткий контекст (`/clear` после шага) даёт больше, и как раз «Сейчас» делает `/clear` безопасным.

## Вопрос и как исследовали

1. **Лучшие практики 2025–2026:** Anthropic (стенд для долгой работы агента, контекст-инжиниринг, документация Claude Code), исследование ETH Zurich о файлах контекста (AGENTS.md, CLAUDE.md), исследование Chroma о падении качества на длинном контексте, статьи Thoughtworks о spec-driven разработке и контексте агентов, классика — записи архитектурных решений Найгарда и сообщения коммитов, подходы других агентов (ExecPlans OpenAI, Memory Bank Cline, Beads, Entire). Список — в «Источниках».
2. **Замер по записям сессий Claude Code** на компьютере пользователя: период kit (2026-09-23…2026-10-19), только kit-проекты (сессии с хуком kit). Рабочие проекты — 8 проектов (9 папок сессий), 23 основные сессии, 559 записей служебных агентов (docs-keeper, git-keeper) и 371 — прочих субагентов; claude-kit — отдельно (22 сессии). Считались чтения и правки документов (Read, Edit, Write, команды Bash), вызовы `git log` и `git show`, подстановки «Сейчас» хуком. Чтения размечены: поиск знаний, проверка только что записанного, служебное (переезд формата, правка скриптом). Здесь — только общие цифры, без имён проектов.
3. **Разбор kit:** что в каких документах лежит, кто пишет, кто читает, что из этого есть в git и сколько кода на это уходит.

## Как вести проект с агентом: пять слоёв

Сводка практик из источников — общая картина, к ней потом приложен kit.

| Слой | Что в нём | Как по практикам | Где описано |
|---|---|---|---|
| Правила | команды, нестандартные соглашения, грабли | короткий файл, грузится всегда (CLAUDE.md или AGENTS.md, до ~200 строк) | документация Claude Code; ETH Zurich |
| Состояние | этап, следующий шаг, чего ждём, открытые вопросы | короткий файл; читается в начале сессии и после сброса контекста | стенд Anthropic (файл прогресса), заметки агента (NOTES.md), activeContext.md в Cline, раздел Progress в ExecPlan |
| История | что сделано, когда, как проверено, почему | git: маленький проверенный шаг — коммит с описанием «что и почему» | стенд Anthropic; Бимс о сообщениях коммитов |
| Знания | значимые решения с причиной и отвергнутым; факты вне кода | короткие нумерованные записи в репозитории; отменяются новой записью, не удаляются | записи архитектурных решений (ADR) — Найгард; Thoughtworks — кольцо Adopt |
| Документы задачи | спек и план крупной задачи, находки по ходу | живут, пока идёт задача; для мелочей не нужны; поддерживать спек после задачи — польза не доказана | ExecPlan OpenAI; SPEC.md в документации Claude Code; Бёклер о spec-driven разработке |

Общие правила поверх слоёв:
- **Не хранить выводимое из кода и git.** Claude Code советует не класть в CLAUDE.md то, что агент поймёт из кода, и то, что часто меняется; в авто-память — только то, чего нет ни в коде, ни в истории git.
- **Всегда загружаемое — минимум.** По ETH Zurich файлы контекста в целом не повышают долю решённых задач, а стоимость растёт больше чем на 20%; обзоры репозитория не помогают, полезны правила, которых агент сам не угадает.
- **Устаревшее и противоречивое — вред.** Чем больше в контексте лишнего и похожего, тем ниже точность (Chroma); Йегге пишет, что груда устаревших markdown-планов сбивает агента, и заменил их трекером задач с сжатием закрытых (Beads). Готовое — в архив или удалять.
- **Короткие сессии.** Качество падает с ростом контекста даже на простых задачах (Chroma: 18 моделей; короткий точный запрос сильно лучше полной истории в ~113 тыс. токенов); Claude Code советует `/clear` между задачами. Это работает, только если состояние лежит в файле.
- **Большие документы не поддерживают и не читают** (Найгард): пишут мало и коротко, о значимом, рядом с кодом.
- **Новое в 2026:** трекеры задач для агентов (Beads) и контекст сессий, привязанный к коммитам (Entire: подсказки и записи сессий хранятся отдельной веткой, коммит ссылается на них). Даже подходы «вокруг git» добавляют к нему свой слой — голого git им мало.

## Замер: что пишется и что читается

**Пишется** (рабочие проекты; в основном до 3.0, когда журнал вёл агент docs-keeper, — 413 вызовов): `progress.md` — 1 318 правок служебными агентами, решения — 136, баги — 70, справочник — 130, этапы — 31, план выкладки — 168; спеки и планы — 466 правок в основных сессиях. Решений накопилось 409 строк на 8 проектов (медиана 43, максимум 133).

**Читается:**
- «Сейчас» — 111 подстановок хуком: 13 запусков, 30 возобновлений, 31 сжатие, 37 — прежней версией хука.
- Решения, баги, справочник, закрытые этапы, архив — поиск знаний в 9 сессиях из 23, в 4 папках проектов из 9; около 60 обращений по ручной разметке. Примерно столько же — проверка только что записанного (агент искал свою строку `grep -c`). Поводы поиска: план нового раздела (опора на прежние решения и факты), вопрос пользователя о прошлом решении или забытом деле, инструкция для заказчика, разбор отложенных багов, отчёт заказчику, ревью.
- Архив спеков и планов — 1 сессия из 23. Спеки и планы текущего этапа — 156 чтений: пока этап идёт, ими пользуются активно.
- git — около 730 вызовов `git log` и `git show` в 16 сессиях из 23. Больше всего — проверка последнего коммита (около 370) и «последние N коммитов» (около 240: что было недавно); около 120 — поиск в истории кода (подробнее — в следующем разделе); `git blame` — ни разу.
- В claude-kit картина та же, только к старым спекам обращаются чаще (архив — в 5 сессиях из 22): разработка плагина опирается на прежние этапы.

**Сколько стоит журнал в kit 3.x** (с 2026-10-16; всего 7 закрытий шага — выборка маленькая): от вызова `/kit:step-done` до записи журнала — медиана 3–5 ходов модели, 6–8 тыс. токенов прироста контекста, меньше полуминуты; всё закрытие с просмотром и коммитом — 8–11 ходов и 11–32 тыс. токенов. В рабочих проектах это близко к цели этапа 36 (не больше 8 ходов и 10 тыс.). До 3.0 один вызов docs-keeper стоил 1,1 мин и 59 тыс. токенов (замер этапа 36).

**Сессии длинные:** на 23 сессии — 31 сжатие контекста; средний ход, по замеру этапа 36, идёт при контексте ~485 тыс. токенов.

## Куда агенты обращаются: git или документы

| Куда | Сколько (рабочие проекты) | Сессий из 23 | Зачем |
|---|---|---|---|
| git: поиск в истории | около 120 | 12 | история кода: старая версия файла (65), история изменений файла (39), когда в коде появилась строка (9); по тексту сообщений коммитов — 1 раз, `git blame` — ни разу |
| git: последние N коммитов | около 240 | 15 | что было недавно |
| Документы: решения, справочник, баги, этапы, архив | около 60 | 9 | что и почему решили, что ответил заказчик, что отложено; отчёт заказчику |
| Документы: «Сейчас» | 111, хуком | все | что делать сейчас и дальше |
| Документы: спек и план этапа | 156 чтений | — | как делать этап |

Ещё около 370 вызовов git — проверка последнего коммита сразу после него; к поиску знаний это не относится.

git и документы не соперничают, а делят работу: **git — история кода** (как и когда менялся код, прежние версии), **документы — направление и причины** (что дальше, что решили и почему, что сказал заказчик). «Почему» в git почти не ищут, потому что коммиты kit его не содержат.

| Практика | kit сейчас | Оценка |
|---|---|---|
| Короткий постоянный контекст | правила проекта в `.claude/CLAUDE.md`; хук добавляет «Сейчас» (до 4 000 знаков) и ~10 правил процесса | соответствует |

| Устаревшее — убирать | `work/` → `archive/`; «Сейчас» переписывается целиком | соответствует |
| Короткие сессии | отложено (решение 2026-10-16) | сессии длинные — главный рычаг по токенам |
| Структурированное состояние | таблицы markdown, правит скрипт | достаточно: скрипт снимает риск порчи формата |

## Хватит ли одного git

Нет. git хорошо отвечает на вопросы «что сделано» и «что было недавно» — агент и так спрашивает его об этом постоянно. Но он молчит о четырёх вещах:
- **что дальше** — следующий шаг, блокеры, ответы, которых ждём от заказчика: git знает прошлое, а не планы;
- **почему** — решение редко принадлежит одному коммиту, отмена решения («Заменяет №N») в истории не видна, а «почему» kit в коммит сейчас и не пишет;
- **знания вне кода** — отложенные баги, факты и материалы заказчика, что удалить с сервера;
- **история там, где git нет** — `.git` на сервер не уезжает, а удалённый репозиторий есть у 8 проектов из 12. Журнал при «Документах на сервере: да» (6 проектов из 12) — копия истории на сервере, её открывают по FTP.

Поэтому вывод практик — не «документы или git», а **разделение**: история — в git, состояние и знания — в коротких файлах. В kit это разделение почти есть; мешают дубли — но часть дублей (таблица шагов) служит копией истории там, где git недоступен.

| Что сейчас в журнале | Куда по варианту Б |
|---|---|
| Что сделано и как проверено на шаге | только git: заголовок и тело коммита шага |
| Таблицы закрытых этапов | только git: `git log` по ID шагов |
| Реестр «Документы» | не нужен: статус видно по папке |
| Почему так решили на шаге | в тело коммита шага (1–3 строки) и, если решение значимое, — в `decisions.md` |
| «Сейчас», значимые решения, баги, справочник, план выкладки | остаются в журнале |
| Спек и план этапа | остаются: `work/`, потом `archive/` |

## Насколько похудеет плагин

- Скрипты документов (`kit-journal.js`, `lib/journal.js`, `journal-split.js`, `decision-inbox.js`, `lib/md.js`) — 1 233 строки из 5 823 (21%). Тесты к ним — 611 строк из 6 438 (около 10%). Тексты скиллов о документах (блоки журнала в step-done, закрытие этапа, отчёт, шаблоны журнала) — около 23 КБ из 192 КБ (12%).
- Основной вес — другое: выкладка и сервер (`ssh-deploy.js`, `ssh-probe.js`, `remote-php.js`, `kit-exec.js` и библиотеки), снимки `/kit:visual` (~1 400 строк), `/kit:project-init` (59 КБ текста), коммит и защита (`kit-commit.js`, `secret-scan.js`, `guard-bash.js`).
- «Только git» убрал бы до пятой части скриптов и 3–5 ходов модели на шаг — ценой «Сейчас», решений и знаний.
- Вариант Б — меньше: уходят `journal-split.js` (240 строк), реестр и перенос этапов в `lib/journal.js`, часть закрытия этапа. Оценка — 300–500 строк кода, 150–300 строк тестов, короче step-done и закрытие этапа. На ходах шага почти не скажется: строки журнала и сейчас пишет скрипт. Выигрыш — в простоте: меньше кода и правил формата, короче журнал, проще закрытие этапа, один источник истории вместо двух.

## Варианты

**А. Оставить как есть (kit 3.1).**
- Плюсы: ничего не меняется; проекты только что переехали на формат 3.0; таблица шагов остаётся копией истории на сервере и без GitHub.
- Минусы: дубли git остаются — две записи одного факта, ~1 200 строк кода документов, запись намного больше чтения.

**Б. История — в git, в журнале — только то, чего в git нет.**
- Что меняется: таблица шагов не ведётся (история шага — коммит: заголовок — что сделано, тело — как проверено и почему); этапы не переносятся в `journal/stages/` (старые файлы остаются как есть, в «Этапах» — строка на этап с датами и итогом сверки); реестра «Документы» нет — статус по папке; `/kit:report` берёт «Сделано» из коммитов. «Сейчас», решения, баги, справочник, план выкладки, спек и план этапа — без изменений.
- Плюсы: один источник истории, меньше кода и правил, проще закрытие этапа, git сам отвечает на «почему».
- Минусы:
  - ещё одна смена формата — без переезда (старые таблицы остаются историей), но с правками скриптов, step-done, отчёта и тестов;
  - список шагов этапа виден не в журнале, а через Claude — `/kit:report` или вопрос «что сделано на этапе N»;
  - **найдено при обсуждении:** git на сервер не уезжает, а удалённый репозиторий есть не у всех проектов. Без таблицы шагов история шагов новых этапов на сервере по FTP не видна, а в проектах без GitHub лежит в одной копии — на компьютере. По 12 проектам: GitHub и документы на сервере — 5 (на сервере историю больше не видно), документы на сервере без GitHub — 1 (пропадает последняя копия истории вне компьютера), GitHub без документов на сервере — 3 и ни того ни другого — 3 (без изменений).

**Б-мягкий (появился при обсуждении).**
- Что меняется: в коммит шага добавляется «Почему»; реестра «Документы» нет — статус по папке; таблицы шагов и перенос этапов в `journal/stages/` — как сейчас.
- Плюсы: главная польза Б для агента (git отвечает на «почему») без потери истории на сервере и без GitHub; 2–3 шага.
- Минусы: дубль «таблица шагов — коммит» остаётся; кода уходит меньше (~100–150 строк).

**В. Только git и файл состояния.**
- Что меняется: убрать `journal/` целиком; решения — только в коммитах, баги и факты — в «Сейчас» или нигде.
- Плюсы: минимум файлов и кода документов.
- Минусы: теряются «почему» и отменённые решения, справочник и материалы заказчика, отложенные баги; отчёт заказчику беднеет; расходится с практиками (ADR, файл прогресса у Anthropic); те же потери истории на сервере и без GitHub, что у Б.

**Г. Документы не трогать, сократить контекст.**
- Что меняется: вернуться к отложенному «короткому контексту» — `/clear` после шага и порог автосжатия.
- Плюсы: по замеру этапа 36 — примерно вчетверо меньше токенов на ход; исследования (Chroma, Anthropic) прямо за короткий контекст.
- Минусы: нюансы разговора, не попавшие в журнал или спек, после `/clear` забываются; решение было отложено пользователем до работы с kit 3.0 в нескольких проектах. С А и Б не конфликтует.

## Рекомендация и решение

**Рекомендация исследования** была — вариант Б: он убирает ту часть, где запись не окупается чтением и повторяет git, и оставляет состояние, значимые решения, знания вне кода и документы текущей задачи. «Кратно» плагин от этого не похудел бы — минус 300–500 строк кода и проще закрытие этапа. Больший выигрыш по скорости и токенам — у варианта Г.

**Что выяснилось при обсуждении.** Таблица шагов — не только дубль git, но и копия истории там, где git недоступен: на сервере (`.git` не выкладывается, документы открывают по FTP) и в проектах без удалённого репозитория. Полный Б в части сценариев терял бы историю шагов; у Б-мягкого этого минуса нет.

**Решение пользователя (2026-10-19):** документы не менять — пока работаем на kit 3.1, дальше видно будет. В будущем лучше реализовать вариант Г: в нём больше выигрыша. Вариант Б отвергнут — в некоторых сценариях он приводит к потере истории.

## Что ещё нашлось

- **«Почему» в коммите полезно при любом варианте.** Claude Code советует искать ответ на «почему так сделано» в истории git, а агент чаще всего смотрит именно последние коммиты. Одна-две строки «Почему: …» в теле коммита шага стоят почти ничего.
- **Обзор проекта в шаблоне `CLAUDE.md`.** По ETH Zurich обзоры репозитория не помогают агенту, полезны только нестандартные правила. Раздел «Проект» шаблона можно сократить при следующей правке.
- **Закрытие шага в 3.x** в рабочих проектах уже близко к цели этапа 36 (8 ходов, 11 тыс. токенов против цели 8 и 10) — по трём закрытиям; живая проверка 3.0 остаётся за пользователем.

## Ограничения

- Замер — 4 недели, 8 рабочих проектов, 23 сессии; закрытий шага в kit 3.x — всего 7.
- Разметка «поиск знаний / проверка записи / служебное» — правила по тексту команд плюс ручной просмотр; точность — до десятков процентов, но соотношение «пишется много, читается мало» держится при любой разметке.
- Чтение журнала человеком (в редакторе или по FTP) не измерялось.
- Цену редкого обращения числом не измерить: один ответ «почему так сделали» может сберечь час.
- Исследования ETH Zurich и Chroma — про другие задачи (одиночные задачи из репозиториев, синтетические тесты); на многодневные проекты их выводы переносятся с осторожностью.
