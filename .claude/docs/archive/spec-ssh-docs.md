# Спецификация — «Документы на сервере» в режиме «Claude по SSH»

> Разделы kit поверх дизайна `superpowers:brainstorming`. Выбранный подход и отвергнутые — в «Решения» журнала (DECISIONS).

## Задача

- Номер: без задачи — замечание пользователя (2026-10-15): режим «Claude по SSH» не умеет того, что умеет автозаливка PhpStorm, — при «Документы на сервере: да» папка `.claude` (кроме служебного) на сервер не уезжает.
- Цель: при «Выкладка: Claude по SSH» и «Документы на сервере: да» на сервере после каждого шага — те же документы, что локально, включая журнал этого шага; состав — как у автозаливки PhpStorm; снаружи `/.claude/` закрыта.

**Откуда.** Этап 32 (Т-7 спека `archive/spec-claude-ssh.md`) решил: при «Claude по SSH» вопрос «Документы на сервере» не задаётся, параметр — `нет`, `ssh-deploy.js` исключает `/.claude` целиком (`ALWAYS_SKIP` в `lib/deploy.js`). Автозаливка PhpStorm при «да» везёт `.claude/docs` (без снимков `visual`), `.claude/CLAUDE.md` и `.claude/.htaccess` (`KEEP` в `phpstorm-exclude.js`). Сложность режима SSH: журнал шага пишет docs-keeper уже после заливки и проверки на сервере (ему нужны их итоги), а следующая заливка считает изменения от коммита шага — документы, поехавшие вместе с кодом, отставали бы на шаг, а часть не попала бы на сервер никогда.

## Требования

### Скрипт `ssh-deploy.js --docs`

- Т-1. Вызов из корня проекта:
  ```
  node ssh-deploy.js [--env прод|дев] [--base <коммит>] [--timeout сек] --docs [--all]        — список, без подключения
  node ssh-deploy.js [--env прод|дев] [--base <коммит>] [--timeout сек] --docs [--all] --go   — залить, удалить, сверить md5
  ```
- Т-2. Документы на сервере — ровно набор автозаливки PhpStorm: `.claude/.htaccess`, `.claude/CLAUDE.md`, `.claude/docs/**` без папки снимков `/kit:visual` (`visualRel`). Список — один на оба режима: общий модуль, `phpstorm-exclude.js` берёт его оттуда же. Пути сравниваются без учёта регистра. Документы вне `.claude` (старая раскладка `docs/`) не уезжают — как у хука PhpStorm.
- Т-3. Без `--all` — документы, изменённые от той же базы, что у основной заливки (`resolveBase`, Т-10 этапа 32): изменённые и новые — «Залить», удалённые — «Удалить» (как у основной заливки: файл, который есть на диске, на сервере не удаляется). «Не выкладывать» действует, кроме записей `.claude` / `/.claude` (они — для ручной выкладки, как у хука PhpStorm).
- Т-4. С `--all` — все документы набора, которые есть на диске и не игнорируются git (отслеживаемые и новые), без удалений; база не считается. Для первой заливки и починки.
- Т-5. `.claude/.htaccess` — первым в «Залить», даже без изменений, если в документах есть что залить или удалить (и всегда при `--all`): папка закрыта раньше, чем на сервер попадёт первый документ, а удалённый на сервере `.htaccess` восстанавливается. Документы не менялись — «Нечего заливать», код 0, без подключения: один `.htaccess` не едет.
- Т-6. Отказ до подключения (на сервер ничего не ушло): параметр «Документы на сервере» не `да` — код 2 («документы на сервер не выкладываются»); нет локального `.claude/.htaccess` — код 2 («документы были бы открыты снаружи — /kit:project-init»); `--docs` вместе с `-- <пути>` или `--all` без `--docs` — код 4 (аргументы).
- Т-7. Вывод и коды — как у основной заливки (Т-12–Т-16 этапа 32), заголовок списка — «Документы»; строки `DEPLOY Файлы:` нет (docs-keeper к этому моменту уже отработал). Повтор безопасен.
- Т-8. Основная заливка (без `--docs`) не меняется: `.claude` в неё не попадает ни при каком значении параметра.

## Дизайн

**Общий набор документов.** В `lib/project.js` — `DOCS_KEEP` (`docs`, `CLAUDE.md`, `.htaccess` — имена внутри `.claude`), `docsOnServer(params)` (параметр ровно `да`) и `isDocOnServer(rel, info)` (путь — `.claude/.htaccess`, `.claude/CLAUDE.md` или под `.claude/docs/`, но не под `visualRel`; без учёта регистра). `phpstorm-exclude.js` берёт `DOCS_KEEP` и `docsOnServer` оттуда; «открыто для PhpStorm» = `docsOnServer && !isSsh` (Т-15).

**`lib/deploy.js`.** `docsRules(info)` — «Не выкладывать» без записей `.claude` / `/.claude`; `docsChanges(cwd, base, info)` — `changes(..., { worktree: true })` с `docsRules`, затем фильтр `isDocOnServer`; `docsAll(cwd, info)` — `git ls-files` и `ls-files --others --exclude-standard` по `.claude`, фильтр `isDocOnServer` и `docsRules`, только то, что есть на диске. `.htaccess` ставится первым (без повторов).

**`ssh-deploy.js`.** Разбор `--docs` / `--all` и отказы Т-6 — до чтения базы; дальше — тот же сценарий `buildScript`, `runSsh`, разбор `KIT_*` и сверка md5, что у основной заливки; без строки DEPLOY.

**`/kit:step-done`.** Раздел «3в. Заливка документов» между п. 3б и п. 4; пометки в п. 1.4 (порядки шага), п. 3а (описание «Коммитить» / «Залить на сервер»), п. 3а.6 (продолжение после «Остановиться» — с п. 3в).

**Изменения плагина:** `scripts/lib/project.js`, `scripts/lib/deploy.js`, `scripts/ssh-deploy.js`, `scripts/phpstorm-exclude.js`, `skills/step-done/SKILL.md`, `skills/project-init/SKILL.md`, `skills/project-init/templates/CLAUDE.md`, `skills/project-init/templates/deploy-prod.md`, тесты; выпуск — `plugin.json`, `marketplace.json`, README, спек плагина, обзор.

**Отвергнуто:**
- документы вместе с кодом в основной заливке и повторная полная заливка после docs-keeper — код заливается дважды за шаг;
- все документы целиком каждый шаг — ничего не отстаёт, но с ростом архива заливка тяжелеет; `--all` оставлен для первой заливки и починки;
- документы в основной заливке без второй — журнал шага пишется после неё и отставал бы, а часть файлов (записи закрытых этапов, решения) не попала бы на сервер никогда: база следующей заливки — коммит шага;
- коммит при неудачной заливке документов — по той же причине незалитое потерялось бы.
