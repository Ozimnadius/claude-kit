# Спецификация — прод главный: синхронизация с продом по команде `/kit:sync` (этап 48)

> Разделы kit поверх дизайна `superpowers:brainstorming`. Решения пользователя 2026-10-29 — в `journal/decisions.md` строками шагов
> 48.1 и 48.5; выбранный подход и отвергнутые — там же. Первая редакция (одобрена 2026-10-29) задавала вход с прода сам в каждой
> новой сессии и запрет правок файлов сайта до входа. После шага 48.4 пользователь заменил это ручной командой: «это всё лишнее» —
> синхронизация только по команде. Ядро первой редакции (три версии файла, забор одним коммитом, совмещение, что не забирать) —
> без изменений; номера требований сохранены, снятые помечены. В коде и прежних шагах синхронизация называлась «вход».

## Задача

- Номер: без задачи
- Цель: kit не затирает чужие правки на проде. Когда пользователь знает или подозревает, что прод меняли без нас, он запускает
  `/kit:sync`: всё, что поменяли на сервере без нас, ложится в git отдельной записью, а наша незалитая работа не теряется.

**Почему.** Типичный случай: проект сделан и выложен, прошли месяцы, клиент просит новые правки. За это время прод меняли без нас:
клиент в админке Битрикса (публичные страницы и включаемые области — это файлы), обновления Битрикса и решений Аспро, другие
подрядчики. Git отстал от прода. Сейчас kit негласно считает главным git: заливка (`ssh-deploy.js --go`, автозаливка PhpStorm) пишет
файл поверх, не проверяя, что лежит на сервере (`ssh-deploy.js`, `buildScript`). Чужая правка пропадает молча, сайт может сломаться,
клиент недоволен.

**Что есть сейчас (прод целиком не сверяет никто):** `remote-check.js` сравнивает git только с удалённым репозиторием (GitHub);
`ssh-deploy.js --md5` и `md5-check.js` сверяют файлы шага или заданный список; `/kit:project-init` скачивает исходники с сервера,
только если папка проекта пуста.

**Подход (выбрал пользователь): прод главный, git — наша рабочая копия и журнал; синхронизация — по команде.** Перед работой над
проектом, где прод могли менять без нас (например, клиент вернулся с правками после перерыва), пользователь запускает `/kit:sync`.
Синхронизация забирает в git всё, что поменяли на сервере без нас, одной записью, не теряя нашу незалитую работу. Автоматики нет:
при старте сессии kit о проде молчит, правки файлов сайта ничем не ограничены.

Расхождение git с сервером между синхронизациями — не авария, а норма: оно попадает в историю записью синхронизации. Наша работа,
которая ещё не дошла до сервера, при синхронизации не теряется (Т-5).

**Принцип пользователя:** «простая система, надёжная, как молоток; меньше морочек и действий».

- **Цели:** одна команда — и чужие изменения с прода в git, без вопросов по каждому файлу (по SSH); чужие изменения видны в истории;
  пользователь узнаёт о них одной строкой.
- **Не цели:** синхронизация сама — при старте сессии, в `/kit:project-init`, по расписанию; напоминания о синхронизации; запрет
  правок до синхронизации; страховка во время работы — проверка сервера перед каждой записью; база данных; запрет правок на проде для
  клиента.
- **Анти-цели (провал, даже если работает):** синхронизация откатывает или удаляет нашу работу; вопросы пользователю по каждому
  файлу; ручные шаги там, где есть SSH; в git попадают бэкапы и архивы; kit идёт на прод или останавливает работу без команды
  пользователя; синхронизация проекта, где ничего не менялось, заметно медленная.

## Требования

Сервер — сервер окружения (`serverEnv` в `lib/project.js`: «Окружение: дев» — дев, иначе прод); SSH — параметр «SSH прод» /
«SSH дев» (`serverSsh` в `lib/ssh.js`). **Файлы сайта** — пути внутри папки проекта, которые выкладываются: не под `ALWAYS_SKIP` и
«Не выкладывать» (`skipRules` в `lib/deploy.js`), не в `.claude/`.

- Т-1. **Где работает.** `/kit:sync` — в kit-проекте, у которого задан адрес сервера окружения («Прод» или «Дев») или SSH
  окружения. Иначе навык говорит, что синхронизировать не с чем, и ничего не делает (например, этот репозиторий: «Прод: —»).
- Т-2. **Когда.** По команде `/kit:sync` или по просьбе пользователя словами («синхронизируй с продом»): Claude видит навык, но
  запускает его только по просьбе пользователя, сам — нет. Хука при старте сессии нет; `/kit:project-init` синхронизацию не
  запускает и не засчитывает (уточнено 2026-10-29: первая редакция — вход в каждой новой сессии).
- Т-3. *Снято (2026-10-29).* Запрета правок файлов сайта до синхронизации нет.
- Т-4. **Что сверяется.** Файлы сайта, которые ведёт git, и новые файлы на сервере в путях, которые git не игнорирует (`.gitignore`
  проекта) и которые выкладываются. Ядро, загрузки, кеш (исключены `.gitignore`) — вне сверки. Чего синхронизация не забирает — Т-11.
- Т-5. **Три версии файла.** Каждый файл сравнивается в трёх версиях (отсутствие файла — тоже версия):
  - **база** — последняя точка, где сервер точно совпадал с git, по каждому пути: версия из последней заливки (коммит последней
    строки «Залито на …» плана выкладки, `baseFromPlan` в `lib/deploy.js`; нет — первый коммит репозитория, исходники с сервера), а у
    путей, которые после неё менял коммит синхронизации своего окружения, — версия из самого нового такого коммита. Дерево коммита
    синхронизации целиком базой не служит: в нём и наши незалитые шаги, с которыми сервер не совпадал (уточнено в 48.3);
  - **HEAD** — наш git;
  - **сервер** — что лежит там сейчас.

  | Сервер | HEAD | Что это значит | Что делает синхронизация |
  |---|---|---|---|
  | = база | любой | на сервере без нас не меняли | ничего: наше незалитое остаётся как есть |
  | ≠ база | = база | изменили без нас | забрать версию сервера |
  | = HEAD | ≠ база | наше уже на сервере | ничего |
  | ≠ база и ≠ HEAD | ≠ база | менялось и у нас, и без нас | совместить (Т-8) |

  Файл, удалённый нашим шагом, но ещё лежащий на сервере (раздел «Удалить с сервера» плана выкладки или удалён коммитом шага),
  синхронизация не возвращает, а называет в строке «ждёт удаления с сервера». Старая или неточная база правил не ломает: больше
  файлов попадёт в «наше уже на сервере» или в совмещение, которое сойдётся само.
- Т-6. **Синхронизация по SSH.** Сверка без записи на сервер; версии «изменили без нас» скачиваются в рабочую копию байт в байт
  (удалённые без нас — удаляются локально). Затем коммит через `kit-commit.js` — **без просмотра и без вопросов** (прод главный) —
  с заголовком `Прод: изменения без kit на ГГГГ-ММ-ДД (N файлов)` (окружение дев — `Дев: …`), по которому коммит синхронизации
  отличим от шагов, и списком файлов в теле; при заданном «Удалённом репозитории» — с `--push`. Нечего забирать — коммита нет. Путей
  больше, чем помещается в одну команду, — несколько коммитов синхронизации подряд (уточнено в 48.3).
- Т-7. **Что видит пользователь.** Одну строку: сколько файлов на сервере изменено, добавлено и удалено без kit. Отдельно — файлы
  с нашими прошлыми доработками (их меняли коммиты шагов, а не только первый коммит и коммиты синхронизации), путями: клиент или
  обновление (например, Аспро) могли их затереть. Отдельно — совмещённое с нашими правками (Т-8), что не совместилось само, что не
  забрано (Т-11) и что ждёт удаления с сервера (Т-5). Нечего забирать — одна короткая строка «прод совпадает с git».
- Т-8. **Наши незакоммиченные правки и совмещение.** Сервер совпадает с рабочей копией — это наша правка, уже на сервере
  (автозаливка, `--go` без коммита, работа исполнителя Мэтта до приёмки): синхронизация её не трогает и в строку не включает — её
  закроет шаг. Файл менялся и у нас (в HEAD или в рабочей копии), и без нас — совместить (база; наша — рабочая копия; их — сервер),
  результат — в рабочую копию, пользователь видит его в панели изменений. В коммит синхронизации идут только версии «изменили без
  нас»; совмещённое и наши правки остаются незакоммиченными поверх (совмещённый путь в коммит синхронизации не идёт — уточнено в
  48.4). Не совмещается само — рабочая копия этого файла не трогается, версия сервера кладётся во временную папку вне проекта,
  остальное синхронизируется; Claude спрашивает: «Совместить вручную» / «Оставить нашу» / «Взять версию сервера» (уточнено в 48.4).
- Т-9. **Без SSH.** Рабочая копия должна быть чиста: иначе предупредить, что скачивание затрёт незакоммиченные правки, и спросить.
  Claude даёт короткий список папок и файлов для скачивания по FTP (корни того, что сверяет Т-4) и как скачать в PhpStorm. После
  ответа «скачал» — правила Т-5, где «сервер» — скачанная версия: файлы, которые скачивание вернуло к базе поверх нашего незалитого
  (HEAD ≠ база, скачанное = база), возвращаются из HEAD; дальше — коммит и строка, как в Т-6 и Т-7. Удалённые на сервере файлы так
  не видны — это ограничение. Ответ «не буду скачивать» — синхронизация отменяется.
- Т-10. **Синхронизация не удалась** (нет сети, SSH не пустил, вышло время): Claude называет причину и спрашивает через
  AskUserQuestion: «Повторить» / «Отложить». Остановилась после записи файлов (коммит не прошёл, обрыв): «Повторить» доводит
  синхронизацию до конца, «Отменить» возвращает записанные ею файлы к HEAD (наши правки и совмещённое не трогает).
  Отметок «пропущено» нет (уточнено 2026-10-29: первая редакция — «Работать без входа» с отметкой на сессию).
- Т-11. **Чего синхронизация не забирает.** Бэкапы и архивы — как при первом скачивании в `/kit:project-init` (раздел 6 справки
  `reference/ssh.md`: `_*.back*`, `_*_back*.zip`, `*.tar.gz*`; полный список — `skipTake` в `lib/prod.js`) — и файлы больше 10 МБ.
  Не забираются и файлы с секретом: скачанное проверяется до записи той же проверкой, что у `kit-commit.js` (`secret-scan.js`);
  в git остаётся прежняя версия, и наша заливка правки такого файла затрёт серверную — об этом говорит строка (решение пользователя
  2026-10-29). Всё это остаётся на сервере; синхронизация называет такие файлы в строке один раз (что уже названо — помнит
  отметка); дописать путь в `.gitignore` Claude может по просьбе пользователя. Забрать за одну синхронизацию нужно больше 50 МБ —
  до скачивания стоп и один вопрос: «Забрать всё» / «Не забирать папки» (Claude допишет их в `.gitignore` и повторит) / «Отложить».
- Т-12. **Повтор безопасен.** Оборванная синхронизация не оставляет наполовину записанных файлов и коммита с частью файлов;
  повторный запуск доводит её до конца.
- Т-13. **Заливка после синхронизации.** База заливки (`resolveBase` в `lib/deploy.js`) остаётся прежней — иначе наши незалитые шаги
  выпали бы из заливки. Файлы, которые после базы заливки менялись только коммитами синхронизации и не изменены в рабочей копии,
  `ssh-deploy.js` («Claude по SSH») не заливает: они уже на сервере. Заливка документов (`--docs`) — как прежде.
- Т-14. **PhpStorm Always.** Скачанное синхронизацией PhpStorm может залить обратно (`autoUploadExternalChanges`) — это те же байты,
  вреда нет. Опасность — File Watchers (справка `project-init/reference/phpstorm.md`, «Грабли»): если синхронизация пишет исходник,
  который пересобирает watcher (SCSS, LESS, минификация), пересборка перезапишет результат и PhpStorm зальёт его на сервер. Такие
  файлы синхронизация называет пользователю до записи в рабочую копию и не пишет без его ответа (совмещаемые исходники для решения
  скачиваются в память — уточнено в 48.4).
- Т-15. **Worktree и проекты Мэтта.** Синхронизацию с записью делает сессия в основной папке проекта. В сессии в worktree
  `/kit:sync` только сверяет основную папку (без скачивания для записи и без коммита): нечего забирать — так и говорит; есть что —
  «синхронизация — в основной папке проекта». Исполнитель Мэтта синхронизацию не запускает (её запускает только пользователь);
  `/kit:matt` не меняется.
- Т-16. **`/kit:project-init`** — без изменений: исходники в пустую папку скачиваются, как прежде, синхронизацией не засчитываются.
  README и обзор — про `/kit:sync`.
- Т-17. **Проверки:** тесты скрипта синхронизации (заглушка `KIT_SSH`, как у тестов `ssh-deploy.js`) — все строки таблицы Т-5, Т-8,
  Т-11, обрыв и отмена, без SSH; тест навыка `/kit:sync`; `npm test`, `claude plugin validate plugins/kit --strict`,
  `claude plugin validate . --strict`, `node tools/kit-denylist.js tree`.
- Т-18. **Выпуск kit 3.4.0:** версии в `plugin.json`, `marketplace.json` и «Версия kit» в `.claude/CLAUDE.md`; README — раздел
  «Прод главный: `/kit:sync`»; обзор `work/overview/` — новый навык и скрипт (правило выпуска).
- Т-19. **Обезличенно:** в файлах и коммитах — без имён проектов, клиентов, доменов, учёток и IP.

## Критерии готовности

Живая проверка — на дев-стенде или копии сайта, не на проде клиента:
- новая сессия в проекте с сервером — kit о проде молчит, правки файлов сайта проходят без синхронизации;
- по SSH: на сервере изменить отслеживаемый файл, добавить новый файл в отслеживаемую папку, удалить отслеживаемый файл, изменить
  файл с историей шагов → `/kit:sync` → один коммит синхронизации, строка с тремя числами и пометкой о доработках; `git status`
  после — как до; повторный `/kit:sync` — «прод совпадает с git», коммита нет;
- закоммиченный, но не залитый шаг («Claude по SSH» без `--go`) → `/kit:sync` его не откатывает; `ssh-deploy.js` после
  синхронизации предлагает залить файлы шага и не предлагает файлы синхронизации;
- наша незакоммиченная правка уже на сервере (автозаливка) → синхронизация её не трогает, в строке её нет;
- наша незакоммиченная правка и изменение того же файла без нас → совмещение в рабочей копии (видно в панели изменений), в коммите
  синхронизации этого файла нет; не совмещается — рабочая копия не тронута, версия сервера во временной папке, вопрос;
- файл, удалённый нашим шагом, лежит на сервере → синхронизация не возвращает, строка «ждёт удаления с сервера»;
- архив, файл больше 10 МБ и файл с секретом на сервере → не забраны, названы в строке один раз;
- PhpStorm Always и File Watcher на забираемом исходнике → вопрос до записи; после синхронизации md5 забранных файлов на сервере не
  изменились;
- без SSH: список для FTP; после «скачал» — коммит и строка;
- сервер недоступен — вопрос «Повторить / Отложить»; остановка после записи — «Отменить» возвращает записанное к HEAD;
- сессия в worktree — только сверка основной папки;
- проект без сервера («Прод: —») и этот репозиторий — `/kit:sync` говорит, что синхронизировать не с чем;
- проверки Т-17 зелёные.

Стенд называет пользователь при выпуске; стенда нет — по его решению сценарный прогон на поддельном сервере (`KIT_SSH`) и запись
«без живой проверки», как на этапе 47.

## Предположения

- На серверах есть `sh`, GNU `find` (с `-printf`), `md5sum`, `base64`, `xargs -0`, `cut`, `mktemp -d` — как уже требует сверка
  шага 48.3; иначе — код 3 с причиной.
- Переводы строк: сервер может отдавать CRLF при LF в git — сравнение учитывает это (md5 без `\r`).
- Отметка `.claude/kit-prod.json` не попадёт в git: `.gitignore` проектов исключает `/.claude/*`, кроме правил, документов и скриптов.

## Дизайн

**Компоненты:**
1. **Навык `/kit:sync`** (`skills/sync/SKILL.md`; запуск — командой или по просьбе пользователя словами, описание навыка велит
   Claude не запускать его самому). Запускает скрипт синхронизации и по коду выхода говорит и спрашивает (AskUserQuestion): 0 —
   строка итога (совмещённое — показать панель изменений); 1 — нужен ответ (File Watchers и объём — до записи; конфликт совмещения;
   остановка после записи — «Повторить» / «Отменить»); 2 — синхронизировать не с чем или параметры неверны; 3 — «Повторить» /
   «Отложить»; 4 — сказать пользователю. Без SSH — список для FTP, после «Скачал» — разбор скачанного.
2. **Скрипт синхронизации** `prod-sync.js` (до шага 48.6 — `prod-entry.js`). Режимы: синхронизация по SSH (по умолчанию); только
   сверка (`--check`; в worktree — всегда, по основной папке); без SSH — список для FTP и разбор после скачивания (`--ftp-done`);
   отмена незаконченной синхронизации (`--abort`). Флаги ответов: `--watchers-ok`, `--big-ok`; срок — `--timeout`. Коды выхода по
   образцу `ssh-deploy.js`: 0 — синхронизация сделана (или нечего забирать), 1 — нужен ответ пользователя, 2 — синхронизировать не с
   чем или параметры неверны, 3 — нет подключения, обрыв, вышло время, 4 — аргументы, git.
3. **Отметка** `.claude/kit-prod.json` — только `named` (уже названные в строке файлы, Т-11) и `pending` (пути незаконченной
   синхронизации, Т-12). Записей сессий нет.
4. **Коммит синхронизации** — через `kit-commit.js`: он проверяет пути и секреты. Секрет в скачанном синхронизация находит раньше,
   той же проверкой, и такой файл не забирает (Т-11); если `kit-commit.js` всё же остановил коммит — «Повторить» / «Отменить».
   Заголовок отличает коммит от шагов: по нему находятся база Т-5, «наши доработки» Т-7 (файлы из коммитов, кроме коммитов
   синхронизации и первого коммита) и файлы, которые не заливаются по Т-13.
5. **Совмещение** — трёхстороннее, `git merge-file` (база, наша, их) во временной папке; результат остаётся незакоммиченным для
   просмотра (`mergeVersions` в `lib/prod.js`, шаг 48.4).
6. **Заливка после синхронизации** — `ssh-deploy.js` не льёт обратно файлы коммитов синхронизации (Т-13).

**Сверка по SSH** (сделано в 48.3–48.4): сервер отдаёт состояния и md5 отслеживаемых пачкой, список остальных файлов (`find`) с
размерами; крупные исключённые папки отрезаются ещё на сервере — только где git точно ничего не вернёт (`.gitignore` с отрицаниями);
список фильтруется локально (`git check-ignore --stdin`, правила выкладки, предел размера); версии сравниваются у нас (как есть и в
вариантах переводов строк), неясное — скачивается; сравнение с базой и HEAD по таблице Т-5. Порядок записи: объём 50 МБ — до
скачивания; совмещаемые — скачать в память и совместить; File Watchers — по тому, что будет записано; затем забор одним
подключением (base64, порциями), запись через временный файл и переименование, сверка md5 после записи.

**Ошибки:** нет подключения — код 3 и вопрос Т-10; обрыв посередине — повтор доводит до конца (Т-12) или «Отменить»; секрет в
скачанном — файл не забирается (Т-11); File Watchers при Always и больше 50 МБ — код 1 и вопрос.
