# План этапа 21 — история проекта: «что делали, как проверили, почему так решили»

> **Исполнителям:** задачи по порядку, каждая закрывается `/kit:step-done` (один проверенный шаг — один коммит `ID: …`). Остановка на проверку пользователя — после каждой задачи. Шаги — с чекбоксами (`- [ ]`).

**Цель:** журнал kit-проекта отвечает на три вопроса — что делалось, как проверено и почему так решили; superpowers работает в kit-проекте по правилам kit, а не в обход них.

**Архитектура:** только тексты агентов и скиллов, шаблоны и два хука, которые уже есть. Новых скриптов, хуков и скиллов нет. Старые журналы не мигрируют: `docs-keeper` определяет формат по заголовку конкретной таблицы.

**Стек:** Node ≥ 18 без зависимостей, `node --test`.

**Откуда:** разбор идей доработки (kit 2.7.1, superpowers 6.4.x, spec-kit 1.1.0) с пользователем 2026-10-05. Решения обсуждения — ниже; передать их блоком DECISIONS при закрытии 21.1.

## Решения обсуждения (2026-10-05)

- В этап 21 — идеи 1, 2, 4, 5 (таблицы и блоки), 15 в виде «формат по заголовку таблицы», 6 и 10 в виде надстройки над superpowers.
- Superpowers не убираем и его скиллы не запрещаем: kit задаёт правила, как они работают в kit-проекте. Свой `/kit:spec` не делаем — спецификацию ведёт `superpowers:brainstorming` по правилам kit.
- Потом: автосбор ответов `AskUserQuestion` хуком (3), сверка «задумано ↔ сделано» при закрытии этапа (8), `/kit:why` (13), отчёт для заказчика (14).
- Не берём: вес задачи (7), архив только для чтения (9), прогоны по сценариям давления и микротесты описания `/kit:step-done` (11, 12), метку версии журнала (15 в исходном виде), мост со spec-kit (16).

## Общие ограничения

- Файлы — UTF-8 без BOM, LF; файлы целиком не переформатировать.
- Старые строки таблиц «Решения», шагов и багов не переписываются. Единственное исключение — пометка `→ заменено №M` в ячейке «Решение» новой таблицы (21.1).
- Журналы, созданные до 2.8.0, продолжают работать без правок: таблицы старого формата остаются как есть.
- Перед каждым коммитом: `npm test`, `claude plugin validate plugins/kit --strict`, `claude plugin validate . --strict`.
- Приоритет — простота и надёжность: без многоагентных прогонов и тестов на экзотику. Поведение `docs-keeper` проверяется одним запуском на копии журнала.
- Установленный плагин — 2.7.1 до выпуска 21.4: шаги 21.1–21.3 закрываются старыми агентами, новый формат в журнале этого репозитория появится только после выпуска.

## На что смотреть при проверке

1. **Старый журнал** (таблица «Решения» `| Дата | Решение |`, этапы с 4 колонками) — первая запись в новом формате не трогает старые строки: новая таблица появляется под старой, текущий этап дописывается в своём формате.
2. **Решение без «почему»** — `docs-keeper` его не записывает и прямо говорит об этом в отчёте; `/kit:step-done` не идёт к `git-keeper`, пока не исправит.
3. **Решения агента** — не больше 1–3 за шаг и только значимые; после `/kit:step-done` пользователь видит их отдельным списком.
4. **Brainstorming в kit-проекте** — спецификация ложится в `<папка документов>/work/`, коммита в обход `/kit:step-done` нет.
5. **Исключения выкладки** — `.superpowers`, `.worktrees`, `docs/superpowers` появляются в Excluded Paths на следующем старте сессии; настоящие папки сайта (`specs` и т. п.) не исключаются.
