- скиллы Битрикса — отдельный вопрос в `/kit:project-init`, при «да» — свежие версии из репозиториев при каждом запуске;
- файл-канал `kit-exec.php` оставить — SSH есть не везде;
- облегчить и разработку самого плагина (claude-kit) — отдельным шагом;

- короткий контекст (`/clear` после шага, порог автосжатия) отложен; подсказки `/clear` пока нет (см. «Открытые вопросы»).

**Не входит:** хуки (кроме правил `session-start.js`), `/kit:server` и файл-канал, `/kit:visual`, содержимое скиллов Битрикса, интеграция с PhpStorm, `secret-scan.js`, просмотр перед коммитом — без изменений. Плагины и MCP-серверы окружения — отдельная задача вне kit.

**Неудача этапа**, даже если всё работает:
- потеряна история (журнал, решения, баги);
- сломан основной сценарий (шаг → журнал → один коммит → отправка);
- закрытие шага не стало кратно короче по ходам модели и прочитанному тексту (критерии готовности);
- в скриптах появился код ради редких случаев.

Размер кода сам по себе мерой не служит: скрипты агент не читает, токены тратят текст скиллов и вывод команд.

## Требования

### Один формат — переезд по требованию

- Т-1. kit 3.0 понимает один формат проекта:
  - документы — в `.claude/docs`;
  - журнал по частям: `journal/decisions.md`, `journal/bugs.md`, `journal/reference.md`, `journal/stages/`;
  - таблица текущего этапа — со столбцами `Шаг | Статус | Что сделано | Как проверено`; столбец «Коммит», если он есть в таблице, не заполняется и не мешает;
  - последняя таблица в `journal/decisions.md` — `| № | Дата | Шаг | Решение | Почему | Что отвергли | Кто |`;
  - «Окружение» — `прод` или `дев`; «Выкладка» — `PhpStorm Always`, `Claude по SSH` или `вручную`.
- Т-2. Старый формат — любой из признаков:
  - журнал не в `.claude/docs` (раскладка `docs/` или параметр «Журнал» в другом месте);
  - рядом с журналом нет папки `journal/`;
  - у таблицы текущего этапа (последний раздел `## Этап N` журнала) нет столбца «Как проверено»;
  - последняя таблица `journal/decisions.md` — старая `| Дата | Решение |`;
  - «Окружение: дев+прод» или «Выкладка: вручную; дев — PhpStorm Always».

  Проверка — одна функция в `lib/`; ею пользуются хук, `kit-step.js` и `kit-journal.js`.
- Т-3. Хук старта (`session-start.js`) в проекте старого формата добавляет в контекст правило: «Журнал или параметры в старом формате (<признаки>) — до работы предложи пользователю /kit:project-init: переезд на формат kit 3.0». Это правило заменяет нынешнюю подсказку о переезде из `docs/`. `kit-step.js` и `kit-journal.js` в таком проекте ничего не пишут: код 2 и то же сообщение.
- Т-4. `/kit:project-init` в существующем проекте переводит всё старое одним запуском; в плане на согласие — строка на каждый найденный признак:
  - переезд `docs/` → `.claude/docs` (нынешний п. 4.7);
  - журнал на части (`journal-split.js --migrate`; сейчас это вопрос — становится обязательным пунктом плана);
  - столбец «Как проверено» в таблице текущего этапа (у старых строк — пустой);
  - новая таблица решений под старой: строка `С kit 2.8 — с обоснованием:` и шапка;
  - старые значения параметров: `дев+прод` — вопрос, какой сервер у проекта один (прод или дев); `вручную; дев — PhpStorm Always` — `Окружение: дев` и `Выкладка: PhpStorm Always`, с подтверждением;
  - строки удалённых параметров («Код пишет», «Коммит») — предложить убрать.

  Отказ от переезда — kit 3.0 в проекте шаги не закрывает (Т-3); это сказано в тексте вопроса.

  Переезд закрывается шагом п. 4.8 — очередным шагом текущего этапа. Если открытого этапа нет — первым шагом нового этапа «переезд на kit 3.0» (`STAGE`), а NEXT — следующий шаг из «Сейчас» или `—`. Решение агента: шаги закрытых этапов скрипт не правит (Т-8).
- Т-5. Удаляются:
  - режим «Код пишет: пользователь» — правило хука, вопрос и параметр в `/kit:project-init`, варианты шаблона `CLAUDE.md`, ветка «Работает / Не работает» в step-done;
  - параметр «Коммит» со значением «сразу» — просмотр перед коммитом всегда, правило хука о просмотре — без условия;
  - в скриптах (`session-start.js`, `lib/project.js`, `lib/deploy.js` и где найдутся) — поддержка старых значений «Окружения» и «Выкладки», раскладки `docs/` (`docsRel === '.'`) и журнала одним файлом.

  Строки удалённых параметров в существующих `.claude/CLAUDE.md` никто не читает, поэтому они не мешают.
- Т-6. Правило хука «Код пишет Claude: после записи проверить результат на сервере» — только если у окружения задан адрес сервера (`Прод` при «Окружение: прод», `Дев` при «дев»). Без сервера, как в claude-kit, правила нет. Варианты правила для SSH и автозаливки — как сейчас, с уточнением Т-24.

### Скрипт журнала `kit-journal.js` вместо агента docs-keeper

- Т-7. Вызов из корня проекта, из Bash; блоки подаются heredoc с кавычками, как сообщение `kit-commit.js`:
  ```
  node kit-journal.js <<'KIT_BLOCKS'
  STEP: 36.3
  STATUS: ✅
  SUMMARY: …
  CHECK: …
  NEXT: 36.4 — …
  DECISIONS:
  - 2026-10-16 | … | … | … | пользователь
  KIT_BLOCKS
  ```
  Блоки — те же, что получал docs-keeper:
  - обязательные: `STEP`, `STATUS` (`✅`, `⏳`, `⏸`, `❌`), `SUMMARY`, `CHECK` (при `✅` обязателен), `NEXT` (`ID — строка` или `—`);
  - необязательные: `STAGE`, `DECISIONS`, `DOCS`, `BUGS`, `PROD_TODO`, `DEPLOY`, `NOTES`, `RECONCILE` и новый `BLOCKERS`.

  Однострочный блок записывается как `КЛЮЧ: значение`, многострочный — `КЛЮЧ:`, а за ним строки `- …` до следующего ключа. Код 4 (ничего не записано): неизвестный ключ, обязательный блок без значения или неверный STATUS. Блоков `COMMITS` и `RULES` больше нет (Т-12, Т-15).
- Т-8. Что делает скрипт (правила — из нынешнего docs-keeper, в одном формате Т-1):
  - **Строка STEP** в таблице этапа N (N — часть STEP до первой `.`; у ID не вида `N.M` — этап из `STAGE`, иначе текущий): обновить «Статус», «Что сделано» (SUMMARY), «Как проверено» (CHECK); строки нет — добавить по порядку ID. Столбцы определяются по шапке. Таблицы этапов, уже перенесённых в `journal/stages/`, скрипт не правит: код 2 «этап N уже перенесён — шаг пишется в текущий этап».
  - **`STAGE`** — новый раздел `## Этап N — название` в конце журнала с таблицей `| Шаг | Статус | Что сделано | Как проверено |` и строка `| N | название | ниже |` в оглавлении «Этапы».
  - **STATUS `✅`** — у NEXT ставится `⏳` (строки нет — добавить; «Что сделано» — текст NEXT после ID). NEXT `—` — ничего.
  - **«Сейчас»** — снимок, пункты переписываются целиком:
    - «Этап» — `N — название (начат ГГГГ-ММ-ДД); последний шаг <STEP> — <SUMMARY>`; дата начала берётся прежняя, у нового этапа — сегодняшняя; этап закрыт (NEXT `—` при STEP вида `N.M`) — `N — название — закрыт ГГГГ-ММ-ДД`;
    - «Следующий шаг» — NEXT; при NEXT `—` — «нет — этап закрыт»;
    - «Блокеры и открытые вопросы» — текст `BLOCKERS` целиком, если блок передан, иначе прежний текст.
  - **`DECISIONS`** (`ГГГГ-ММ-ДД | решение | почему | что отвергли | кто`) — строки в последнюю таблицу `journal/decisions.md`. № — следующий, «Шаг» — STEP. «Почему» и «что отвергли» могут быть `—`. Если текст начинается с «Заменяет №N», в строку №N дописывается ` → заменено №M`.
  - **`DOCS`** (`<путь> — <о чём> — <статус>`) — реестр «Документы»: путь уже есть — обновить; есть «(было <старый путь>)» — найти строку по старому пути и заменить путь; иначе добавить.
  - **Чек-лист плана** — только при `✅`. Ищется в документах реестра со статусом `в работе, этап N` (пути `work/…`) и в документе, который этот же вызов переносит в архив (`archive/…` из `DOCS`). Строка `- [ ] <STEP> — …` становится `- [x] …`; строки нет — предупреждение.
  - **`BUGS`** (`<№> | <баг> | <где> | <статус>`) — «Баги на потом»: № уже есть — обновить переданные непустые поля; нет — добавить. Если № не указан, берётся следующий с той же приставкой, что у последней строки.
  - **`PROD_TODO`** — пункты в «Прод: не забыть»; заглушка «(пока пусто)» убирается.
  - **`NOTES`** — пункты в «Справочник» `journal/reference.md`. Строка с приставкой «Заказчик:» идёт в «Материалы заказчика» (без приставки). «Отчёт заказчику: …» — дословно в «Справочник».
  - **`RECONCILE`** — под таблицей этапа N строка `Сверка ГГГГ-ММ-ДД (сверено с: …): пунктов M, сделано K; расхождения: ….`. Если «на следующий этап» не `—`, в конец «Блокеров» дописывается `на следующий этап (сверка этапа N): …`.
  - **`DEPLOY`** — план выкладки:
    - `Файлы` (с `Коммит` и `Проверка`) — строка в «Залито на прод» или «Залито на дев» по «Окружению»; при «Выкладка: PhpStorm Always» строка не пишется, вместо неё предупреждение «при автозаливке «Залито» не ведётся»;
    - `Удалить` — строки в «Удалить с сервера»;
    - `Чек-лист` — пункты «Чек-листа переключения».
- Т-9. Повторный вызов с теми же блоками ничего не удваивает: строка шага правится на месте; строка DECISIONS, BUGS, DOCS, NOTES, PROD_TODO или RECONCILE, уже записанная дословно, второй раз не добавляется.
- Т-10. Всё или ничего: изменения собираются в памяти. При ошибке скрипт ничего не записывает, выдаёт код 2 и причину. Ошибки: журнала нет, старый формат, нет раздела этапа для строки, таблица не разбирается. Запись — через временные файлы, как в `journal-split.js`.
- Т-11. Вывод:
  - раздел «Сейчас» после правки;
  - список изменённых файлов — пути от корня проекта, по одному в строке, готовые для `kit-commit.js`;
  - предупреждения: `в плане <путь> нет строки <STEP>`, «при автозаливке «Залито» не ведётся», «нет CHECK при ✅».

  Коды: 0 — записано; 1 — записано с предупреждениями; 2 — ничего не записано (Т-10); 4 — неверные блоки (Т-7).
- Т-12. `.claude/CLAUDE.md` скрипт не трогает. Правило проекта (бывший блок RULES) Claude правит сам, одной правкой (Edit), и передаёт строку DECISIONS `Правило: <что изменилось> | <почему> | — | пользователь`; файл — в путях коммита.
- Т-13. Агент `kit:docs-keeper` удаляется совсем и запасным не остаётся — как git-keeper (решение №23). Удаляются `agents/docs-keeper.md`, раздел «Если агент не подхватился» в step-done и упоминания в скиллах, шаблонах, хуке, скриптах, описаниях плагина, README, обзоре и тестах. История (журнал, архив) остаётся как есть.

### Подготовка и завершение шага — по одной команде

- Т-14. `kit-step.js` — подготовка шага, только чтение, из корня проекта: `node kit-step.js [<STEP>]`. Печатает:
  - **файлы шага** — по `git -c core.quotepath=false status --porcelain=v1`, готовыми аргументами для `kit-commit.js`: в двойных кавычках, при переименовании — оба пути. Отдельным списком — пути, которые скрипт коммита не пропустит (`.idea/`, «Не коммитить», запреты `secret-scan.js --paths`);
  - **входящие** — записи `decision-inbox.js` готовыми строками DECISIONS: `ГГГГ-ММ-ДД | <вопрос> → <ответ> | <описание выбранного варианта или —> | <другие варианты через «; » или —> | пользователь`. Свой ответ — с пометкой `(свой ответ)`, заметки — строками `NOTES`, в конце — `входящих: N`;
  - **режим:**
    - выкладка — при «Claude по SSH» итог сухого прогона `ssh-deploy.js` («Залить N, Удалить M» или «Нечего заливать») и указание «порядок SSH — прочитай reference/ssh.md»; блок «Пропущено — не файл» — как сейчас;
    - «Документы на сервере»;
    - удалённый репозиторий — имя или `—`; если ветки там ещё нет — пометка «первая отправка»;
  - **напоминание:** если шаг закрывает этап (NEXT другого этапа или `—`), прочитай `reference/stage-close.md`.

  Коды: 0 — готово; 2 — не kit-проект, нет журнала или старый формат (Т-3); 4 — неверные аргументы.
- Т-15. Хешей коммитов в журнале больше нет:
  - блок `COMMITS`, `git log -50` и правило docs-keeper о хешах уходят;
  - новые таблицы этапов создаются без столбца «Коммит» — и в шаблоне `progress.md`, и для этапа 0 в `/kit:project-init`;
  - старые хеши в закрытых этапах остаются как есть.

  Коммит шага находится по ID в заголовке (`<ID>: …`). `/kit:report` ищет его так же — по `git log --format="%h %s"` с отбором по началу заголовка, а не по столбцу «Коммит». Таблица «Залито на …» плана выкладки:
  - при ручной выкладке строку пишет шаг, на котором пользователь сообщил о выкладке; хеш не нужен (`deploy-list.js` больше нет, Т-22);
  - при «Claude по SSH» — как сейчас: ячейка пустая, базу находит `commitOfStep`.

  `/kit:report` при «PhpStorm Always» берёт «Выложено на сайт» из шагов, закоммиченных в периоде (автозаливка их уже увезла), а не из строк «Залито». При «вручную» и «Claude по SSH» — из строк «Залито», как сейчас.
- Т-16. `kit-commit.js` — новые необязательные аргументы до `--`:
  - `--inbox N` — после проверенного коммита (код 0) убрать первые N входящих (`clearFirst` из `decision-inbox.js`); при кодах 1, 2 и 3 входящие не трогаются;

## Дизайн

**Общий модуль.** `lib/journal.js` читает и правит журнал в формате Т-1 поверх `lib/md.js` (`getSection`, `parseTable`): найти раздел и таблицу, строку по ID, вставить строку по порядку ID, переписать пункт «Сейчас», записать через временные файлы. `oldFormat(info)` возвращает признаки Т-2 (пустой список — формат текущий). Модулем пользуются `kit-journal.js`, `kit-step.js`, `session-start.js` и, где это упрощает код, `journal-split.js`.

**`kit-journal.js`.** Разбор блоков → план правок по файлам в памяти → проверка (Т-10) → запись → вывод (Т-11). Правила Т-8 — по одной функции на блок; каждая возвращает новый текст файла и предупреждения.

**`kit-step.js`.** Собирает вывод Т-14:
- `git status`;
- входящие через `readInbox` из `decision-inbox.js`, без отдельного процесса;
- сухой прогон `ssh-deploy.js` — функцией, если её можно вынести, иначе процессом;
- `git remote`;
- параметры через `kitInfo`.

**`kit-commit.js`.** `--inbox` и `--push` разбираются до `--`. После самопроверки — очистка входящих (`clearFirst`) и отправка (при первой — `secret-scan.js --history`, затем `git push -u`); код 4 — по Т-16.

**`/kit:step-done`.** Ядро — по Т-18, справки — по Т-19. Разделы нынешнего SKILL.md переезжают в справки почти без изменений; не переезжает удалённое — docs-keeper, COMMITS, «Коммит: сразу», проверка «Работает / Не работает».

**Порядок шагов (для плана).**
1. Спек и план этапа.
2. Один формат: переезд в `/kit:project-init`, `oldFormat`, правила хука, удалённые режимы, шаблоны.
3. `kit-journal.js` и `lib/journal.js`.

6. Неиспользуемое и мелкие правки: `/kit:why`, `/kit:deploy-list`; вопрос о скиллах Битрикса; пакетная проверка в браузере.
7. claude-kit: спек заморожен, правила выпуска.
8. Выпуск 3.0.0.

Каждый шаг — с тестами своей части и `npm test`.
