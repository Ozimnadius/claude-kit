# Спецификация — прод главный: вход с прода в каждой сессии (этап 48)

> Разделы kit поверх дизайна `superpowers:brainstorming`. Решения пользователя 2026-10-29 (обсуждение перед этапом) — в `journal/decisions.md` строками шага 48.1; выбранный подход и отвергнутые — там же.

## Задача

- Номер: без задачи
- Цель: kit не затирает чужие правки на проде. В начале каждой новой сессии рабочая копия и git обновляются с сервера, и только потом идёт работа.

**Почему.** Типичный случай: проект сделан и выложен, прошли месяцы, клиент просит новые правки. За это время прод меняли без нас: клиент в админке Битрикса (публичные страницы и включаемые области — это файлы), обновления Битрикса и решений Аспро, другие подрядчики. Git отстал от прода. Сейчас kit негласно считает главным git: заливка (`ssh-deploy.js --go`, автозаливка PhpStorm) пишет файл поверх, не проверяя, что лежит на сервере (`ssh-deploy.js`, `buildScript`). Чужая правка пропадает молча, сайт может сломаться, клиент недоволен.

**Что есть сейчас (прод целиком не сверяет никто):** `remote-check.js` сравнивает git только с удалённым репозиторием (GitHub); `ssh-deploy.js --md5` и `md5-check.js` сверяют файлы шага или заданный список; `/kit:project-init` скачивает исходники с сервера, только если папка проекта пуста.

**Подход (выбрал пользователь): прод главный, git — наша рабочая копия и журнал.** Работа над проектом идёт заходами:
1. **Вход** — копия обновляется с сервера: всё, что поменяли без нас, ложится в git отдельной записью.
2. **Работа** — как сейчас: шаг, заливка, проверка, коммит.
3. **Выход** — всё залито и закоммичено, ничего не висит.

Расхождение git с сервером между заходами — не авария, а норма: оно попадает в историю записью входа. Выход kit не проверяет и на него не опирается: наша работа, которая ещё не дошла до сервера, при входе не теряется (Т-5).

**Принцип пользователя:** «простая система, надёжная, как молоток; меньше морочек и действий».

- **Цели:** вход сам, без действий пользователя (по SSH); правки сайта не начинаются, пока вход не сделан; чужие изменения видны в истории; пользователь узнаёт о них одной строкой.
- **Не цели:** страховка во время работы — проверка сервера перед каждой записью (пользователь отказался: «хватит входа»; правку клиента, сделанную в ту же сессию, можно затереть — это принято); база данных; запрет правок на проде для клиента.
- **Анти-цели (провал, даже если работает):** вход откатывает или удаляет нашу работу; вопросы пользователю по каждому файлу; ручные шаги там, где есть SSH; «молоток заклинило» — kit не даёт работать, когда сервер недоступен, и выхода нет; в git попадают бэкапы и архивы; заметно медленный старт сессии в проекте, где ничего не менялось.

## Требования

Сервер — сервер окружения (`serverEnv` в `lib/project.js`: «Окружение: дев» — дев, иначе прод); SSH — параметр «SSH прод» / «SSH дев» (`serverSsh` в `lib/ssh.js`). **Файлы сайта** — пути внутри папки проекта, которые выкладываются: не под `ALWAYS_SKIP` и «Не выкладывать» (`skipRules` в `lib/deploy.js`), не в `.claude/`.

- Т-1. **Где работает.** Kit-проект, у которого задан адрес сервера окружения («Прод» или «Дев») или SSH окружения. Иначе — тишина, поведение kit прежнее (например, этот репозиторий: «Прод: —»).
- Т-2. **Когда.** Вход нужен в каждой новой сессии Claude Code: запуск, возобновление старой сессии, `/clear`, ответвление (fork). Сжатие контекста (`compact`) — та же сессия, вход не повторяется. Строка в контексте при старте говорит Claude сделать вход первым делом (по SSH) — до первой правки файлов сайта. Если строка `remote-check.js` требует `git pull --ff-only` — сначала pull, потом вход.
- Т-3. **Запрет правок до входа.** Пока в текущей сессии вход не сделан или не пропущен по решению пользователя (Т-10), хук не пускает Write, Edit, MultiEdit, NotebookEdit файлов сайта — с подсказкой, какой командой сделать вход. Правки `.claude/` (журнал, документы, правила), файлов «Не выкладывать» и файлов вне папки проекта проходят.
- Т-4. **Что сверяется.** Файлы сайта, которые ведёт git, и новые файлы на сервере в путях, которые git не игнорирует (`.gitignore` проекта) и которые выкладываются. Ядро, загрузки, кеш (исключены `.gitignore`) — вне сверки. Чего вход не забирает — Т-11.
- Т-5. **Три версии файла.** Каждый файл сравнивается в трёх версиях (отсутствие файла — тоже версия):
  - **база** — последняя точка, где сервер точно совпадал с git: самый поздний из коммитов — последний коммит входа и коммит последней строки «Залито на …» плана выкладки (`baseFromPlan` в `lib/deploy.js`); нет ни того, ни другого — первый коммит репозитория (исходники с сервера);
  - **HEAD** — наш git;
  - **сервер** — что лежит там сейчас.

  | Сервер | HEAD | Что это значит | Что делает вход |
  |---|---|---|---|
  | = база | любой | на сервере без нас не меняли | ничего: наше незалитое остаётся как есть |
  | ≠ база | = база | изменили без нас | забрать версию сервера |
  | = HEAD | ≠ база | наше уже на сервере | ничего |
  | ≠ база и ≠ HEAD | ≠ база | менялось и у нас, и без нас | совместить (Т-8) |

  Файл, удалённый нашим шагом, но ещё лежащий на сервере (раздел «Удалить с сервера» плана выкладки или удалён коммитом шага), вход не возвращает, а называет в строке «ждёт удаления с сервера». Старая или неточная база правил не ломает: больше файлов попадёт в «наше уже на сервере» или в совмещение, которое сойдётся само.
- Т-6. **Вход по SSH.** Сверка без записи на сервер; версии «изменили без нас» скачиваются в рабочую копию байт в байт (удалённые без нас — удаляются локально). Затем один коммит через `kit-commit.js` — **без просмотра и без вопросов** (прод главный) — с заголовком, по которому коммит входа отличим от шагов (например, `Прод: изменения без kit на ГГГГ-ММ-ДД (N файлов)`), и списком файлов в теле; при заданном «Удалённом репозитории» — с `--push`. Нечего забирать — коммита нет.
- Т-7. **Что видит пользователь.** Одну строку: сколько файлов на сервере изменено, добавлено и удалено без kit. Отдельно — файлы с нашими прошлыми доработками (их меняли коммиты шагов, а не только первый коммит и коммиты входа), путями: клиент или обновление (например, Аспро) могли их затереть. Отдельно — что не забрано (Т-11) и что ждёт удаления с сервера (Т-5). Нечего забирать — одна короткая строка «прод совпадает с git».
- Т-8. **Наши незакоммиченные правки и совмещение.** Сервер совпадает с рабочей копией — это наша правка, уже на сервере (автозаливка, `--go` без коммита, работа исполнителя Мэтта до приёмки): вход её не трогает и в строку не включает — её закроет шаг. Файл менялся и у нас (в HEAD или в рабочей копии), и без нас — совместить (база; наша — рабочая копия; их — сервер), показать результат пользователю в панели изменений; не совмещается само — стоп и вопрос. В коммит входа идут только версии «изменили без нас»; совмещённое и наши правки остаются незакоммиченными поверх.
- Т-9. **Без SSH.** Рабочая копия должна быть чиста: иначе предупредить, что скачивание затрёт незакоммиченные правки, и спросить. Claude даёт короткий список папок и файлов для скачивания по FTP (корни того, что сверяет Т-4) и как скачать в PhpStorm. После ответа «скачал» — правила Т-5, где «сервер» — скачанная версия: файлы, которые скачивание вернуло к базе поверх нашего незалитого (HEAD ≠ база, скачанное = база), возвращаются из HEAD; дальше — коммит и строка, как в Т-6 и Т-7. Удалённые на сервере файлы так не видны — это ограничение. Пользователь может ответить «не буду скачивать» — как «Работать без входа» в Т-10. Без SSH вход нужен не первым делом, а перед первой правкой файлов сайта (её останавливает Т-3): просто поговорить о проекте можно без скачивания.
- Т-10. **Вход не удался** (нет сети, SSH не пустил, вышло время): Claude называет причину и спрашивает через AskUserQuestion: «Повторить» / «Работать без входа». «Без входа» — отметка «пропущен по решению пользователя» на эту сессию; хук Т-3 пропускает правки; ответ попадает во входящие как решение.
- Т-11. **Чего вход не забирает.** Бэкапы и архивы — как при первом скачивании в `/kit:project-init` (раздел 6 справки `reference/ssh.md`: `_*.back*`, `_*_back*.zip`, `*.tar.gz*`; полный список — на усмотрение исполнителя) — и файлы больше предела (ориентир 10 МБ). Они остаются на сервере; вход называет их в строке один раз (что уже названо — помнит отметка входа); дописать путь в `.gitignore` Claude может по просьбе пользователя. Забрать за один вход нужно больше ориентира 50 МБ — стоп и один вопрос: какие папки не забирать.
- Т-12. **Повтор безопасен.** Оборванный вход не оставляет наполовину записанных файлов и коммита с частью файлов; повторный запуск доводит вход до конца.
- Т-13. **Заливка после входа.** База заливки (`resolveBase` в `lib/deploy.js`) остаётся прежней — иначе наши незалитые шаги выпали бы из заливки. Файлы, которые после базы заливки менялись только коммитами входа и не изменены в рабочей копии, `ssh-deploy.js` («Claude по SSH») не заливает: они уже на сервере. Заливка документов (`--docs`) — как прежде.
- Т-14. **PhpStorm Always.** Скачанное входом PhpStorm может залить обратно (`autoUploadExternalChanges`) — это те же байты, вреда нет. Опасность — File Watchers (справка `project-init/reference/phpstorm.md`, «Грабли»): если вход забирает исходник, который пересобирает watcher (SCSS, LESS, минификация), пересборка перезапишет результат и PhpStorm зальёт его на сервер. Такие файлы вход называет пользователю до скачивания и не скачивает без его ответа.
- Т-15. **Проекты Мэтта и worktree.** Вход делает общая сессия в основной папке проекта. Исполнитель (подчинённая сессия) и сессия в worktree коммитов входа не делают: вход только сверкой, без скачивания; нечего забирать — работа идёт; есть что забрать — стоп и сообщение: вход — в общей сессии (в основной папке). Задание исполнителю (`/kit:matt`) говорит об этом. Субагенты работают в сессии, которая их запустила, и входа не повторяют (предположение — проверить).
- Т-16. **`/kit:project-init`.** Исходники с сервера в пустую папку (раздел 6 справки `reference/ssh.md`) засчитываются входом этой сессии. Шаблон `CLAUDE.md`, README, обзор и правила при старте сессии — по новому поведению.
- Т-17. **Проверки:** тесты скрипта входа (заглушка `KIT_SSH`, как у тестов `ssh-deploy.js`) — все строки таблицы Т-5, Т-8, Т-11, обрыв; тесты хука Т-3 и строки при старте; `npm test`, `claude plugin validate plugins/kit --strict`, `claude plugin validate . --strict`, `node tools/kit-denylist.js tree`.
- Т-18. **Выпуск kit 3.4.0:** версии в `plugin.json`, `marketplace.json` и «Версия kit» в `.claude/CLAUDE.md`; README — раздел «Прод главный»; обзор `work/overview/` — новый скрипт и хук (правило выпуска).
- Т-19. **Обезличенно:** в файлах и коммитах — без имён проектов, клиентов, доменов, учёток и IP.

## Критерии готовности

Живая проверка — на дев-стенде или копии сайта, не на проде клиента:
- по SSH: на сервере изменить отслеживаемый файл, добавить новый файл в отслеживаемую папку, удалить отслеживаемый файл, изменить файл с историей шагов → новая сессия → правка файла сайта до входа — отказ хука с подсказкой → вход сам → один коммит входа, строка с тремя числами и пометкой о доработках; `git status` после входа — как до него; повторный вход — «прод совпадает с git», коммита нет;
- закоммиченный, но не залитый шаг («Claude по SSH» без `--go`) → вход его не откатывает; `ssh-deploy.js` после входа предлагает залить файлы шага и не предлагает файлы входа;
- наша незакоммиченная правка уже на сервере (автозаливка) → вход её не трогает, в строке её нет;
- наша незакоммиченная правка и изменение того же файла без нас → совмещение показано в панели, в коммите входа — только версия сервера;
- файл, удалённый нашим шагом, лежит на сервере → вход не возвращает, строка «ждёт удаления с сервера»;
- архив и файл больше предела на сервере → не забраны, названы в строке один раз;
- без SSH: список для FTP; после «скачал» — коммит и строка;
- сервер недоступен — вопрос «Повторить / Работать без входа»; после «без входа» правки проходят;
- PhpStorm Always: после входа md5 скачанных файлов на сервере не изменились;
- проект без сервера («Прод: —») и этот репозиторий — поведение прежнее;
- проверки Т-17 зелёные.

## Предположения

- На серверах есть `sh`, `find`, `md5sum`, `base64` — как уже требует `ssh-deploy.js`.
- Хуки получают `session_id` (его уже пишет `decision-inbox.js`), а SessionStart — источник: startup, resume, clear, compact, fork (их перечисляет `hooks.json`).
- Субагенты (Agent) вызывают инструменты с `session_id` сессии, которая их запустила, — проверить вживую.
- Переводы строк: сервер может отдавать CRLF при LF в git — сравнение учитывает это, как `md5-check.js` (md5 как есть и с LF).
- Отметка входа в `.claude/` не попадёт в git: `.gitignore` проектов исключает `/.claude/*`, кроме правил, документов и скриптов.

## Дизайн

**Компоненты** (имена — рабочие, исполнитель может выбрать другие):
1. **Скрипт входа** `prod-entry.js`. Режимы: сверка и забор по SSH (по умолчанию); только сверка (Т-15); без SSH — список для FTP и разбор после скачивания (Т-9); пропуск по решению пользователя (Т-10); `--hook` для SessionStart (Т-2). Коды выхода по образцу `ssh-deploy.js`: 0 — вход сделан (или нечего забирать), 1 — нужен ответ пользователя (совмещение, File Watchers, больше 50 МБ; при «только сверке» — есть что забрать), 2 — вход не нужен или параметры неверны, 3 — нет подключения, обрыв, вышло время, 4 — аргументы, git.
2. **Отметка входа** — файл в `.claude/` (например, `.claude/kit-prod.json`): `session_id`, время, итог (сделан / пропущен), коммит входа, уже названные в строке файлы (Т-11). Новую сессию хук SessionStart распознаёт по `session_id`; при `compact` отметка остаётся.
3. **Хук Т-3** — PreToolUse на `Write|Edit|MultiEdit|NotebookEdit`: отдельный скрипт или ветка в существующем `guard-matt.js` (он уже стоит на этих инструментах, но работает только в проектах Мэтта). Нет отметки текущей сессии — отказ с подсказкой.
4. **Строка при старте** — отдельным хуком SessionStart (или `prod-entry.js --hook`) после `remote-check.js`: вывод `session-start.js` в проекте Мэтта уже у предела (8 990 символов при тесте ≤ 9 000).
5. **Коммит входа** — через `kit-commit.js`: он проверяет пути и секреты (секрет в скачанном файле — код 1, разбор с пользователем, как у шагов). Заголовок входа отличает коммит от шагов: по нему находятся база Т-5, «наши доработки» Т-7 (файлы из коммитов, кроме коммитов входа и первого коммита) и файлы, которые не заливаются по Т-13.
6. **Совмещение** — трёхстороннее, `git merge-file` (база, наша, их); результат остаётся незакоммиченным для просмотра.

**Сверка по SSH** (на усмотрение исполнителя, ориентир): сервер отдаёт список файлов (`find`), крупные исключённые папки (`/bitrix`, `/upload` по `.gitignore`) и бэкапы с архивами отрезаются ещё на сервере, вместе с размером файла; список фильтруется локально (`git check-ignore --stdin`, правила выкладки, предел размера); по оставшимся — md5 (как есть и с LF); сравнение с базой и HEAD по таблице Т-5. Версии «изменили без нас» — скачать одним подключением (base64), при большом объёме — порциями; запись через временный файл и переименование, сверка md5 после записи.

**Ошибки:** нет подключения — код 3 и вопрос Т-10; обрыв посередине — повтор доводит до конца (Т-12); секрет в скачанном — остановка `kit-commit.js`, как у шагов; File Watchers при Always и больше 50 МБ — код 1 и вопрос.

- сверка в три версии с базой «последняя точка совпадения» (Т-5) — по проверке спека исполнителем: сравнение только с HEAD откатило бы наши незалитые шаги («вручную», Мэтт без пользователя, удаления при автозаливке); отвергнуты: остановка и вопрос при незалитых коммитах, вход без ручной выкладки, обязательный проверяемый выход;
- сервер совпадает с рабочей копией — это наша незакоммиченная правка, вход её не трогает (Т-8);
- бэкапы, архивы и файлы больше 10 МБ не забираются, больше 50 МБ за вход — один вопрос (Т-11): иначе первый же вход затащил бы в git гигабайты, а отправка на GitHub не прошла бы (предел 100 МБ на файл);
- копии файлов на сервере перед перезаписью не нужны — откат из git;
- без SSH вход — перед первой правкой, а не первым делом (Т-9);
- исполнитель Мэтта и сессия в worktree только сверяют (Т-15).

## Вне этапа

- Проверка сервера перед каждой записью во время работы — отвергнута пользователем.
- База данных: тексты и настройки, изменённые в админке.
- Перенос с дева на прод (при «Окружение: дев» сверяется дев; правки клиента на проде — вне kit, как и перенос).
- Правки через Bash в обход Write/Edit (sed, копирование, скрипты) — хук Т-3 их не видит.
- Правки пользователя в PhpStorm до входа и открытые в редакторе файлы с несохранёнными правками (общий риск автозаливки, справка `phpstorm.md`).
