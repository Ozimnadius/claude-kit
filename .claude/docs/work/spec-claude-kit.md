## 1. Цель

Убрать рутину при старте и ведении каждого проекта пользователя: перенос агентов, объяснение правил работы, журнал в `.md`, настройка git и исключений деплоя. У пользователя ~45 папок в `C:\OSPanel\home`, из них ~30 сайтов `*.server`, почти все — 1С-Битрикс (часто Аспро).

Образцы, из которых обобщено: `gamma.server` (дев + прод, код пишет пользователь, выкладка на прод вручную), `alpha.server` (дева нет, код пишет Claude, PhpStorm-автозаливка Always на прод), `epsilon.server` (MODX; урок про nginx и `.htaccess`).

## 3. Проверенные факты о Claude Code (2.1.278, документация на 2026-09-23)

- Маркетплейс: `.claude-plugin/marketplace.json` в корне. Документация утверждает, что плагин с относительным `source` из локального маркетплейса грузится на месте, но на практике (2.1.278, 2026-09-23) `claude plugin install kit@claude-kit` скопировал его в `~/.claude/plugins/cache/claude-kit/kit/1.0.0` (`installPath`, `gitCommitSha` в `installed_plugins.json`), а `claude plugin update` без повышения версии ответил «already at the latest version». Выпуск изменений — только с повышением `version`.
- Скиллы плагина — `/<плагин>:<скилл>`; агенты — `<плагин>:<агент>`. Вызов без префикса работает: `/step-done` разрешается в `/kit:step-done`, если имя уникально (проверено 2026-09-23).
- Проектный агент `docs-keeper` и плагинный `kit:docs-keeper` — **разные имена**, проектный плагинный не перекрывает, они живут рядом. Приоритет «проект → пользователь → плагин» действует только при совпадении имени.
- Плагинные агенты игнорируют `hooks`, `mcpServers`, `permissionMode`.
- В тексте скиллов и агентов подставляются `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_DATA}`.
- Плагин не поставляет `CLAUDE.md`; общие правила процесса подставляет хук `SessionStart`.
- Хуки: `hooks/hooks.json` с обёрткой `{"hooks": {...}}`; JSON на stdin (`cwd`, `hook_event_name`, `tool_name`, `tool_input.file_path`, `tool_input.command`, у SessionStart — `source`). Exec-форма `"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/…"]` идёт без оболочки — на Windows это надёжнее Git Bash.
- SessionStart: обычный stdout добавляется в контекст. PostToolUse: exit 2 — stderr видит Claude (вызов уже выполнен). PreToolUse: JSON `hookSpecificOutput.permissionDecision: "deny"` + `permissionDecisionReason` (или exit 2 + stderr) блокирует вызов.
- CLI: `claude plugin validate <путь> [--strict]`, `claude plugin marketplace add|update|list|remove`, `claude plugin install <плагин>@<маркетплейс> [-s user|project|local]`, `claude plugin details`, `claude --plugin-dir <путь>` для проверки без установки.
- Постоянная папка данных плагина (`${CLAUDE_PLUGIN_DATA}`) — `~/.claude/plugins/data/<плагин>-<маркетплейс>` (`kit-claude-kit`); у плагина, загруженного через `--plugin-dir`, — своя (`kit-inline`), проверено 2026-09-25. Поэтому зависимости снимков держим не там, а в `%LOCALAPPDATA%\kit\visual` — общая папка для установленного плагина и разработки.
- Защищённые пути (документация `permission-modes#protected-paths`, проверено 2026-09-28): папки `.claude` (кроме `.claude/worktrees`), `.idea`, `.git`, `.vscode` и др. Запись в них инструментами Edit/Write: `default`/`acceptEdits` — подтверждение (в вопросе есть вариант «разрешить правки в `.claude` этого проекта на сессию»), `auto` — решает классификатор, `bypassPermissions` — без вопросов, `dontAsk` — запрет; `permissions.allow` вроде `Edit(.claude/**)` подтверждение **не** снимает. Субагенты (docs-keeper) подчиняются тому же. Хуки — внешние процессы, эта проверка их не касается. `.claude/docs/*.md` в контекст сами не загружаются (автозагрузка — только `.claude/CLAUDE.md` и `.claude/rules/*.md`).
- SSH (проверено 2026-09-24 на alpha, хостинг ispmanager): `ssh` есть и в Git Bash (`/usr/bin/ssh`, OpenSSH 9.9), и в Windows (`System32\OpenSSH`), оба читают `~/.ssh/config`; с `-o BatchMode=yes` ssh не спрашивает ни пароль, ни отпечаток нового сервера (сразу ошибка, код 255); команда `php` на сервере может быть старой (на alpha — 5.4), нужные версии — полным путём (`/opt/php74/bin/php`); страж `guard-bash` команду `ssh alpha '…'` не блокирует.

**Обновление:** установленный плагин — копия в кэше, снятая с основного checkout (ветка `master`). Выпуск: поднять `version` в `plugin.json` и `marketplace.json` (одинаково — это проверяет тест манифестов и `claude plugin tag`) → слить в `master` → `claude plugin marketplace update claude-kit` и `claude plugin update kit@claude-kit` → перезапустить сессии. Без повышения версии обновление не происходит. Проверка без выпуска — `claude --plugin-dir …\plugins\kit`.

**Главное правило всех хуков и инструментов:** вне kit-проекта — тишина. Плагин ставится на пользователя и работает во всех папках, поэтому без журнала и раздела параметров хуки ничего не выводят и ничего не блокируют.

«Kit-проект» — папка, где есть раздел «Параметры для агентов» в `.claude/CLAUDE.md` **или** файл журнала (по умолчанию — ниже).

**Папка документов** (`lib/project.js`, с 2.3.0):
- журнал — параметр «Журнал»; не задан — первый существующий из `.claude/docs/progress.md` и `docs/progress.md` (старая раскладка); нет ни одного — `.claude/docs/progress.md`;
- папка документов — папка журнала (`.claude/docs`, у непереехавших — `docs`); новых параметров нет;
- план выкладки — параметр «План выкладки», не задан — `deploy-prod.md` в папке документов;
- внутри папки документов: `work/` — текущие планы, спеки, чек-листы, материалы задач; `archive/` — готовое и устаревшее; `visual/` — снимки `/kit:visual` (только локально). Та же раскладка работает и в старой `docs/`.
- `kitInfo(dir)` → `{ dir, params, journalRel, journalPath, hasJournal, docsRel, planRel, visualRel, isKit }` (пути — от корня проекта, через `/`; журнал в корне проекта — `docsRel` = `.`, `visualRel` = `visual`); `docsInClaude(docsRel)` — папка документов внутри `.claude` (её закрывает исключение `.claude`).

Разбор (`lib/params.js`):

- обратные кавычки вокруг значения и элементов списка снимаются; запятая внутри обратных кавычек или скобок не делит список;
- `—`, `-` и пустое значение — «не задано»;
- неизвестные ключи сохраняются (для будущих параметров), ошибкой не считаются;
- `readParams(projectDir) → { found, file, values: {ключ: строка}, list(ключ) → string[], get(ключ, умолчание) }`.

Правила путей (`lib/paths.js`) — для «Не коммитить», «Не выкладывать» и базовых запретов; элемент списка — `шаблон` или `шаблон (кроме a, b)`:
- токен **со `/` в любом месте** — в начале, в середине или в конце (`/bitrix`, `local/modules`, `bitrix/`) — путь от корня проекта и всё внутри: `bitrix/` ловит `bitrix/.settings.php`, но не `local/templates/…/components/bitrix/…` (копии шаблонов компонентов коммитятся), `upload/` не ловит `local/components/my/upload/…`;
- токен **без `/`** (`.idea`, `.settings.php`, `*.back*`) — имя любого сегмента пути на любой глубине;
- `*` — внутри сегмента, `**` — через сегменты; маска со `/` проверяется по пути и по папкам-предкам; регистр не важен, `\` равен `/`;
- `(кроме …)` — исключения по тем же правилам: `upload/ (кроме upload/docs/)`.

Базовые запреты зашиты в агентов и инструменты, параметры их **дополняют**, не заменяют:
- не коммитить никогда: `.idea/`, `*.back*`, любые `.settings.php`, `.settings_extra.php`, `dbconn.php`, `.env*` (кроме `.env.example`), `*.pem`, `*.key`, `.claude/settings.local.json`, `.claude/worktrees/`, `/kit-exec.php` (файл-канал `/kit:server`, с 2.4.0; только корень), `docs/visual/` и `.claude/docs/visual/` (снимки `/kit:visual` из-под админа; обе раскладки);
- секреты: вебхук Б24 `bitrix24.<домен>/rest/<число>/<токен>`, приватные ключи `-----BEGIN … PRIVATE KEY-----`, присваивания с непустым строковым значением ключам `password|passwd|secret|token|api_?key|DBPassword` (`=>`, `=`, `:`; через `,` — `define('SMTP_PASSWORD', '…')` — только значение с цифрой), `apikey=<значение>` в URL. Не секреты: короткие (< 16) слова из букв (`'Пароль'`, `'login'`), переменные и подстановки шаблонов — `$key`, `${KEY}`, вывод PHP `<?=$apiKey?>` (шаблон Битрикса `sale.order.ajax`: `?apikey=<?=$apiKey?>`), `<%=key%>`, `{{key}}`, `{!!$key!!}`, `{$key}`, макрос Битрикса целиком `#API_KEY#` (`#Qw3rty` — находка), вне URL ещё `%s`/`%PASSWORD%` (в URL `%` — не подстановка: ключ бывает закодирован, `%2B…`); после `,` — значения без цифр: списки имён полей (`"PASSWORD", "CONFIRM_PASSWORD"`) и соседние аргументы (`setRequestHeader('X-Auth-Token', 'application/json')`). При `=>`, `=`, `:` длинные значения из латиницы с `_` (`$DBPassword = 'bitrix_secret_db'`) — находка. В файлах `.env*` (в том числе `.env.example`), YAML, INI, conf, TOML и properties — ещё значение без кавычек (`KEY=value`, `ключ: значение`, `- KEY=value` в compose), где в ключе `PASSWORD|PASSWD|SECRET|TOKEN|API_KEY` («пароль или токен (без кавычек)»; `DB_PASSWORD=` и `DB_PASSWORD=changeme` — не находка). Ключ-указатель (`…_URL|_URI|_ENDPOINT|_PATH|_FILE` или имя на `name`: `secretName`) — не находка, если в значении нет `@` (учётных данных в адресе); решает имя ключа, а не начало значения: `AWS_SECRET_ACCESS_KEY=/…` и `SLACK_TOKEN=https://…` — находки. Значения YAML не литералом (`!тег`, `&якорь`, `*псевдоним`, `|`, `>`, `[…]`, `{…}`) — не находка. Каждый шаблон перебирает все совпадения в строке: отклонённое (например, список полей) не прячет секрет дальше в той же строке; находка — первое совпадение, прошедшее проверку, по одной на шаблон и строку.

## 6. Агенты

### 6.1 `kit:docs-keeper` (model: sonnet; tools: Read, Edit, Write, Grep, Glob)

Работает в текущей рабочей папке (корень проекта). Читает раздел параметров: `Журнал` (не задан — `.claude/docs/progress.md`, а если его нет, но есть `docs/progress.md` — он), `План выкладки` (не задан — `deploy-prod.md` в папке журнала), `ID шага`. Правит только журнал, план выкладки и `.claude/CLAUDE.md` (последний — только при блоке RULES). Файлы не переносит (перенос в архив делает `/kit:step-done`, §7.1).

Вход (блоки в тексте запроса):
- обязательно: `STEP`, `STATUS` (`✅` / `⏳` / `⏸` / `❌`), `SUMMARY` (одна строка: что сделано), `CHECK` (с 2.8.0; одна строка: как проверено; при `✅` обязателен — нет его, шаг записывается с предупреждением «нет CHECK»), `NEXT` (ID и одна строка);
- необязательно: `COMMITS` (хеши прошлых шагов `1.1=abc1234, 0.7=def5678` — заполнить только пустые ячейки «Коммит»), `STAGE`, `DECISIONS`, `DOCS`, `BUGS`, `PROD_TODO`, `DEPLOY`, `NOTES`, `RULES`.

`DECISIONS` (с 2.8.0) — по строке на решение: `ГГГГ-ММ-ДД | решение | почему | что отвергли (или —) | пользователь / агент`. «Почему» обязательно: строку без него docs-keeper не записывает и называет в отчёте («не записано: нет "почему"»).

`DOCS` — строки реестра документов, по одной на документ: `<путь от папки документов> — <о чём> — <статус>`; при переносе — `archive/x.md (было work/x.md) — … — …`. Статусы: `в работе, этап N`, `готово, этап N (ГГГГ-ММ-ДД)`, `устарел — <чем заменён>`, `постоянный` (документ на все этапы — спек, замечания пользователя; в архив при закрытии этапа не предлагается — К22, исправлено на шаге 11.12б). docs-keeper добавляет строку в раздел «Документы» или обновляет найденную (по пути, а при «было …» — по старому пути). Прежние записи журнала со старыми путями не переписывает: актуальный путь — в реестре.

Журнал — разделы в таком порядке: заголовок и строка «Ведёт агент docs-keeper…», «Сейчас» (этап, следующий шаг, блокеры), «Решения» (`№ | Дата | Шаг | Решение | Почему | Что отвергли | Кто`; в журналах до 2.8.0 — `Дата | Решение`), «Документы» (`Файл | О чём | Статус`; пути — от папки документов; сам журнал и план выкладки в реестр не входят), этапы `## Этап N — название` с таблицей `Шаг | Статус | Что сделано | Как проверено | Коммит` (до 2.8.0 — без «Как проверено»: в такую таблицу колонка не добавляется, в «Что сделано» пишется `SUMMARY; проверено: CHECK`; формат — по заголовку таблицы, ячейка «Коммит» — по заголовку колонки), «Материалы заказчика», «Баги на потом» (`№ | Баг | Где | Статус`), «Прод: не забыть», «Справочник». Правила:
1. прочитать файл целиком;
2. строка STEP: обновить статус, коммит, описание (если SUMMARY точнее); нет строки — добавить в таблицу своего этапа по порядку ID; STAGE — новый раздел с такой же таблицей;
3. `STATUS = ✅` → строке NEXT поставить `⏳` (добавить, если нет), обновить «Сейчас». С 2.11.0 «Сейчас» — снимок, не история: пункты переписываются целиком — «Этап» — только текущий этап (номер, название, дата начала, где он сейчас; закрыт — «закрыт ДАТА»), «Следующий шаг» — только NEXT (или «нет» и причина), «Блокеры» — актуальные (снятое по NOTES «снято: …» убирается, «на следующий этап» — с началом нового этапа). До 2.11.0 агент только дописывал, и «Этап» копил историю всех этапов, а «Следующий шаг» — устаревшие пометки (К52);
4. COMMITS — только пустые ячейки, заполненные не трогать; шага из COMMITS нет ни в одной таблице этапов — строку не добавлять, перечислить такие ID в отчёте;
5. DECISIONS — дописать строки в таблицу нового формата («Шаг» — из STEP, № — следующий в таблице); последняя таблица раздела старого формата `Дата | Решение` — в неё не дописывать, а завести под ней строку «С kit 2.8 — с обоснованием:» и новую таблицу (старые журналы не мигрируют); старые строки не менять, кроме пометки ` → заменено №M` в ячейке «Решение», когда новое решение «Заменяет №N»; DOCS — строки реестра «Документы» (раздела нет — завести после «Решений»); BUGS — добавить/обновить, исправленный баг не удалять, а пометить `✅ шаг X`; PROD_TODO — дописать пункты; NOTES — кратко в «Материалы заказчика» или «Справочник»;
6. markdown-таблицы, русский язык, даты `YYYY-MM-DD`; ничего не выдумывать; существующее не переписывать и не сокращать.

План выкладки — только при блоке DEPLOY. Разделы: «Общие правила» (не трогать), «Залито на прод» (`Шаг | Дата | Файлы | Коммит | Проверка`), «Удалить с сервера» (`Путь | Почему | Удалён`), «Чек-лист переключения» (нумерованный список). Поля DEPLOY: `Файлы`, `Коммит`, `Удалить`, `Проверка`, `Чек-лист`. Пути — от корня сайта; скрипты — целиком в блоках ```php.

RECONCILE (с 2.10.0) — под таблицей этапа N строка `Сверка ГГГГ-ММ-ДД (сверено с: …): пунктов M, сделано K; расхождения: ….` (повторная сверка — новая строка, старая не меняется); «на следующий этап» не `—` — в «Сейчас» → «Блокеры и открытые вопросы»: `на следующий этап (сверка этапа N): …`.

`.claude/CLAUDE.md` — только при RULES: точечно, короткий свод, без истории; история изменения (с 2.8.0) — строка в «Решения» журнала: «Правило: <что изменилось>», почему — из RULES (нет причины — строку не писать, назвать в отчёте). ### 6.2 `kit:git-keeper` (model: haiku; tools: PowerShell, Bash, Read, Grep, Glob)

Работает в репозитории текущей рабочей папки; в удалённый репозиторий не отправляет — это делает `/kit:step-done` после проверки коммита (§7.1, с 2.5.0). Файлы проекта не правит. **Один вызов — не больше одного коммита.**

Вход: `FILES` (пути от корня, включая удалённые; можно папки; пуст — стоп, ничего не коммитить), `MESSAGE` (начинается с ID шага: `2.1: …`), `BODY` (необязательно, 1–3 строки), `COAUTHOR` (строка `Co-Authored-By: …` — писать **дословно**, никогда не подставлять название своей модели; если блок не передан — коммит без неё).

Порядок (все команды, которые выводят пути, — с `git -c core.quotepath=false …`: иначе кириллические пути приходят восьмеричными escape-последовательностями и `git add` их не находит):
1. `git rev-parse --show-toplevel` (корень репозитория должен совпасть с текущей папкой), `git -c core.quotepath=false status --porcelain=v1`, `git -c core.quotepath=false diff --cached --name-status`.
2. Проверить FILES по базовым запретам (§5; в том числе `docs/visual/` и `.claude/docs/visual/`) и параметру «Не коммитить» (правила путей — §5: со `/` — от корня, `bitrix/` не запрещает `local/templates/…/components/bitrix/…`). Нашлось — стоп, ничего не коммитить.
3. Добавить в индекс: пути, которые **уже помечены в индексе как удалённые** (`git -c core.quotepath=false diff --cached --name-only --diff-filter=D`), повторно не добавлять; остальные — `git add -A -- <пути>`; если после исключения уже помеченных удалений путей не осталось, `git add` не запускать вообще. `git add` и `git commit` с пустым списком путей после `--` запрещены.
4. Секреты: `node "${CLAUDE_PLUGIN_ROOT}/scripts/secret-scan.js" --cached -- <FILES>`. Код 1 — стоп (находки); код 2 или скрипт не найден — стоп и отчёт.
5. Одна команда, всегда из Bash (с 2.10.0): `MSYS_NO_PATHCONV=1 git commit -m '<MESSAGE>' [-m '<BODY>'] [-m '<COAUTHOR>'] -- <FILES>`. MESSAGE, BODY и COAUTHOR — только в одинарных кавычках, текст — символ в символ, включая обратные кавычки, `$` и `"` (внутри одинарных кавычек Bash ничего не подставляет); апостроф внутри — `'''`. Не PowerShell: в нём обратная кавычка — символ экранирования, Windows PowerShell 5.1 теряет `"`; на коммитах из PowerShell haiku терял обратные кавычки в начале BODY (шаги 22.2 и 23.1, исправлено на шаге 23.2). `MSYS_NO_PATHCONV=1` — Git Bash переписывает аргументы, начинающиеся с `/` (BODY `/local/templates/x …` → `C:/Program Files/Git/local/…`). Перед запуском — сверка собранной команды с MESSAGE, BODY, COAUTHOR посимвольно. Каждый путь — отдельный аргумент в своих кавычках (пути не склеивать в одну строку). Ошибка — стоп и отчёт; второй попытки другим способом нет.
6. Отчёт: `git -c core.quotepath=false show --stat --format="%h %s%n%n%b" HEAD` (для большого коммита — последняя строка статистики), `git -c core.quotepath=false status --short`; прямо написать, если в коммит попало что-то кроме FILES, заголовок отличается от MESSAGE или подпись отличается от COAUTHOR.

Запрещено: `push`, `pull`, `fetch`; `reset`, `restore`, `checkout`, `switch`, `stash`, `clean`; `rebase`, `merge`, `cherry-pick`, `revert`, `commit --amend`; `gc`, `prune`, `filter-branch`, изменение `git config`; `git add .`, `git add -A` без путей, `git add -f`, `--no-verify`; создание, правка и удаление файлов. Если что-то пошло не так — ничего не исправлять самому, вернуть команды и их вывод.

Особенности, общие для проектов пользователя: `core.autocrlf=input` (предупреждения про CRLF — норма), на прод выкладывают не из git (git нужен, чтобы по шагам видеть изменения), первый коммит — копия прода.

## 7. Скиллы

### 7.1 `/kit:step-done` — закрытие проверенного шага

Claude вызывает сам после проверки шага; пользователь может вызвать руками. Аргумент (необязательно) — ID шага.

1. Проверить, что это kit-проект с журналом; запомнить `HEAD` (`git rev-parse HEAD`).
2. Собрать блоки для docs-keeper из разговора: STEP, STATUS, SUMMARY, NEXT и необязательные. FILES — из `git -c core.quotepath=false status --porcelain=v1`; если неочевидно, какие изменения относятся к шагу, — спросить через AskUserQuestion. Шаг со снимками `/kit:visual` — в NOTES: метки, какое сравнение и итог (совпадает / в пределах шума / что отличается, статусы и ошибки), путь к `report.html`; снимки в FILES не входят (`<папка документов>/visual/` — только локально), изменённый `.claude/scripts/visual/pages.json` — входит. Шаг создал документ в `work/` (план, спек, чек-лист) — строка в DOCS со статусом `в работе, этап N` (документ на все этапы — `постоянный`); документ стал ненужным — статус `устарел — …`. DECISIONS (с 2.8.0, §6.1): решения пользователя — ответы и прямые указания на шаге; решения агента — только те, что трудно откатить или что влияют на следующие шаги, не больше 1–3 за шаг; «почему» и «что отвергли» — из разговора, причину решения пользователя не придумывать, а спросить; отменяет прежнее — «Заменяет №N».
2а. **Закрытие этапа — сверка** (с 2.10.0) — до архива и до docs-keeper. Этап закрывается: передан STAGE, номер этапа в NEXT другой или NEXT пустой / `—` при STEP вида `N.M` (раньше `—` закрывал этап только со STAGE — этапы 21 и 22 так не распознались); ID не вида `N.M` — только по STAGE. Пункты — требования Т-N и критерии спека и задачи плана из документов `work/…` со статусом «в работе, этап N»; документов нет — шаги этапа не `✅`. Таблица `Пункт | Шаги | Итог` (сделано / частично / нет / не просили) — пользователю; расхождения — один вопрос: «В Баги на потом» (BUGS) / «На следующий этап» (в RECONCILE) / «Не делаем — решением» (DECISIONS). Итог — блок RECONCILE docs-keeper'у: `ГГГГ-ММ-ДД | этап N | сверено с: … | пунктов M, сделано K | расхождения: … | на следующий этап: … или —`.
2б. **Закрытие этапа — архив.** Шаг закрывает этап (условие — п. 2а). Тогда прочитать раздел «Документы» журнала; документы `work/…` со статусом `в работе, этап <номер закрываемого этапа>` — кандидаты (`постоянный` — никогда). Нет — ничего не спрашивать. Есть — AskUserQuestion со списком в тексте вопроса: «Все в archive/ (Рекомендую)» / «Оставить в work/»; выбрать часть — через «Другое». Оставленные — строка DOCS со статусом `в работе, этап <номер следующего этапа>` (иначе при закрытии следующего этапа их уже не предложат). Документ не в git — в FILES только новый путь. Выбранное перенести обычным перемещением файлов, без git (PowerShell `Move-Item -LiteralPath <папка документов>/work/<x> -Destination <папка документов>/archive/<x>`; папку `archive/` создать, если её нет; папка-документ, например `work/design/`, переносится целиком; имя в `archive/` занято — спросить пользователя). В DOCS — `archive/<x> (было work/<x>) — … — готово, этап N (дата)`; в FILES — **оба** пути, старый и новый: git-keeper добавит их одной командой `git add -A -- …`, и git увидит переименование — коммит шага остаётся одним.
2в. **Входящие ответы** (с 2.9.0): `decision-inbox.js --list` — ответы пользователя с прошлого закрытия шага; N из строки «записей: N». Процедурные («закрывать?», «начинать?», «отправить?», подтверждения, порядок работы) пропустить; остальное, чего нет в DECISIONS, — в DECISIONS: выбранное — решение, его описание — основа «почему», другие варианты — что отвергли; свой ответ — по смыслу (встречный вопрос — не решение). После успешной проверки коммита (п. 6) — `decision-inbox.js --clear N`: пришедшие во время закрытия шага остаются; проверка не прошла — входящие не трогать.
3. COMMITS: `git log --format="%h %s" -50`, сопоставить префиксы `<ID>:` → передать пары за последние шаги (docs-keeper заполнит только пустые ячейки).
4. Вызвать `kit:docs-keeper`, дождаться отчёта и сверить с файлом: строка шага, номера багов, каждая строка DECISIONS (номер и начало текста), каждая строка DOCS. «Не записано: нет "почему"» — дописать причину и передать только эти строки.
5. Вызвать `kit:git-keeper`: FILES = файлы шага + файлы из отчёта docs-keeper; MESSAGE = `<STEP>: <суть>`; BODY — CHECK дословно; COAUTHOR — строка `Co-Authored-By` из собственных инструкций по подписи коммитов основного агента, дословно.
6. Проверить: от запомненного `HEAD` ровно **один** новый коммит (`git rev-list --count <HEAD>..HEAD` = 1), заголовок (`git log -1 --format=%s`) совпадает с MESSAGE целиком, символ в символ (не только префикс `<STEP>:` — так видны пропавшие `$arResult` и обратные кавычки), подпись совпадает с COAUTHOR дословно, `git -c core.quotepath=false status --porcelain=v1` не содержит файлов шага. Нарушение (0 или 2 коммита, заголовок не совпал, чужая подпись, лишние файлы) — сообщить пользователю, историю не чинить; сам коммит при сбое проверки не делать ни при каких обстоятельствах — ни в обход git-keeper, ни «чтобы доделать».
6а. **Отправка** (с 2.5.0, §14) — только если задан параметр «Удалённый репозиторий» и проверка п. 6 прошла: первая отправка (нет `refs/remotes/<имя>/<ветка>` — ветка там ещё не бывала) — сначала `secret-scan.js --history`: есть находки-секреты или код 2 — не отправлять; находки только «запрещённый путь» (например, `docs/visual/.gitignore`, закоммиченный до переезда) — показать список и спросить «Отправить как есть» / «Не отправлять», с предупреждением про `.settings.php`, `dbconn.php`, `.env`, ключи (найдено финальным ревью 16.8а); затем `git push -u <имя> HEAD`. Отклонено (на удалённом есть коммиты, которых здесь нет) — стоп и вопрос пользователю; нет сети или входа — коммит остаётся локально, причина — одной строкой. `--force`, `pull`, `rebase`, слияния в `/kit:step-done` не выполняются.
7. Ответ пользователю: хеш и заголовок коммита, отправлен ли он (куда или почему нет), «Сейчас» из отчёта docs-keeper. Хеш попадёт в журнал при следующем `/kit:step-done` (п. 3). Записаны решения агента — отдельным списком «Решения агента на этом шаге (можно возразить)» (с 2.8.0).
8. Запасной путь: если тип агента `kit:docs-keeper` / `kit:git-keeper` недоступен — запустить general-purpose с текстом соответствующего файла из `${CLAUDE_PLUGIN_ROOT}/agents/` и моделью из его заголовка.

### 7.2 `/kit:deploy-list [коммит]` — что выложить и что удалить

Обёртка над `scripts/deploy-list.js`:
- база — аргумент или последний непустой «Коммит» в таблице «Залито на прод» плана выкладки; нет таблицы/коммитов — первый коммит репозитория;
- `git diff --name-status --no-renames <база>..HEAD`, пути из «Не выкладывать» отбрасываются; с 2.3.0 всегда — и `.claude` в корне, и папка журнала вне `.claude` (старая `docs/`), как у хука исключений PhpStorm: журнал, планы и перенос в `archive/` не попадают ни в «Залить», ни в «Удалить с сервера» (исправление по финальному ревью, шаг 11.12в);
- вывод: «Залить» (A/M), «Удалить с сервера» (D), предупреждение о незакоммиченных изменениях (`git status --porcelain`);
- значение «Выкладка» начинается с `PhpStorm Always` (без учёта регистра) — печатаются только удаления (заливает PhpStorm; удаление локально сервер не трогает); `вручную; дев — PhpStorm Always` — полный список (на прод вручную).

После выкладки запись в «Залито на прод» / «Удалить с сервера» делается через `/kit:step-done` блоком DEPLOY. Удаления на сервере — пользователь (PhpStorm → Remote Host) или `/kit:server` шаблоном `delete-list.php` (SSH, иначе файл-канал `kit-exec.php`; сухой прогон и согласие).

Третий вызов: адрес дева (при «дев + прод») и (с 2.5.0, §14) удалённый репозиторий — «для работы с другого компьютера: git проекта с журналом отправляется туда после каждого шага»; варианты: найденный remote (`origin` — первым с «(Рекомендую)»; параметр уже задан — он первым), «Создам закрытый репозиторий — адрес в «Другое»», «Не нужен». В тексте вопроса: репозиторий создаёт пользователь, закрытым и **пустым** (без README и лицензии: в непустом уже есть своя ветка — на GitHub `main`, — и `git push -u origin HEAD` не отклоняется, а кладёт `master` рядом, так что `git clone` на другом компьютере приносит не проект; найдено финальным ревью 16.8а); вход в GitHub/GitLab — пользователь при проверке репозитория (п. 4.1а). Параметр уже задан и remote на месте — вопрос не задаётся.

Сразу после вопросов (до плана на согласие), если адрес прода задан, — в любом режиме `node site-probe.js <прод>` (только чтение): версия PHP и путь к `php.exe` в параметр «PHP»; модуля нет в OSPanel или версия скрыта — спросить пользователя (или узнать после SSH-разведки ниже: `ssh-probe.js` печатает версии PHP на сервере).

**Сервер и канал (с 2.4.0).**
1. Сервер — прод. Заданы оба (прод и дев), а пользователь не сказал, где выполнять, — спросить через AskUserQuestion.

3. Согласие — одинаково в обоих каналах: чтение — сразу; любое изменение — AskUserQuestion с точным кодом и явное «да» (одно согласие — одно действие). Окна подтверждения в браузере нет.

**Файл-канал.**
- **Что это.** `kit-exec.php` в корне сайта — диагностический скрипт, в который Claude вшивает код конкретной задачи; каждый запуск — новый файл (перезапись прежнего). Файл не выполняет код из запроса и ничего не сохраняет; из запроса он читает одно — `?run=<номер запуска>`, и только чтобы сверить с номером своей сборки.
- **Устройство файла** (собирает `kit-exec.js`, §9): сначала — своя shutdown-функция (она регистрируется **до** ядра: у настоящего Битрикса `ExceptionHandler` в своей shutdown-функции делает `die()`, и зарегистрированная позже наша не выполнилась бы — фатальная ошибка задачи осталась бы неназванной); подключает ядро Битрикса (пролог; статистика, агенты и почтовые события отключены; `DOCUMENT_ROOT` задаёт веб-сервер; **без** `NOT_CHECK_PERMISSIONS` — права проверяются по-настоящему); если ядро или обработчик событий уже что-то вывели и заголовки ушли (`headers_sent()`), — одна строка `kit: headers already sent - …use SSH` и конец (заголовки `nosniff`/`no-store` выставить нельзя, а вывод задачи мог бы отрисоваться как HTML); затем проверка `$USER->IsAdmin()` — не администратор: ответ 403 и одна строка «kit: только для администратора», больше ничего, код задачи не выполняется; администратор — заголовки `Content-Type: text/plain; charset=utf-8`, `Cache-Control: no-store`, `X-Robots-Tag: noindex`, `X-Content-Type-Options: nosniff`, первой строкой вывода `KIT-RUN <номер этого файла>`; адрес без `?run=<этот номер>` — вторая строка «kit: код не выполнялся — нужен адрес /kit-exec.php?run=<номер>» и конец; иначе — код задачи в блоке `try` (объявления функций и классов в нём условные и выполняются уже после проверки прав, поэтому их пишут до вызова; завершающий `?>` отрезается); исключение (`catch`) и фатальная ошибка PHP (shutdown-функция + `error_get_last`) — текст и номер строки исходного файла кода (строки приставки вычтены); вывод — текстом, на сайте не в UTF-8 — перекодируется в UTF-8.
- **Номер запуска** — короткая случайная метка (`[A-Za-z0-9]{4,32}`, новая на каждый запуск), которую Claude вписывает в файл и в адрес (`?run=`). Она нужна, чтобы файл не выполнил лишнего: старый файл, который ещё не заменили новым, при открытии нового адреса называет свой номер и код не выполняет — так проверка «уехал ли новый файл» не повторит прошлый запуск (открытие страницы = выполнение кода). Claude читает результат, только когда первая строка вывода — номер его запуска. Это не защита от администратора и не секрет, а сверка «тот ли файл».
- **Порядок запуска.**
  1. Код — во временный файл сессии; `php -l` локальной версией из параметра «PHP».
  2. `node kit-exec.js <код.php> --run <N> --out <временный kit-exec.php>` — сборка и `php -l` результата. Без `php -l` файл не собирается (код 4): ошибку компиляции на сервере увидел бы любой посетитель раньше проверки прав.
  3. Один Write готового файла в корень **основной** папки проекта (из git worktree файл на сервер не уедет).
  4. Доставка: при `PhpStorm Always` файл уезжает сам, пока PhpStorm открыт; при ручной выкладке (и на прод при «вручную; дев — PhpStorm Always») пользователь заливает `kit-exec.php` (PhpStorm → Upload to…), Claude просит об этом одной строкой.
  5. Вкладка встроенного браузера Claude (`mcp__Claude_Browser__*`; `tabs_create` открывает её в фоне) → `<адрес>/kit-exec.php?run=<N>` (адрес печатает `kit-exec.js`). Ответ 403 «только для администратора» — на этой странице формы входа нет: вывести свою вкладку вперёд (`tabs_select`), открыть в ней `<сайт>/bitrix/admin/` и попросить пользователя войти администратором там (пароли вводит только он, Claude их не вводит), затем снова открыть адрес файла. 404 или первая строка `KIT-RUN` с другим номером — файл ещё не залит или залит прежний (он код не выполнил): подождать несколько секунд и повторить, затем попросить проверить заливку. `kit: headers already sent …` — код не выполнялся и на этом сайте файл-канал не заработает (часто лишний перевод строки после `?>` в `init.php`): сказать пользователю, выход — включить SSH. Ошибка PHP из пролога или самого файла без строки `KIT-RUN` («Parse error», сбой в `init.php`) — сбой до проверки прав, код не выполнялся: сказать пользователю и сначала найти причину, повторное открытие не поможет. Пустая страница, 500/502/504 или обрыв без `KIT-RUN` и без текста ошибки PHP — причина неясна: строка `KIT-RUN` могла остаться в буфере вывода (`output_buffering=4096`), пока код уже выполнялся и упал или не уложился во время; для чтения можно открыть снова, для изменяющего кода — «результат неизвестен» (адрес не открывать, проверить состояние чтением, спросить пользователя).
  6. Первая строка `KIT-RUN <N>` совпала — код выполнен, остальное — результат (`get_page_text`).
- **Изменения.** Изменяющий код — только после AskUserQuestion с точным кодом и «да»; файл с изменяющим кодом заливают и открывают только после согласия. Открытие страницы = выполнение кода: страницу с изменяющим кодом открывают один раз. Ответ со строкой `KIT-RUN <свой номер>` без «код не выполнялся» — код выполнен: адрес больше не открывают, вывод — результат (изменение проверяют снаружи). Повторно — только когда точно известно, что код не выполнялся: 403 «только для администратора» (после входа администратора), 404 или обычная страница сайта, `KIT-RUN` с другим номером, строка «код не выполнялся». Отсутствие ответа, обрыв, пустая или оборванная страница без итога — результат неизвестен: адрес не открывают снова, состояние проверяют новым запуском только на чтение и спрашивают пользователя. Вкладку изменяющего запуска не перезагружают: пока файл не заменён и не удалён, тот же адрес выполнит код ещё раз (остаточный риск оставлен сознательно — одноразовый файл усложнил бы схему).
- **Конец работы — файл удаляет Claude, а не пользователь** (решение пользователя 2026-09-30, после живой проверки на delta). Последним запуском, как любой изменяющий код (точный код и согласие в чате): задача `echo @unlink(__FILE__) ? 'KIT-DELETED' : 'KIT-DELETE-FAILED', "\n";` (маркеры латиницей: русский текст внутри кода на сайте в windows-1251 перекодировался бы в кракозябры) — собрать, положить в корень, дождаться доставки, открыть страницу (выполнение — одно). `KIT-DELETED` — Claude удаляет локальную копию, открывает `<адрес>/kit-exec.php` (файла быть не должно: 404 или страница сайта, без строки `KIT-RUN`) и пишет в NOTES следующего `/kit:step-done` «kit-exec.php удалён ✅». `KIT-DELETE-FAILED` (у PHP нет прав на файл, залитый по FTP другим пользователем) — этот файл удаляет пользователь (PhpStorm → Remote Host), запись — блоком DEPLOY «Удалить с сервера». Файл лежит на каждом сервере, куда он попал: автозаливка PhpStorm идёт на один сервер (при «вручную; дев — PhpStorm Always» — на дев), даже когда задача выполняется на другом, — тогда файл уезжает и туда; удаление повторяют для каждого такого сервера (с согласием на каждый запуск; сервер с автозаливкой — последним, после удаления локальной копии: иначе файл удаления для другого сервера уедет на него снова), в конце открывают `<адрес>/kit-exec.php` на каждом сервере (файла быть не должно); не вышло — блок DEPLOY «Удалить с сервера» для него. Локальную копию Claude удаляет сразу после запуска: при автозаливке заливается каждое сохранение, а удаление локального файла сервер не трогает (PhpStorm: `remoteFilesAllowedToDisappearOnAutoupload="false"`). Пока файл лежит на сервере, он отдаёт результат только вошедшему администратору.
- **Место файла.** Корень сайта. Не `.claude` (исключена из выкладки), не `upload/` (стандартный `upload/.htaccess` Битрикса отдаёт `.php` как текст), путь `kit-exec.php` — не в «Не выкладывать» (хук исключений PhpStorm исключил бы его из заливки). Строка `/kit-exec.php` — в шаблоне `.gitignore` для Битрикса (файл-канал только для Битрикса) и в базовых запретах «не коммитить» (git-keeper, secret-scan; только корень): файл не попадает в коммиты и в `/kit:deploy-list`. В существующих проектах строку дописывает `/kit:project-init` (п. 4.1, с согласия) или Claude при первом запуске (с согласия).
- **Отличия от SSH:** код работает внутри веб-запроса — `$USER` администратор с его правами, `SITE_ID` — как у страницы в корне сайта; предупреждения и notice не видны; время ограничено `max_execution_time` и таймаутом веб-сервера — крупные удаления и долгие копии только по SSH; файлы и копии `delete-list.php` (`~/kit-backup`) — пользователя веб-сервера. Нужен доступ к сайту по HTTP(S).
- **Кодировка:** вывод перекодируется в UTF-8; русские строки внутри кода на сайте в windows-1251 не перекодируются (как в SSH-канале).

**Сервер и канал (до 2.4.0; справка — причины отказа SSH в п. 2 действуют и дальше).**
1. Сервер — прод. Заданы оба (прод и дев: адрес или `SSH …`), а пользователь не сказал, где выполнять, — спросить через AskUserQuestion.
2. Задан `SSH <сервер>` → канал SSH. Не задан → канал «консоль». Не удалось подключиться (код 3 `remote-php.js` / `ssh-probe.js`; прямой `ssh` вернул 255 без вывода команды) → одной строкой причина из stderr ssh (`Permission denied (publickey)` — ключ не подошёл; `Host key verification failed` без строки `REMOTE HOST IDENTIFICATION HAS CHANGED` — новый сервер, первый вход и `yes` — пользователь; есть `REMOTE HOST IDENTIFICATION HAS CHANGED` — отпечаток сменился (переустановка сервера или подмена): стоп, на консоль сам не переходить, пользователь сверяет отпечаток у хостера и сам удаляет старую запись `ssh-keygen -R <хост>`, Claude — нет; `Connection timed out`; `This account is currently not available` — shell не выдан, на ispmanager — сброшен флажок «Доступ к shell») → канал «консоль». Исключение — изменяющий код: код 3 после начала выполнения значит «результат неизвестен», повтора нет ни в каком канале: проверить состояние только чтением и спросить пользователя (как с повторным «Выполнить» в консоли).
3. Канал «консоль» — только в режиме `bitrix` и при заданном адресе сервера. Иначе — стоп: сообщить, что выполнить негде, и как настроить вход (`project-init/reference/ssh.md`).

**Канал SSH.**
- Все вызовы ssh — с `-o BatchMode=yes -o ConnectTimeout=15` (без пароля и без приёма нового отпечатка: `StrictHostKeyChecking=no`/`accept-new` не использовать — первый вход и `yes` делает пользователь).
- Команды оболочки: `ssh -o BatchMode=yes -o ConnectTimeout=15 <хост> '<команда>'` — команда целиком в одинарных кавычках, пути абсолютные от папки сайта из параметра (`cd` внутри кавычек выполняется на сервере — страж его не блокирует).
- PHP: код в файле — библиотечный скрипт, проектный `.claude/scripts/NN-имя.php` или временный файл в папке сессии → `node "${CLAUDE_PLUGIN_ROOT}/scripts/remote-php.js" [--env дев] <файл>` (§9). `md5-check.js` печатает код в stdout → сохранить во временный файл сессии → `remote-php.js`.
- Git Bash переписывает аргументы, начинающиеся с `/`: флаги с путями сервера (`--host/--root/--php/--url`) — только вне kit-проекта, с `MSYS_NO_PATHCONV=1` перед `node` (путь к файлу тогда `C:/…`, не `/c/…`) или из PowerShell; команду оболочки в кавычках не начинать с `/` (`cd <папка> && …`, `exec /opt/…`).
- Отличия от файл-канала: в CLI нет авторизованного `$USER` (в файл-канале код работает от администратора), проверки прав модулей снимает `NOT_CHECK_PERMISSIONS`; агенты и почтовые события сайта не запускаются; файлы, созданные через SSH, принадлежат пользователю SSH (ispmanager — владелец сайта; BitrixVM — входить под `bitrix`).

**Канал «консоль» до 2.4.0** (Chrome пользователя; справка — в 2.4.0 удаляется из скилла вместе с К15 и К17):
- Инструменты claude-in-chrome загружаются одним ToolSearch (`tabs_context_mcp`, `tabs_create_mcp`, `tabs_close_mcp`, `navigate`, `javascript_tool`, `read_page`, `find`, `computer`).
- Своя вкладка браузера: создать, в конце закрыть. Адрес: параметр «Прод» (или «Дев» — спросить, если есть оба) + `/bitrix/admin/php_command_line.php`. Нужна авторизация — входит пользователь (Claude пароли не вводит).
- В консоли — новая вкладка «+», затем найти `queryN`, которого раньше не было. Чужие вкладки (например «PHP-строка (1)» с кодом пользователя) не открывать и не выполнять; новый `queryN` не появился — код не выполнять: посмотреть страницу ещё раз и сообщить пользователю, существующие вкладки не трогать.
- Редактор: в `BXCodeEditors` учитываются только редакторы, чей `pTA` на странице (`pTA.isConnected`); редакторы с `pTA` вне страницы — остатки прежних вкладок после «+» (`GetValue` у них падает), их не трогать. Редактор с `pTA.id === 'queryN'` (N — номер новой вкладки) должен быть ровно один, иначе не запускать; `editor.SetValue(code)` и `document.getElementById('queryN').value = code`; прочитать обратно (`GetValue` — в `try/catch`, ошибка → `ok: false`) и сравнить с кодом — совпадение обязательно (Битрикс иногда сохраняет последний выполненный код во вкладке). Вставленный текст может не отрисоваться в редакторе — это не ошибка, решает сверка.
- Запуск — кнопка «Выполнить» (`__FPHPSubmit`); результат — последний видимый `<pre>`, поэтому свой код оборачивается в `echo "<pre>"; … echo "</pre>";` (библиотечные скрипты уже так делают). Сниппет запуска сразу помечает все имеющиеся `<pre>` атрибутом `data-kit-old` и возвращается, а кнопку нажимает через `setTimeout(…, 100)`: кнопка открывает окно подтверждения браузера (confirm), пока оно открыто, страница заблокирована — синхронный клик не дал бы сниппету вернуться, любой вызов инструментов Chrome висит до таймаута.
- Сразу после сниппета — AskUserQuestion: «В Chrome открылось окно подтверждения — нажмите ОК, чтобы выполнить код, или Отмена» (код или первые строки и длина: в редакторе он может быть не виден); варианты «Нажал ОК» / «Нажал Отмена». Окно подтверждает только пользователь: Claude не подменяет `window.confirm`/`alert` и не вызывает инструменты Chrome, пока пользователь не ответил; `javascript_tool` не вернулся — клик не повторять, спросить пользователя, что на экране. «Отмена» — код не выполнялся: закрыть вкладку, сообщить; новый запуск — только по новой просьбе пользователя, заново с новой вкладки консоли. Вопрос не заменяет согласие на изменяющий код.
- После «ОК» результат — последний видимый `<pre>` без пометки (сравнение текста до/после не годится: два запуска подряд могут дать одинаковый вывод). Нет такого `<pre>` — подождать 1–3 с и повторить именно чтение, не больше 10 чтений; дальше — стоп, `read_page` и сообщить пользователю. Кнопку «Выполнить» повторно не нажимать ни в каком случае (повторный клик запустит скрипт второй раз).
- Свою вкладку браузера закрывать в любом случае — и при ошибке, и при несовпадении разметки, и при отказе пользователя.

**Правила для обоих каналов.**
- Код PHP: без `<?php` (в SSH-канале `remote-php.js` отрежет его и сам), без `use` — полные имена классов (`\Bitrix\Main\Loader`); перед запуском — `php -l` локальной версией из параметра «PHP» (для `.claude/scripts/*.php` это делает хук).
- Только чтение — сразу: `ls`, `find`, `md5sum`, `du`, `tail`/`grep` по логам, `inventory.php`, `check-files.php`, SELECT.
- Любое изменение (запись, удаление, перенос, `chmod`, правка файла, запросы, меняющие данные, `$dryRun = false`) — только после AskUserQuestion с точной командой или кодом и явного «да»; одно согласие — одно действие:
  - удаление файлов — шаблоном `delete-list.php`, в том числе одиночных файлов в корне сайта (`$base = '/'`, в списке — только имена): сухой прогон (`$dryRun = true`, вывод — что будет удалено и куда лягут копии — показать) → согласие → `$dryRun = false`; `rm` по списку не использовать; маски — самые узкие (`'debug.php'`, `'*.php.back*'`, не `'*.back*'`); «стоп» — не удалено ничего, файл из стоп-листа удаляет пользователь сам; папка копий не определилась или внутри сайта — спросить пользователя и задать `$backupDir` абсолютным путём;
  - правка файла на сервере — сначала копия в `~/kit-backup/<ГГГГММДД-ЧЧММСС>/<путь от корня сайта>` (`mkdir -p` папки копии, затем `cp -p`) — вне папки сайта (копия `.php.back` рядом с оригиналом отдавалась бы веб-сервером как текст и показала бы исходный код); заранее проверить, что `~` не внутри папки сайта (иначе спросить, куда класть копию); в AskUserQuestion — обе команды (копия и правка), копия — после «да», перед правкой; путь копии — в отчёт;
  - после изменения — проверка (md5 через `check-files.php`, ответ сайта, 404 удалённых путей) и запись: удаление → «Удалить с сервера» `✅ ДАТА, скрипт, копии <папка>`; прочее — NOTES следующего `/kit:step-done`.
- Пароли не вводить: SSH — только по ключу (`BatchMode`), в файл-канале в админку входит пользователь.
- Секреты на сервере не выводить: `bitrix/.settings.php`, `.settings_extra.php`, `dbconn.php`, `.env` — не `cat`, нужен ключ — только наличие или маска; PHP на сервере не править `sed -i` (портит `\` неймспейсов).
- Библиотека `skills/server/scripts/` (переехала из `skills/bitrix-console/scripts/`; все проверяются `php -l` через хук):
  - `inventory.php` — инфоблоки (тип, код, активные/все элементы, разделы, URL), свойства, пользовательские поля разделов и HL-блоков, HL-блоки, файлы `b_file` по модулям и типам; только чтение;

  - `check-files.php` — сверка md5; готовый код печатает `node md5-check.js <файлы…>`.
- Проектные скрипты — `.claude/scripts/NN-имя.php` (в git, из выкладки исключены). Итог запуска — в NOTES следующего `/kit:step-done`.

### 7.5 `/kit:visual` — снимки публичной части «до/после» и сравнение

С версии 2.2.0. Перенос прототипа `beta.server/.claude/scripts/visual/` (коммит 0.3 проекта) без потерь плюс то, что показала практика: контрольный прогон, setup при одиночных страницах, статусы и ошибки сети, опасные адреса, защита выкладки. Claude может вызвать сам (например, перед обновлением); аргумент (необязательно): `discover | login | before | after <метка> | compare <до> <после>`. Инструмент — `scripts/visual.js` (§9), команды — из корня проекта.

**Где что лежит.**

| Что | Где |
|---|---|
| Список страниц проекта | `.claude/scripts/visual/pages.json` — в git (шаблон `.gitignore` пропускает `.claude/scripts/`), из выкладки обычно исключён |
| Снимки, сравнения, `links.json` | `<папка документов>/visual/…` (с 2.3.0 — `.claude/docs/visual/`, у непереехавших — `docs/visual/`) — только локально: `visual/.gitignore` (`*`, `!.gitignore`) создаёт сам инструмент, `/.claude/docs/visual/` — в шаблонах `.gitignore`, обе раскладки — в базовых запретах git-keeper и secret-scan; из выкладки её убирает исключение `.claude` (или папки документов), которое дописывает `phpstorm-exclude.js` |
| npm-зависимости | `%LOCALAPPDATA%\kit\visual\deps` — один раз на машину, общие для всех проектов и для разработки из worktree |
| Сессия входа | `%LOCALAPPDATA%\kit\visual\auth\<папка проекта>-<хеш пути>@<хост>.json` — вне проекта, своя на проект и на прод/дев |

**Сценарий.**
1. **Подготовка.** Адрес — параметр «Прод» (`--env дев` — «Дев»; вне kit-проекта — `--url`). `node visual.js deps`: код 5 — AskUserQuestion «поставить зависимости снимков (~15 МБ, `npm install` в `%LOCALAPPDATA%\kit\visual\deps`)?» → после «да» `node visual.js install`. Нет Chrome (код 5 с этой причиной) — сказать пользователю: браузеры Playwright не скачиваются, нужен установленный Chrome.
2. **Страницы — один раз на проект.** pages.json нет → `discover` (гостем; после `login` — с сессией: видны ссылки личного кабинета) → Claude предлагает список: по одной странице на группу похожих ссылок, контексты «гость» и «админ» (если есть вход), для магазина — setup/teardown корзины; опасные адреса не берутся никогда → AskUserQuestion с перечнем → запись `pages.json`. Формат и рецепты (корзина Аспро, выпадающее меню по hover, 404, поиск) — справка `skills/visual/reference/pages.md`.
3. **Вход.** Контекст с `auth` → `node visual.js login` в фоне (Bash с `run_in_background`: окно Chrome ждёт до 15 минут, дольше лимита Bash); сказать пользователю «войдите на сайт в открывшемся окне Chrome»; пароли вводит только пользователь; дождаться завершения. Код 3 — вход не обнаружен: повтор — по просьбе пользователя.
4. **Эталон.** `shoot before` (в фоне: полный прогон — минуты) → `check before` (контрольный прогон `before-check` — заново и с адреса `before` — и замер шума) → пользователю: сколько совпало на 0%, какие страницы шумят и насколько.
5. **После изменения.** `shoot <метка>` — метка по ID шага латиницей (`after-1.1`, `after-10.5a`: кириллица в метке — код 2); целиком или `--only` для страниц, которые шаг затрагивает (setup всё равно выполняется) → `compare before <метка>` → сначала «Статусы и ошибки», затем снимки «отличается»: дифф-картинки и снимки «до/после» этих страниц Claude смотрит сам (Read), прежде чем докладывать → пользователю: что отличается и почему, что в пределах шума, путь к `report.html`.
6. **Закрытие шага** — NOTES для `/kit:step-done` (§7.1).

**Коды → действия.** 0 — дальше; 1 — есть проблемы: `shoot` — страницы, которые не снялись (причина в выводе), `compare` — отличия сверх шума (разобрать); 2 — аргументы или `pages.json` (опасный адрес без `unsafe`, опечатка в ключе, нет адреса сайта, метка снята с другого адреса) — исправить; 3 — нет сессии, истекла или вход не обнаружен → `login`; 4 — защита выкладки: PhpStorm с автозаливкой Always, а папка снимков не исключена ни сама, ни через родителя (`.claude`, папка документов) — запустить `node phpstorm-exclude.js` (§8), при повторном коде 4 — сказать пользователю, какой Excluded Path добавить (справка `project-init/reference/phpstorm.md`); `.idea` Claude сам не правит; 5 — нет зависимостей или Chrome → п. 1.

**Правила.**
- Опасные адреса (§9) — не снимать; `unsafe: true` в `pages.json` — только с согласия пользователя на конкретный адрес.
- Папку снимков не коммитить и не выкладывать; снимки и метки не удалять без согласия пользователя.
- Git Bash переписывает аргументы, начинающиеся с `/` (`discover /catalog/` → `C:/Program Files/Git/catalog/`): инструмент возвращает их как было, но надёжнее передавать без ведущего `/` (`discover catalog/`) или из PowerShell.
- Долгие команды (`login`, полный `shoot`, `check`) — в фоне; вывод дублируется в `<папка снимков>/<метка>/shoot.log`.

### 7.6 `/kit:why <файл | файл:функция | файл:10-30 | тема>` — почему так сделано (с 2.11.0)

Только скилл, без скрипта; только чтение (ничего не правит и не коммитит). Файл, функция, строки → `git log --follow` / `git log -L :имя:путь` / `git log -L от,до:путь` (`--format="%h %ad %s" --date=short`, `-s`) → ID шагов (часть заголовка до первого `: `; без ID — «без шага») → журнал: строка шага, заголовок этапа, «Решения» (новая таблица — по колонке «Шаг», старая — по дате и словам), «Баги на потом», строка «Сверка …», документы этапа из реестра. Тема → сразу «Решения», таблицы этапов, баги, документы, затем `git log -i --grep`. Хеш из журнала не находится (`git cat-file -e`) — опора на журнал, с пометкой; причины нет — «в истории не записана», догадки — со словом «вероятно». Ответ: 2–5 фраз «почему» со ссылками (шаг, коммит, решение №N, документ), «Источники», «Не нашёл»; хронология — по просьбе.

**`phpstorm-exclude.js`** — исключения PhpStorm (Excluded Paths) в `.idea/deployment.xml`. Внешний процесс: защита путей Claude Code (§3) его не касается.
- Запуск: `--hook` (из SessionStart) — только в kit-проекте, иначе тишина; в stdout — JSON `{"systemMessage": "…", "hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "…"}}` с одной и той же строкой: `systemMessage` — пользователю (документация hooks: «To surface a message to the user on any platform, return systemMessage»), `additionalContext` — в контекст Claude (у SessionStart это разные каналы; шаг 11.12г), только если что-то добавлено или есть предупреждение; любая ошибка — тоже `systemMessage` («хук не отработал … проверьте Excluded Paths руками»), exit 0 всегда. Из git worktree Claude Code (`<проект>/.claude/worktrees/<имя>`) — работа с основной папкой проекта: её `.idea` и параметры (исправление по финальному ревью 11.12а). Без `--hook` (руками, из `project-init`) — работает и вне kit-проекта; `--also a,b` — дополнительные пути (ответы project-init до записи параметров); `--check` — только сверка, файл не меняется: код 0 — всё на месте, 1 — чего-то не хватает (по серверам), 2 — `deployment.xml` не разобран; без `--check` — 0 (дописано или не нужно) / 2.
- Файла `.idea/deployment.xml` нет или в нём нет компонента `PublishConfigData` — ничего не делать.
- Обязательные пути: `.idea`, `.git`, `.claude`, папка документов, если она вне `.claude` (у непереехавших — `docs`); с 2.8.0 — служебные папки superpowers `.superpowers`, `.worktrees`, `docs/superpowers` (всегда, в обоих режимах «Документов на сервере»: появляются посреди сессии; `specs` и `.specify` — нет, так может называться папка сайта); плюс из «Не выкладывать» и `--also` — только простые пути: без `*`, `?`, `[`, без `(кроме …)`; ведущие `./` и `/`, конечный `/` снимаются, `\` → `/`; `--also` без значения (следом `--check`) — пусто (маски по-прежнему учитывает `deploy-list`). Путь уже исключён сам или через родителя (`excludedPath local="true"` с путём-предком) — не добавляется; из обязательных внутри одного исключённого родителя — тоже.
- Серверы: каждый блок `<paths name="…">`, где в `<mappings>` есть `<mapping … local="$PROJECT_DIR$" …/>` (корень проекта; сервер, сопоставленный с подпапкой, например `dist`, не трогается). Автозаливка значения не имеет: исключения защищают и ручной «Upload to…».
- Запись — только добавление, остальной текст файла не меняется: строки `<excludedPath local="true" path="$PROJECT_DIR$/<путь>" />` перед `</excludedPaths>` блока сервера с отступом соседних строк; блока нет (или `<excludedPaths />`) — создать после `</mappings>` с отступом `<mappings>`; значения экранируются для XML; перевод строки — как в файле (`\r\n` или `\n`). Атомарно: временный файл рядом → `rename`, временный файл удаляется и при ошибке; запись не удалась (файл только для чтения, занят антивирусом) — код 2 и `[kit] Исключения PhpStorm: не удалось записать .idea/deployment.xml (<код>) — добавьте в Excluded Paths руками: «ftp» — …`; затем перечитать и сверить `readDeployment` — всё добавленное на месте, иначе вернуть исходный текст и предупредить. Файл с байтами не в UTF-8 (U+FFFD после чтения) и сопоставление с корнем вне распознанного блока `<paths name="…">` — «не разобран», а не «серверов нет».
- Вывод: `[kit] Исключения PhpStorm: добавлено «ftp» — .claude, docs. Если PhpStorm открыт и не подхватил — File → Reload All from Disk.` (несколько серверов — через `; `); без `--hook` при полном наборе — `Исключения PhpStorm на месте: ftp.`, при `--check` с нехваткой — `Исключения PhpStorm: не хватает — «ftp» — …`; не разобран (нет закрывающего `</paths>`, `local="$PROJECT_DIR$"` без `<mappings>` и т. п.) — `[kit] Исключения PhpStorm: .idea/deployment.xml не разобран (<причина>) — исключения не проверены, добавьте .idea, .git, .claude в Excluded Paths руками.`, файл не меняется.
- Библиотека `lib/deployment.js`: `readDeployment(xml) → { always, server, excluded, servers: [{ name, root, excluded }], names }` (`excluded` — у сервера по умолчанию, как раньше; из `lib/visual/guard.js` переезжает сюда; `names` — «Exclude items by name», атрибут `exclude` через `;`, с 2.6.0), `isExcluded(list, путь)` (сам или предок), `addExclusions(xml, пути) → { xml, added: { сервер: [пути] } }` (исключение с причиной — при неразобранном файле), `removeExclusions(xml, пути) → { xml, removed: { сервер: [пути] } }` (с 2.6.0: только локальные `excludedPath` ровно с этим путём — не подпапки, регистр не важен — у серверов с корнем проекта; строка, где элемент один, уходит целиком; самопроверка — убранное не читается).
- **«Документы на сервере: да»** (с 2.6.0, этап 18; zeta — документы и на сервере, по FTP): из `.claude` на сервер уезжают только `docs`, `CLAUDE.md` и `.htaccess`. Обязательные пути вместо `.claude` — `.idea`, `.git`, всё, что лежит в `.claude` на диске, кроме этих трёх (`.claude/<имя>`, по алфавиту), заранее `.claude/worktrees`, `.claude/settings.local.json` и (с 2.7.0) `.claude/skills` (появляются посреди сессии, раньше следующего старта) и папка снимков `<папка документов>/visual`; `.claude` из «Не выкладывать» (она там для ручной выкладки) в Excluded Paths не возвращается. Исключение `.claude` целиком хук убирает — единственное удаление, только при этом параметре; убрано — в строке вывода `убрано «ftp» — .claude` и пояснение «На сервер уезжают … — после заливки проверьте снаружи, что /.claude/ закрыта (check-closed)». Если есть сервер с корнем проекта, а `.claude/.htaccess` нет — хук создаёт его из шаблона `project-init/templates/htaccess-deny` (`wx`: существующий не перезаписывается) раньше записи `deployment.xml`; создать не вышло — код 2, `deployment.xml` не меняется. `--check` файл не создаёт: `Исключения PhpStorm: нет .claude/.htaccess; убрать — «ftp» — .claude; не хватает — …` (код 1). Маски «Exclude items by name», под которые попадают `.claude`, `docs`, `CLAUDE.md` или `.htaccess` (`*`, `?`, регистр не важен), — отдельная строка-предупреждение при каждом старте: «Документы на сервер не уедут: … есть *.md, docs — из-за них не уезжают .claude/docs, .claude/CLAUDE.md. Уберите эти имена руками…»; сам список хук не меняет — он общий для всего проекта (`*.md` закрывает все `.md`). Новое в `.claude` исключается на следующем старте; до того его закрывает `.htaccess`. Ручная выкладка (`deploy-list`) `.claude` не включает при любом значении.

**`remote-check.js`** (с 2.5.0, §14) — сверка с удалённым репозиторием при старте сессии. Отдельный скрипт, а не часть `session-start.js`: хуки одного события работают параллельно, сеть не задерживает «Сейчас».
- Молчит: не kit-проект; параметр «Удалённый репозиторий» не задан; не git-репозиторий; `HEAD` отсоединён.
- Remote с таким именем нет — строка «Параметр «Удалённый репозиторий: <имя>», но remote <имя> в git нет — подключить через `/kit:project-init`» (и в контекст, и пользователю; правила отправки нет — отправлять некуда).
- `git fetch --quiet <имя>` не дольше 8 с, без окон и вопросов входа: `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `GIT_SSH_COMMAND=ssh -o BatchMode=yes -o ConnectTimeout=5` (если своей `GIT_SSH_COMMAND` нет). Не вышло — строка «не удалось проверить <имя>: <последняя строка stderr или «вышло время»>», дальше работа идёт.
- Удалённая ветка — `refs/remotes/<имя>/<ветка>` (туда отправляет `git push -u <имя> HEAD`; upstream не используется — он может смотреть в другой remote); нет её — «ветка <ветка> ещё не отправлена в <имя> — отправит `/kit:step-done`». Иначе `git rev-list --left-right --count HEAD...<удалённая>` → здесь `A`, там `B`:
  - `B > 0`, `A = 0` — «на <имя> новых коммитов: B (работали с другого компьютера) — до любой правки: `git pull --ff-only <имя> <ветка>` (не по upstream — К47), затем перечитай раздел «Сейчас» в <журнал>: в контексте он из журнала до pull; мешают незакоммиченные изменения — стоп и вопрос пользователю» (`session-start.js` работает параллельно и кладёт «Сейчас» до pull — найдено финальным ревью 16.8а);
  - `A > 0`, `B = 0` — «не отправлено коммитов: A — отправь: `git push -u <имя> HEAD`»;
  - оба > 0 — «ветка разошлась с <имя>: здесь A, там B — стоп, спроси пользователя; `--force`, `rebase` и слияния — только с его согласия»;
  - оба 0 — «в синхроне с <имя>».
- Всегда, когда remote есть, — правило: «Удалённый репозиторий <имя>: после каждого шага `/kit:step-done` отправляет коммит (`git push -u <имя> HEAD`); `--force`, `rebase` и слияния — только с согласия пользователя».
- Вывод — JSON, как у `phpstorm-exclude.js --hook`: `additionalContext` — строка состояния и правило; `systemMessage` (видно пользователю) — только при новых коммитах там, расхождении, неотправленном и неудачной проверке. Любая внутренняя ошибка — exit 0 без вывода.

**`php-lint.js`** — только `*.php`, только в kit-проекте с параметром «PHP»: абсолютный путь, оканчивающийся на `php.exe` (регистр не важен), файл существует; иначе (относительный путь, другой exe, файла нет) — молчит. Скрипт консоли — файл в `.claude/scripts/` или `skills/server/scripts/` без `<?php`/`<?=` — проверяется через временный файл в `os.tmpdir()` с приставкой `<?php\n` — файл вне папки проекта, на автозаливку не влияет (путь временного файла в сообщении подменяется на исходный, номер строки в сообщении исправляется на −1). Остальные файлы — `php -l <файл>` как есть: включаемые области Битрикса бывают чистым HTML в `.php`, приставка дала бы ложную ошибку. Ошибка синтаксиса → stderr `php -l (PHP X.Y) нашёл ошибку в <файл>: <сообщение>` и exit 2.

**`decision-inbox.js --hook`** (с 2.9.0) — PostToolUse на `AskUserQuestion`, только в kit-проекте: по строке JSON на отвеченный вопрос в `.claude/kit-inbox.jsonl` — `ts`, `session`, `question`, `header`, `multiSelect`, `options` (подписи с описаниями), `answer` (подпись; мультивыбор — подписи через «, »; текст из «Другое» — как есть), `own` (ответ не совпал с подписями — свой текст). Ответы — из `tool_response.answers` (запасной путь — `tool_input.answers`); вопрос без ответа не пишется. Без вывода, всегда код 0. Отсев процедурных вопросов — не здесь, а в `/kit:step-done` (§7.1, п. 2в). Файл локальный: в базовых запретах secret-scan, в ранних исключениях выкладки (`phpstorm-exclude.js`, «Документы на сервере: да»), в шаблонах `.gitignore` — через `/.claude/*`.

**`guard-bash.js`** — только в kit-проекте. Разбор команды: heredoc и here-string вырезаются; комментарии вырезаются (Bash — `#` в начале слова вне кавычек, в том числе сразу после закрывающей `)`; PowerShell — `#…` в начале слова и сразу после закрывающей кавычки, а также блочные `<# … #>`); содержимое кавычек не учитывается; команда делится по `&&`, `||`, `;`, `|`, `&`, переводу строки:
- Bash: `cd`/`pushd`/`popd` первым словом команды **вне** `( … )` и `$( … )` → deny: «cd меняет рабочий каталог всей сессии: абсолютные пути или ( cd … )»;
- PowerShell: `cd`/`chdir`/`sl`/`Set-Location` первым словом команды в любом месте (скобки в PowerShell не изолируют каталог) → deny;
- команда, первое или любое слово которой `sed`, с флагом `-i`/`--in-place` и целью `.php` → deny: «sed портит обратные слеши в PHP — правь через Edit». Цель `.php` засчитывается, если она вне кавычек, либо если закавыченный аргумент целиком оканчивается на `.php` (иначе `.php` внутри самого sed-скрипта в кавычках ловило бы редактирование другого файла).
Deny — JSON `hookSpecificOutput` (`permissionDecision: "deny"`, `permissionDecisionReason`), exit 0.
Команды на сервере (`ssh <хост> 'cd /путь && …'`) не блокируются: `cd` внутри кавычек выполняется на сервере и каталог сессии не меняет (закреплено тестом).

**`lib/ssh.js`** — общее для `remote-php.js` и `ssh-probe.js`:
- `serverSsh(params, env)` → `{ host, root }` из «SSH прод» / «SSH дев» (деление по первому `:`; нет значения, нет `:`, папка не абсолютная → `null`; папка с `'`, `"`, `` ` ``, `$`, `\` или управляющими символами → тоже `null` — защита в глубину: папку подставляют в `ssh <хост> '… <папка> …'`); хост — только `^[A-Za-z0-9_][A-Za-z0-9_.@-]*$` (`validHost`): без `-` в начале, иначе значение из параметров проекта стало бы опцией ssh (`-oProxyCommand=…` запускает локальную команду); то же проверяют флаг `--host` у `remote-php.js` и хост у `ssh-probe.js` (код 4);
- `runSsh(host, remoteCmd, stdin)` → `{ connected, exitCode, stdout, stderr }`: `spawn(KIT_SSH || 'ssh', ['-o', 'BatchMode=yes', '-o', 'ConnectTimeout=15', '-o', 'ServerAliveInterval=15', '-o', 'ServerAliveCountMax=4', host, remoteCmd + '; printf "\\n__KIT_EXIT=%s\\n" "$?"'])` без оболочки; `KIT_SSH`, оканчивающийся на `.js`, запускается через `process.execPath` (заглушка тестов); метка `__KIT_EXIT=N` в конце stdout — команда на сервере завершилась с кодом N (метка и добавленный перед ней перевод строки из вывода убираются); метки нет — `connected: false` (не пустил или соединение оборвалось; ssh возвращает 255 и тогда, когда 255 вернул сам PHP после фатальной ошибки — поэтому только метка отличает одно от другого). Удалённая оболочка — POSIX (`sh`/`bash`), так на ispmanager и BitrixVM.
- Кавычки: аргументы удалённой команды — в одинарных кавычках, `'` внутри → `'\''`.
- Общий таймаут (с 2.4.0, К13): `runSsh(host, cmd, stdin, { timeoutMs })` — по таймеру `child.kill()`, результат `{ connected: false, timedOut: true }` (код 3 у `remote-php.js`); на сервере PHP запускается под `timeout -k 5 <сек>`, если команда `timeout` есть (`command -v timeout`), — код 124 значит «время вышло на сервере», а 137 — SIGKILL: PHP не отпустил SIGTERM и через 5 с (`-k`) получил его вместе с самим `timeout`, либо его убила нехватка памяти или лимит хостинга (сообщение называет обе причины; оба кода — тоже код 3: результат изменения неизвестен). `--timeout` у `remote-php.js`, по умолчанию 90 с (вместе с запасом ssh 10 с — 100 с, меньше таймаута инструмента Bash 120 с, отсчёт которого начался раньше); долгий скрипт — большее значение и запуск в фоне.

**`lib/kitexec.js`** (с 2.4.0) — `buildKitExec(code, { run }) → { php, prefixLines, shift }`: тело `kit-exec.php` (§7.4) — приставка (своя shutdown-функция, ядро Битрикса, `headers_sent()`, проверка `IsAdmin`, заголовки, `KIT-RUN <run>`, обработчик исключений), затем код задачи в блоке `try` и хвост с обработчиком ошибок; `prefixLines` — число строк приставки, `shift` — на сколько номер строки в файле больше номера в файле с кодом (`prefixLines` минус строка съеденного `<?php`); по `shift` в сообщениях об ошибках номера строк пересчитываются в строки исходного файла кода; ведущий `<?php`, BOM и завершающий `?>` кода отрезаются (у `remote-php.js` — ведущий `<?php` и BOM); «без `use`» — правило скилла для обоих каналов (полные имена классов; в блоке `try` `use` недопустим); `run` — только `[A-Za-z0-9]{4,32}`.

**`lib/msys.js`** (с 2.4.0, К16): `isMsysRewritten(p)` — путь, переписанный Git Bash (`C:/…/Git/…`) или MSYS2 (`C:/msys64/…`, `…/msys32/…`); общая функция для `remote-php.js` (код 4 с подсказкой) и `visual/args.js` (`fixMsysPath` — возвращает как было).

**Общий режим по SSH (с 2.4.0, К20):** приставка `--plain` при заданной папке сайта — `<?php` и `$_SERVER['DOCUMENT_ROOT'] = '<папка сайта>';` (без `chdir`: относительные пути кода — как раньше); `check-files.php` и `delete-list.php` при пустом `DOCUMENT_ROOT` — «DOCUMENT_ROOT не задан — стоп» (запуск `--plain --host` без `--root` вне проекта).

Хотя бы один ключ-действие обязателен.
- `hide` (CSS `display:none!important`) и `mask` (закраска Playwright `mask`) — на уровне файла, контекста и страницы, складываются.

**Опасные адреса** (`links.js`; путь с query, без учёта регистра): `logout` — выход, сессия пропадёт; `/cancel/`, `[?&]cancel=y` — отмена заказа; `copy_order=` — повтор заказа; `[?&]action=` — действие через GET (корзина, сравнение, удаление); `[?&](del|delete|remove)(_[a-z0-9]+)?=`, `/(delete|remove)/` — удаление (`?delivery=` — не удаление: после `del` нужен `=` или `_`); `sessid=` — ссылка с токеном Битрикса, значит что-то меняет; `unsubscribe` — отписка; `clear_cache` — сброс кеша; `^/bitrix/` — служебное; плюс регулярные выражения из `danger`. `discover` помечает причину; `shoot`/`check` с опасным `url` страницы или `goto` без `unsafe: true` — код 2 до запуска браузера. Файлы (`.pdf`, `.doc(x)`, `.xls(x)`, `.ppt(x)`, `.zip`, `.rar`, `.7z`, картинки, видео, `.mp3`, `.csv`, `.xml`, `.txt`) — пометка «файл», в группы страниц не входят.

**Ссылки `discover`:** только свой сайт (тот же хост и схема http/https), без `#…`, без `utm_*`, `yclid`, `gclid`, `fbclid`; query остаётся (`?q=`, `?PAGEN_1=2`), но значение `sessid` заменяется на `***` (токен сессии администратора не пишется в вывод и `links.json`; опасность по `sessid=` остаётся); без повторов. Шаблон группы: сегменты пути из цифр → `{n}`, у query — только имена (`/catalog/?q` , `/news/?PAGEN_1`). `links.json`: `{ base, date, ctx, seeds: [{ url, status, final, title, uid }], links: [{ url, pattern, from: [затравки], danger?: причина, file?: true }] }`.

**Съёмка (`browser.js`)** — как в прототипе:
- `chromium.launch({ channel: 'chrome', headless })` — системный Chrome; контекст: `desktop` — 1920×1080, `deviceScaleFactor` 1; `mobile` — `devices['iPhone 13']` с `deviceScaleFactor` 1; `ignoreHTTPSErrors`, `locale` `ru-RU`, `timezoneId` `Europe/Moscow`; сессия — `storageState` из файла сессии.
- Стабилизация (перед снимком): CSS `animation-duration/delay: 0s`, `transition: none`, `caret-color: transparent`, `scroll-behavior: auto`; скрыты `#bx-panel`, `#bx-panel-back`, `#bx-admin-prefix`, `.bx-core-waitwindow`, `.style-switcher`, `#jivo-iframe-container`, `jdiv` и `hide`; заморозка: видео — пауза и первый кадр, `autoplay` снят; Swiper — `autoplay.stop()`, в режиме `loop` — `slideToLoop(0, 0, false)` (обычный `slideTo(0)` в loop попадает на клон), иначе `slideTo(0, 0, false)`; owl — `stop.owl.autoplay`; flexslider — `pause()` и `flexAnimate(0)`; прокрутка до низа шагом 700 px через 120 мс (до 40000 px) и наверх — для lazy-load; `networkidle` (до 15 с); `document.fonts.ready`; заморозка ещё раз; пауза 700 мс. После `actions` — 500 мс.
- Страница: `goto` (`domcontentloaded`, 60 с) → статус → `load` (до 30 с) → стабилизация → `actions` → финальный адрес, title, USER_ID (`login.check`) → снимок (`fullPage`, `mask`, таймаут 90 с) → `innerText`.
- **setup/teardown** выполняются для каждой пары «контекст × ширина», где снимается хоть одна страница, — и с `--only` (без setup в шапке менялся счётчик корзины: ложное отличие 3→0); `--no-setup` — пропустить явно. Ошибка setup — в вывод и в `meta.json`, съёмка продолжается; teardown — в `finally`.
- **Проверка сессии:** в контексте с `auth` до setup — `goto <адрес>/` и `login.check`; пусто или `0` — контекст не снимается (страницы — `fail: "нет входа"`), в конце — код 3 с подсказкой `login`.
- **Сбой группы** вне цикла страниц (не открылась `/` при проверке входа, не создался контекст браузера — например, испорчен файл сессии): её ещё не снятые страницы получают `fail: "группа <контекст>/<ширина>: <причина>"`, их прежние снимки в метке удаляются, съёмка остальных групп продолжается; `meta.json` пишется всегда, код 1 (найдено ревью задачи 10.8).
- **Сеть и ошибки по странице** (сбрасываются перед каждой страницей): `errors` — `pageerror` и `console.error`; `bad` — ответы со статусом ≥ 400 `{ status, url, type }`; `failed` — несостоявшиеся запросы `{ url, error, type }`; адреса своего сайта — от корня (`/order/ajax.php?…`), чужие — целиком.
- `meta.json`: `{ base, env (прод | дев; null — адрес из --url), date, full, runs: [{ date, filters }], setup: { "ctx/vp": ошибка }, pages: [{ ctx, vp, name, url, status, final, title, uid, errors, bad, failed, fail? }] }`; `full` — прогон без фильтров (у новой метки с фильтрами — `false`; дописывание в полную метку `full` не снимает).
- Вывод: `ok  admin/desktop/order  500 /order/  js-ошибок: 2  ответов ≥400: 1` / `ERR …  причина`; в конце — итог и отдельный список страниц со статусом ≥ 500. Всё дублируется в `visual/<метка>/shoot.log`.

**Сравнение (`image.js`, `diff.js`):**
- Пиксели — как в прототипе: картинки разного размера добиваются белым до общего, `pixelmatch` с `threshold: 0.1`, `includeAA: false`; доля — `100 × отличающиеся / (ш × в)`, три знака; размер `a×b → c×d`.
- Текст — как в прототипе: строки `innerText` без пробелов по краям, пустые отброшены; «пропало» и «появилось» — с учётом числа повторов строки.
- meta по странице (ключ `ctx/vp/name`): статус, финальный адрес, USER_ID; JS-ошибки — новые и исчезнувшие (по тексту); ответы ≥ 400 и несостоявшиеся запросы — новые и исчезнувшие по ключу «код/ошибка + адрес без query» (`?v=…` после обновления не даёт отличий); ошибка setup в «после», которой не было в «до». У меток прототипа нет `bad`/`failed` — сеть сравнивается, только когда она записана в обеих.
- Шум — из `<до>/noise.json`: строки текста, JS-ошибки и ответы, разошедшиеся в контрольном прогоне, помечаются «шум» и в вердикт не идут. Строки сравниваются с точностью до чисел (цифры → `#`): таймер или «Найдено 12» в контрольном прогоне и «Найдено 13» потом — один и тот же шум (проверено на тестовом сайте 2026-09-25: без этого таймер давал отличие в каждом сравнении). Смена статуса, адреса или USER_ID между двумя одинаковыми прогонами — не шум: `check` печатает её строкой «внимание … — это не шум, разобрать».
- Вердикт снимка: **совпадает** — 0 %, в тексте и meta отличий нет (кроме шума); **в пределах шума** — снимок есть в `noise.json`, доля ≤ 2 × шум + 0,1 и в тексте только шум, meta без отличий; **отличается** — всё остальное (любое отличие meta — всегда «отличается»). Нет `noise.json` — вердикта «шум» нет, в отчёте — подсказка `check`.
- Полнота: снимок только в «до» — «после» полный → **не снято** (проблема, как «отличается»), частичный → «не снимали» (сведения); только в «после» — «новый».
- Консоль: «Статусы и ошибки» (построчно), «Отличается» по убыванию доли, «Не снято», итог «совпадает N, в пределах шума N, отличается N, не снято N (из N)», путь к отчёту.

## 13. Вне охвата

- Настройки PhpStorm Claude не меняет (`.idea` только читается). - Хук-запрет записи `.scss`/`.min.*`/`.map` — отклонён пользователем.
- Заливка файлов на сервер — делает пользователь (PhpStorm); заливка через SSH (scp с копией и сверкой md5) — отдельной задачей позже (решение 2026-09-24). Удаление файлов на сервере — пользователь (Remote Host) или `/kit:server` с согласия.
- Снимки (`/kit:visual`): обход сайта вглубь (только ссылки со страниц-затравок), снимки по расписанию и в CI, сравнение разных ширин между собой, выкладка отчётов куда-либо; браузеры Playwright не скачиваются — только системный Chrome.

Без SSH выполнить PHP на таком сервере негде — выход один: включить SSH у хостинга (`reference/ssh.md`, решение 2026-09-30).
- Удалённый репозиторий (§14): создание репозитория за пользователя, работа с двух компьютеров одновременно (слияния), разные параметры для разных машин (параметр «PHP» — путь на конкретной машине, лежит в git), автоматическая отправка у самого claude-kit (его правило — push только после выпуска и с согласия).
- Консоль Битрикса через Claude in Chrome (канал до 2.4.0) — удалена; вместо неё — файл-канал `kit-exec.php` (§7.4). Окно подтверждения браузера, HTTP-запросы к Командной PHP-строке и сохранённые сессии администратора для работы на сервере не используются (решение 2026-09-30).

## 14. Удалённый репозиторий и работа с другого компьютера (с 2.5.0, этап 16)

**Зачем.** Всё состояние kit-проекта — журнал, решения, план выкладки, правила, история шагов — лежит в `.claude/docs` и git одной машины; `.claude` на сервер не выкладывается намеренно. Заболел или работаешь из дома — продолжить не с чего. Закрытый удалённый репозиторий, куда уходит каждый шаг, делает продолжение одним `git clone`.

**Схема.**
1. Пользователь создаёт закрытый пустой репозиторий (GitHub, GitLab, корпоративный сервер — где разрешает работодатель).
2. `/kit:project-init` (новый проект или повторный запуск в существующем — задаётся один вопрос) привязывает его: `git remote add origin <адрес>`, параметр «Удалённый репозиторий: origin» (§7.3, п. 4.1а).
3. `/kit:step-done` после проверенного коммита отправляет его: первый раз — после `secret-scan.js --history`, всегда — `git push -u <имя> HEAD` (§7.1, п. 6а). Git-keeper не пушит (§6.2).
4. Хук SessionStart `remote-check.js` при каждом старте сверяет ветку с удалённой и говорит Claude, что делать: `git pull --ff-only`, отправить неотправленное, остановиться при расхождении (§8).

**Что уходит в репозиторий** — то же, что в git проекта: код, `.claude/CLAUDE.md`, `.claude/docs` (кроме `visual/`), `.claude/scripts` (в том числе `visual/pages.json`). Не уходит: `.idea`, снимки, `bitrix/`, `upload/` (кроме `upload/docs/`), секреты — их не пускают `.gitignore`, git-keeper и `secret-scan.js`; ядро и загрузки при необходимости скачиваются с сервера.

**Безопасность.** Адрес `http(s)://` с логином, паролем или токеном внутри не принимается: он попал бы в `.git/config` открытым текстом; вход — пользователь, через Git Credential Manager при первой отправке (или SSH-ключ для `git@…`). Проверка всей истории перед первой отправкой ловит секреты и запрещённые пути из коммитов, сделанных до kit (например, `bitrix/.settings.php`); нашлось — не отправлять: убрать секрет из истории или начать новый репозиторий с текущего состояния — решает пользователь, kit историю не переписывает. `--force` не используется никогда без его согласия.

**Работа с другого компьютера** (раздел README):
1. Claude Code, Node ≥ 18, плагин (`claude plugin marketplace add …`, `claude plugin install kit@claude-kit`).
2. `git clone <адрес>` в папку проекта (для сайтов — туда же, где он лежит на работе, например `C:\OSPanel\home\<сайт>`: параметр «PHP» — путь на машине, и он в git; OSPanel в другой папке — `php -l` молча пропускается, `kit-exec.php` не собирается). Remote в параметре не `origin` — `git clone -o <имя> <адрес>`, иначе хук скажет, что такого remote нет (К50).
3. PhpStorm: открыть папку, настроить сервер выкладки (`.idea` не в git); исключения `.idea`, `.git`, `.claude` допишет хук при первом старте сессии.
4. SSH к серверу — свой ключ этой машины (справка `reference/ssh.md`); без SSH на Битриксе — файл-канал.
5. Снимки `/kit:visual` — зависимости ставятся заново; эталоны `before` остались на первой машине — снять заново.
6. Работать с одного компьютера за раз: хук при старте сверит ветку с удалённой, а Claude по его строке до любой правки подтянет чужие коммиты (`git pull --ff-only <имя> <ветка>`, К49); `/kit:step-done` отправит свои.
