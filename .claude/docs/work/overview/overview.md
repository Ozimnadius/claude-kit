# Как устроен kit

<!-- Файл собирается командой node .claude/docs/work/overview/build/build.js — правьте build.js и diagrams.js, а не этот файл. -->

Плагин Claude Code, который ведёт проект по шагам: журнал с решениями и проверками, один коммит на проверенный шаг, выкладка, работа на сервере, снимки «до/после» и отчёт заказчику. Внутри — общий каркас для любых проектов и модуль для сайтов на 1С-Битрикс.

**5** команд `/kit:` · **4** хука · **20** node-скриптов · **3** PHP-скрипта для сервера

**Цвета на схемах:** оранжевый — хук, срабатывает сам; синий — команда `/kit:`; красный — пользователь, согласие или стоп; жирная рамка — Claude и ключевые узлы; пунктир — внешнее: git, сервер, сайт, PhpStorm.

> **Главное условие.** Плагин включается только в kit-проекте — там, где в `.claude/CLAUDE.md` есть раздел «Параметры для агентов» или лежит журнал `.claude/docs/progress.md`. В остальных папках хуки молчат. Проект старого формата (журнал в `docs/` или одним файлом, старые значения параметров) хук находит при старте и предлагает `/kit:project-init` — переезд на формат kit 3.0. Ошибка внутри хука сессию не ломает: любой сбой — тихий выход с кодом 0.

Та же страница с навигацией — [overview.html](overview.html): скачать и открыть в браузере.

## Карта

Команды Claude вызывает сам, когда подходит ситуация, или по вашей команде `/kit:…`. Хуки не вызывает никто: Claude Code запускает их на событиях сессии. Вся тяжёлая логика — в node-скриптах, чтобы поведение было одинаковым и проверялось тестами, а не зависело от того, как модель поймёт текст скилла.

![Карта плагина kit: пользователь даёт команды Claude, хуки перехватывают события сессии, Claude вызывает шесть команд /kit:, каждая работает через свои скрипты и меняет git, журнал, сервер или сайт либо только читает историю.](img/01-karta.svg)

*Каждая команда — своя колонка: какие скрипты она запускает и что в итоге меняется. Параметры проекта читает не только Claude: хуки и скрипты берут их сами (таблица «Параметры» ниже).*

## Цикл работы

![Цикл работы: после /kit:project-init идёт петля шаг — проверка — /kit:step-done — следующий шаг; хук php -l срабатывает при записи кода; /kit:visual снимает до и после, /kit:server проверяет на сервере и удаляет файлы; выкладка вручную или автозаливкой возвращается в журнал блоком DEPLOY, а при «Claude по SSH» шаг заливает сам /kit:step-done.](img/02-cikl.svg)

*Петля в центре — обычный рабочий день: шаг, проверка, закрытие шага, следующий. Справа — команды, которые подключаются по ситуации. Выкладка вручную возвращается в журнал: что залито, пишется через /kit:step-done блоком DEPLOY; при автозаливке PhpStorm строк «Залито» нет, при «Claude по SSH» заливает сам /kit:step-done.*

- **Один шаг за раз.** Следующий начинается только после проверки предыдущего. ID шага — `N.M`, исправления после ревью — `N.Mа`, `N.Mб` отдельными коммитами, без amend.
- **Автозаливка.** При «Выкладка: PhpStorm Always» любое сохранение сразу уезжает на сервер. Поэтому черновики живут во временной папке сессии, PHP проверяется там же, а в проект попадает одной правкой. Удаление локального файла сервер не трогает — такие файлы записываются в «Удалить с сервера».

- **Проверка на сервере.** Код пишет Claude. Если у окружения задан адрес сервера, после записи он сам проверяет результат — страницу на десктопной и мобильной ширине одним пакетным вызовом браузера (с 3.0.0: по замерам браузер — четверть всех ходов модели).
- **Worktree.** Сессия в `.claude/worktrees/…` при автозаливке: правки не попадут на сервер, пока их не сольют, так что сразу проверять на сервере бессмысленно.
- **Git — не ваша забота.** Команды git пользователю не выдаются, коммит делает только скрипт `kit-commit.js` из `/kit:step-done`.

## Хуки

Это часть плагина, которая работает без участия Claude. Все хуки сначала проверяют, kit-проект ли это, и только потом что-то делают.

![Хуки: каждое событие сначала проверяет, kit-проект ли это; если нет — тишина. SessionStart дописывает исключения PhpStorm, кладёт в контекст раздел «Сейчас» и правила и сверяет ветку с удалённым репозиторием; PreToolUse запрещает cd вне подоболочки и sed -i по PHP, а в проекте Мэтта (с 3.3.0) ещё коммит в обход /kit:step-done, ветки и worktree, при автозаливке — перезапись рабочей копии старыми версиями (guard-bash.js), файлы Мэтта в корне проекта и уход в worktree (guard-matt.js); PostToolUse после правки прогоняет php -l и при ошибке возвращает код 2, а после вопроса пользователю записывает ответ во входящие для /kit:step-done.](img/03-huki.svg)

*SessionStart готовит сессию, PreToolUse может отказать команде оболочки ещё до запуска, PostToolUse проверяет только что записанный PHP и записывает ваши ответы на вопросы во входящие. Отказ и ошибка приходят Claude как обычный ответ инструмента — он переписывает команду или чинит код.*

### Что SessionStart кладёт в контекст

Хук срабатывает при старте, `resume`, `/clear`, после сжатия контекста и в ответвлённой сессии (`fork`, с 3.3.0) — поэтому Claude не теряет текущий шаг даже в длинной сессии. Так начинается сессия в этом репозитории (сокращено):

```text
[kit] Проект ведётся по журналу .claude/docs/progress.md.

## Сейчас (из .claude/docs/progress.md)
- Этап: 36 — облегчение kit: закрытие шага скриптами, один формат, без двойного учёта (начат 2026-10-16); последний шаг 36.7 — …
- Следующий шаг: 36.8 — выпуск 3.0.0
- Блокеры и открытые вопросы: …

## Правила процесса (плагин kit)
- Один шаг за раз: следующий — только после проверки предыдущего.
- После проверенного шага — /kit:step-done (kit-step.js → kit-journal.js → kit-commit.js, один коммит на шаг).
- Документы проекта — в .claude/docs/: планы, спеки, чек-листы, материалы — в work/, готовое — в archive/ …
- Superpowers по правилам kit: спеки и планы — в .claude/docs/work/ …
- Журнал по частям: решения — .claude/docs/journal/decisions.md, баги — …/bugs.md, …
…
```

Шесть правил процесса добавляются всегда, остальное — по параметрам проекта:

| Условие | Что добавляется |
| --- | --- |
| всегда | раздел «Сейчас» из журнала (до 4000 знаков) и шесть правил: шаг за разом, вопросы через AskUserQuestion, /kit:step-done, git только через /kit:step-done (kit-commit.js), LF, грабли cd / sed / Git Bash |
| Выкладка: PhpStorm Always | любое сохранение уходит на сервер окружения (прод или дев) — черновики только во временной папке |
| Выкладка: Claude по SSH | правки локально до /kit:step-done; заливка после просмотра, проверка на сервере, коммит; предупреждение, если в PhpStorm включена автозаливка |
| адрес сервера окружения («Прод» или «Дев», с 3.0.0) | после записи — проверка на сервере, десктоп и мобильная ширина, одним пакетным вызовом браузера (`browser_batch`); при «Claude по SSH» — после заливки в /kit:step-done |
| автозаливка + сессия в worktree | правки не уедут на сервер до слияния — не проверять сразу |
| всегда (с 3.0.0) | коммит — после просмотра: панель изменений и ответ «Коммитить» |
| старый формат (с 3.0.0) | журнал не в `.claude/docs`, одним файлом, без «Как проверено», старая таблица решений, «дев+прод» или «вручную; дев — PhpStorm Always» — предложить /kit:project-init: переезд на формат kit 3.0; до переезда kit шаги не закрывает |
| нет «Параметров для агентов» | предложить /kit:project-init |
| всегда | где лежат документы (`work/`, `archive/`, реестр) |
| всегда, кроме проекта Мэтта с плагином (с 2.8.0) | superpowers по правилам kit: спеки и планы — в `work/` по шаблону `spec.md`, в плане — чек-лист задач (с 2.13.0), сам superpowers не коммитит, задача плана = шаг kit |
| журнал по частям (с 2.13.0) | где лежат части: решения, баги, справочник, закрытые этапы — искать и там |
| автозаливка, кроме проекта Мэтта с плагином (с 2.8.0) | superpowers — без отдельных веток и worktree |
| «Система Мэтта: да» и плагин Мэтта на проекте (с 3.3.0) | правил superpowers и строки «автозаливка — без веток» нет; вместо них — правила Мэтта: указатель на `/kit:matt`, навыки «только по команде» — не инструментом Skill, а файлом (`matt-skill.js <имя>`), трекер — локальные файлы по справке `reference/tracker.md`, места файлов, без веток и worktree, шаг закрывает только общая сессия (исполнитель тикета `/kit:step-done` не вызывает), без пользователя — без `git push` и `--push` до разбора, даже если хук велит отправить, TDD — только где есть тесты; если установлена не 1.3.1 (правила kit проверены на ней) и есть папка `<docs>/work/*/issues/` — ещё строка сверить правила с навыком |
| проект Мэтта с плагином и «Выкладка: PhpStorm Always» (с 3.3.0) | без веток и worktree; рабочую копию старыми версиями не переписывать (`bisect`, `stash`, переход на другой коммит или ветку, `reset --hard`, `rebase`) — бисекция в копии через `git clone` во временную папку; при окружении не «дев» ещё — прототип `prototype` только HTML-файлом в `work/<тема>/`, без вариантов на страницах сайта, и без пользователя не работать |
| «Система Мэтта: да», но плагина на проекте нет (с 3.3.0) | правила superpowers остаются, добавляется напоминание Claude и пользователю: запустить `/kit:project-init` (включение плагинов на проект лежит в `.claude/settings.json`, а он не в git) |

Второй скрипт SessionStart, `phpstorm-exclude.js`, дописывает в `.idea/deployment.xml` исключения `.idea`, `.git`, `.claude`, простые пути из «Не выкладывать» и служебные папки superpowers (`.superpowers`, `.worktrees`, `docs/superpowers`, с 2.8.0) — каждому серверу, сопоставленному с корнем проекта. Он только добавляет и ничего не удаляет; из worktree работает с основной папкой проекта. Исключение — параметр «Документы на сервере: да» (с 2.6.0): тогда хук убирает исключение `.claude` целиком и исключает всё в ней поимённо, кроме `docs`, `CLAUDE.md` и `.htaccess` (нет `.htaccess` — создаёт), — документы уезжают на сервер автозаливкой, папка закрыта из веба. В режиме «Claude по SSH» (с 2.18.0) хук держит `.claude` исключённой: документы туда же заливает `/kit:step-done` скриптом `ssh-deploy.js --docs`.

Третий скрипт SessionStart, `remote-check.js` (с 2.5.0), работает, только если задан параметр «Удалённый репозиторий». Он делает `git fetch` не дольше 8 секунд и без окон входа и сравнивает ветку с удалённой: новые коммиты там — Claude до любой правки выполняет `git pull --ff-only`; неотправленные здесь — отправляет; разошлись — останавливается и спрашивает. Нет сети или входа — строка «не удалось проверить», работа идёт дальше.

### Страж команд и php -l

- `guard-bash.js` разбирает команду как оболочка: вырезает heredoc, here-string и комментарии, делит на команды по `;`, `&&`, `|`. `cd` в Bash разрешён только внутри подоболочки `( cd … && … )`; в PowerShell `cd` и `Set-Location` запрещены везде — скобки там не помогают. Например, при подготовке этого обзора страж остановил команду Claude с `cd`, и её пришлось переписать через подоболочку. В проекте Мэтта (с 3.3.0) отказывает ещё в трёх случаях. Коммит в обход `/kit:step-done` — `git commit`, `merge` локальной ветки, `revert`, `cherry-pick`, `am` (коммит делает только `kit-commit.js` — исполнитель не коммитит, тикет принимает общая сессия); слияние удалённой ветки (`origin/…`, `@{u}`, `FETCH_HEAD`) по потоку kit «ветка разошлась — с согласия» проходит, как и его завершение после конфликта, пока есть `MERGE_HEAD`. Создание веток и worktree (`checkout -b`, `switch -c`, `branch <имя>`, `stash branch`, `worktree add`) — при любой выкладке: шаг коммитится в текущую ветку основной папки. При «Выкладка: PhpStorm Always» — ещё перезапись рабочей копии старыми версиями: `bisect`, `stash`, `checkout` и `switch` на другой коммит или ветку, `reset --hard`, `restore --source`, `rebase`, `pull --rebase` — файлы с диска уезжают на сервер; `checkout -- <пути>` и `checkout HEAD -- <путь>` проходят.
- `guard-matt.js` (с 3.3.0) — PreToolUse на `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `Agent`, `Task`, `EnterWorktree` и `start_session`, только в проекте с «Система Мэтта: да». Запись в корень проекта (на сайте это корень сайта) файлов навыков Мэтта — `GLOSSARY.md`, `GLOSSARY-MAP.md`, `CONTEXT.md`, `CONTEXT-MAP.md`, `MISSION.md`, `RESOURCES.md`, `to-questionnaire-*.md`, `docs/adr/`, `docs/agents/`, `.scratch/`, `lessons/`, `learning-records/`, `.out-of-scope/` — отказ с подсказкой: глоссарий и ADR — в папке документов, карта, спек и тикеты — в `work/<тема>/`, прочее — в `work/`. Сессия в worktree приложения проверяется по корню и основной папки, и самого worktree. Уход в отдельный worktree — `EnterWorktree`, субагент с `isolation: worktree`, подчинённая сессия с `use_worktree` — отказ при любой выкладке (исполнители работают в основной папке); облачная копия (`isolation: remote`) — только при «PhpStorm Always»: правки из копии не дойдут до сервера.
- `php-lint.js` берёт `php.exe` из параметра «PHP» — только абсолютный путь к существующему файлу, иначе молчит. Скрипты для сервера (`.claude/scripts/`, библиотека `/kit:server`) пишутся без `<?php`: хук проверяет их через временную копию с этой приставкой и сдвигает номера строк обратно.
- `decision-inbox.js` (с 2.9.0) — PostToolUse на `AskUserQuestion`: каждый ответ пользователя (вопрос, варианты с описаниями, выбор или свой текст) дописывается в локальный `.claude/kit-inbox.jsonl` — не в git и не на сервер. `kit-step.js` выдаёт их готовыми строками решений («почему» — описание выбранного варианта, «что отвергли» — другие), `/kit:step-done` отбрасывает процедурные, `kit-commit.js --inbox` после проверенного коммита убирает разобранное — решения переживают сжатие контекста.

## Закрытие шага `/kit:step-done`

Claude вызывает команду сам, как только результат шага проверен. С 3.0.0 закрытие шага — три скрипта: `kit-step.js` готовит шаг одной командой (файлы шага, ваши ответы на вопросы — готовыми строками решений, режим выкладки), `kit-journal.js` пишет журнал по блокам, `kit-commit.js` делает один коммит, проверяет его, убирает разобранные входящие и отправляет. Раньше журнал вёл агент-модель: по замерам он один занимал больше минуты и 59 тысяч токенов на закрытие, а всё закрытие — медиану 5 минут и 16 ходов модели. Текст скилла — короткое ядро (14 КБ вместо 36 КБ); ветки лежат в справках `reference/ssh.md` (порядок «Claude по SSH»), `stage-close.md` (сверка и архив) и `push.md` (коммит не отправился), и Claude читает их, только когда на них указывает вывод подготовки или код скрипта.

Журнал отвечает и на «как проверено», и на «почему так решили»: SUMMARY — что сделано, CHECK — как проверено (отдельная колонка в таблице этапа и тело коммита); решения пишутся с обоснованием и отвергнутыми вариантами (`№ | Дата | Шаг | Решение | Почему | Что отвергли | Кто`). «Почему» для ваших ответов — описание выбранного варианта, «что отвергли» — другие варианты: отдельно Claude не переспрашивает. Значимые решения агента Claude показывает отдельным списком — можно возразить. `kit-journal.js` работает по принципу «всё или ничего»: неверные блоки — код 4, старый формат или нет нужного раздела — код 2, и ни один файл не тронут; повтор с теми же блоками ничего не удваивает.

Закрытие этапа (новый STAGE, другой номер этапа в NEXT или NEXT «—») начинается со сверки: Claude сравнивает задуманное — требования спека и задачи плана этапа из `work/`, а без них шаги этапа — со сделанным и показывает таблицу «пункт → шаги → итог». Расхождения — одним вопросом: в «Баги на потом», на следующий этап или «не делаем» с причиной в «Решениях»; итог — строка «Сверка …» под таблицей этапа. Раздел этапа переезжает в `journal/stages/` после ответа «Коммитить», прямо перед коммитом: до этого шаг ещё можно поправить по комментариям. Коммит — одна команда Bash: сообщение уходит скрипту через heredoc `<<'KIT_MSG'` и попадает в git как есть, без перепечатки и подстановок.

![Последовательность /kit:step-done с 3.0.0: Claude запускает kit-step.js — тот отдаёт файлы шага, входящие ответы готовыми строками решений и режим; при закрытии этапа Claude сверяет задуманное со сделанным; блоки шага уходят в kit-journal.js, который пишет журнал, его части и чек-лист плана по принципу «всё или ничего» и возвращает «Сейчас» и изменённые файлы; Claude показывает незакоммиченные изменения в панели приложения Claude и ждёт «Коммитить», а при закрытии этапа после этого переносит его в journal/stages/; kit-commit.js проверяет пути, добавляет файлы, проверяет секреты, делает один коммит, сверяет его, убирает разобранные входящие и, если задан удалённый репозиторий, отправляет коммит — в первый раз после проверки всей истории.](img/04-step-done.svg)

*Время идёт сверху вниз. Сплошная стрелка — вызов, пунктир — ответ. kit-step.js и kit-journal.js возвращают Claude готовое: файлы и строки решений, «Сейчас» и список изменённых файлов. secret-scan проверяет дважды: пути до git add (чтобы запрещённый файл даже не попал в индекс) и добавленные строки после; код 1 — стоп без коммита, индекс остаётся как есть. После проверенного коммита kit-commit.js убирает разобранные входящие и, если задан удалённый репозиторий, отправляет коммит; в первый раз — только после проверки всей истории на секреты.*

### Если что-то не так

- **Просмотр перед коммитом** — всегда (с 3.0.0 параметра «Коммит» нет): Claude открывает панель незакоммиченных изменений приложения Claude (в терминале — статистику в чате) и ждёт «Коммитить». Вопрос по строке — клик по ней в панели, комментарий, Ctrl+Enter; правки по комментариям — часть шага. «Не коммитить пока» — шаг ждёт.
- Старый формат проекта — `kit-step.js` и `kit-journal.js` отвечают кодом 2 и сообщением о переезде: сначала `/kit:project-init`.
- Найден секрет или запрещённый путь — стоп до коммита; значения в выводе замаскированы.
- Код скрипта коммита 2 или 3 — Claude сообщает, что показали команды, и останавливается. Никаких `reset`, `amend`, `rebase`, и сам в обход скрипта не коммитит.
- Код 4 — коммит сделан и проверен, но не отправлен: причина одной строкой (нет сети или входа, на удалённом чужие коммиты, секреты в истории), что делать — `reference/push.md`.

### Особенности

- **Отправка** (с 2.5.0; с 3.0.0 — `kit-commit.js --push`) — после проверки коммита, если задан «Удалённый репозиторий»: `git push -u <имя> HEAD` не дольше 90 секунд — меньше предела команды Bash. `--force`, `pull` и `rebase` — никогда без согласия.
- Хешей коммитов в журнале нет (с 3.0.0): коммит шага находится по ID в заголовке (`36.3: …`) — и для заливки по SSH, и для отчёта.
- Подпись `Co-Authored-By` основной агент берёт из своих инструкций и пишет в сообщение дословно — не устаревает при смене модели.
- Сообщение коммита — heredoc с кавычками: Bash ничего не подставляет, `$arResult` и обратные кавычки доходят как есть; скрипт сверяет сообщение коммита с поданным побайтно и проверяет, что путей шага больше нет в `git status`.
- `core.quotepath=false` во всех командах git: иначе кириллические пути приходят escape-последовательностями и `git add` их не находит.
- Конец этапа: документы `work/…` «в работе, этап N» предлагаются в `archive/`. Перенос — обычным `Move-Item`, в коммит идут оба пути, и git видит переименование; галочку последнего шага `kit-journal.js` ставит уже в архивном плане.
- Скрипт коммита не делает `pull`, `reset`, `checkout`, `stash`, `rebase`, `git add .` и второй коммит; `push` — только с `--push` и после проверки коммита.

## Журнал, решения и планы

Журнал отвечает на три вопроса: что делали, как проверили и почему так решили. С 2.13.0 он разложен по частям: в главном файле — только текущее, остальное рядом.

```text
.claude/docs/
  progress.md          «Сейчас», оглавление «Этапы», «Документы», «Прод: не забыть», текущий этап
  journal/
    decisions.md       «Решения»: № · дата · шаг · решение · почему · что отвергли · кто
    bugs.md            «Баги на потом»
    reference.md       «Справочник», «Материалы заказчика», «Отчёт заказчику: …»
    stages/stage-NN.md закрытые этапы: шаги, «Как проверено», строка «Сверка …»
  work/                текущие планы и спеки, archive/ — готовое
```

- **«Сейчас» — снимок, не история.** `kit-journal.js` переписывает пункты целиком: текущий этап и последний шаг, следующий шаг, блокеры — текстом блока BLOCKERS. Хук SessionStart показывает раздел в начале каждой сессии.
- **Решения.** Ваши ответы на вопросы Claude хук складывает во входящие; `kit-step.js` превращает их в строки решений, `/kit:step-done` процедурное («закрывать?») отбрасывает. Значимые решения агента — туда же, со списком «можно возразить».
- **Закрытие этапа.** Сверка «задумано ↔ сделано» с планом или таблицей этапа, расхождения — одним вопросом; затем `journal-split.js --stage N` переносит этап в `journal/stages/` строка в строку.

- **Чек-лист в плане.** В начале плана этапа — строка на задачу `- [ ] N.M — …`; закрывая шаг, `kit-journal.js` ставит `[x]`. Подробные шаги внутри задач — без чекбоксов.
- **Один формат** (с 3.0.0). Журнал по частям, столбец «Как проверено», таблица решений с «Почему». Старый журнал переводит `/kit:project-init` одним запуском (`journal-split.js --migrate` — с проверкой, что ни одна строка не потерялась); закрытые этапы и их хеши остаются как есть.
- **Что из этого читают.** `/kit:report` собирает отчёт заказчику за период: шаги — по ID в заголовках коммитов, их строки — из журнала.

## Работа на сервере `/kit:server`

> **Правило согласия.** Чтение — сразу: `ls`, `md5sum`, логи, SELECT, `inventory.php`. Любое изменение — только после вопроса с точной командой или кодом и явного «да». Одно согласие — одно действие. Пароли вводит только пользователь: SSH — по ключу (`BatchMode=yes` пароль не спросит), в админку сайта он входит сам.

![Выбор канала /kit:server: если для сервера задан параметр SSH — канал SSH с кодами 0, 1, 3; при коде 3 отказ во входе ведёт на файл-канал, смена отпечатка — стоп, обрыв изменяющего кода — результат неизвестен. Без SSH: в режиме bitrix с адресом сайта — файл-канал kit-exec.php, иначе выполнить негде.](img/05-server.svg)

*Канал выбирается по параметрам проекта. Код 3 по SSH разбирается по причине: отказ во входе можно обойти файл-каналом, смену отпечатка сервера — нельзя (это может быть подмена), а обрыв во время изменяющего кода означает, что изменение могло пройти, — повторять его нельзя, только проверить чтением и спросить.*

### Файл-канал kit-exec.php

Нужен для Битрикса без SSH. Это не консоль: код одной задачи вшит в файл при сборке, из запроса файл ничего не выполняет. Номер запуска `?run=` — не секрет, а сверка «тот ли это файл»: старый файл, который ещё не заменили, при открытии нового адреса называет свой номер и ничего не делает. Без проверки `php -l` файл не собирается: ошибку компиляции на сервере увидел бы любой посетитель раньше, чем PHP дошёл бы до проверки прав.

![Файл-канал: код задачи собирается в kit-exec.php с проверкой php -l, кладётся в корень проекта, доезжает на сервер и открывается во встроенном браузере Claude. На сервере файл загружает ядро Битрикса, пускает только администратора, печатает свой номер запуска и выполняет код, только если номер в адресе совпал. В конце работы файл удаляет сам себя.](img/06-kit-exec.svg)

*Верхний ряд — как файл попадает на сервер, нижний — что он делает при открытии. Проверка администратора стоит после ядра Битрикса, поэтому права настоящие. В конце работы файл удаляет себя сам — тоже изменяющим запуском, с согласия.*

### Как читать ответ страницы

| На странице | Что это значит | Что делать |
| --- | --- | --- |
| `KIT-RUN <свой номер>` без «код не выполнялся» | код выполнен | вывод — результат; адрес больше не открывать |
| «kit: только для администратора» (403) | администратор не вошёл | вкладку вперёд, пользователь входит в `/bitrix/admin/`, открыть снова |
| `KIT-RUN` с чужим номером, 404 или страница сайта | новый файл ещё не доехал | ждать 5–10 секунд, до 6 попыток, потом просить проверить заливку |
| «код не выполнялся» | адрес без верного `?run` | открыть адрес из вывода `kit-exec.js` |
| Parse error, сбой `init.php` без `KIT-RUN` | упало до проверки прав | искать причину; повтор не поможет |
| пусто, 500/502/504, обрыв | неизвестно: `KIT-RUN` мог застрять в буфере | чтение — повторить можно; изменение — не открывать, проверить чтением и спросить |
| «headers already sent» | сайт что-то вывел раньше заголовков | на этом сайте канал не заработает — нужен SSH |

Остаточный риск оставлен сознательно: пока файл с изменяющим кодом лежит на сервере, тот же адрес выполнит код ещё раз. Поэтому такую страницу открывают один раз, вкладку не перезагружают и по истории на неё не возвращаются. При автозаливке файл уезжает и на тот сервер, куда льёт PhpStorm, — удалять его в конце нужно на каждом.

### Удаление файлов — delete-list.php

`$dryRun = true`: список и куда лягут копии → «Выполнить по-настоящему?» — «да» → копия в `~/kit-backup/<дата>/…`, сверка md5, затем `unlink` → снаружи 404, отметка ✅ в плане выкладки

Каждый путь проверяется через `realpath`: внутри `$base`, файл, не симлинк, под узкую маску (`*.php.back*`, а не `*.back*` — под неё попал бы `jquery.backstretch.js`); маски `*` и `*.*` не принимаются. Стоп-лист не удаляется никогда: `.htaccess`, `.settings.php`, `dbconn.php`, `.env`, а в корне ещё `index.php`, `urlrewrite.php`, `robots.txt`, `sitemap*.xml`. Копия не удалась — файл остаётся; места меньше, чем копии плюс 100 МБ, — стоп.

### Чем каналы отличаются

|   | SSH | Файл-канал |
| --- | --- | --- |
| Где работает код | PHP CLI на сервере, код идёт через stdin | веб-запрос к сайту |
| Режимы проекта | любой; bitrix — с ядром Битрикса | только bitrix |
| Кто такой `$USER` | никто, права снимает `NOT_CHECK_PERMISSIONS` | вошедший администратор |
| Предел времени | `--timeout` 90 с + 10 с запаса — меньше лимита Bash в 120 с | `max_execution_time` и таймаут веб-сервера |
| Владелец созданных файлов | пользователь SSH (BitrixVM — входить под `bitrix`) | пользователь веб-сервера |
| Обрыв при изменении | код 3 — результат неизвестен | пустая страница или 5xx — результат неизвестен |

Библиотека скриптов работает в обоих каналах: `inventory.php` — окружение, сайты и шаблоны, модули, инфоблоки, HL-блоки, файлы `b_file`; `check-files.php` — сверка файлов с локальными по md5 (код готовит `md5-check.js`); `delete-list.php` — удаление строгим списком. Проектные копии с конкретными путями лежат в `.claude/scripts/NN-имя.php`: в git есть, на сервер не уезжают.

## Снимки «до/после» `/kit:visual`

Нужны перед обновлением ядра, модулей или шаблона и после каждого шага, который может задеть вид страниц. Снимаются гость и администратор, ширины 1920 и 390.

![Снимки /kit:visual: один раз — зависимости, список страниц и вход администратора; на каждое изменение — эталон before, контрольный прогон для замера шума, шаг, снимки after, сравнение и отчёт. Перед записью снимков проверяется, что PhpStorm не зальёт их на сервер.](img/07-visual.svg)

*Контрольный прогон check снимает эталон второй раз теми же настройками: всё, что разошлось между двумя одинаковыми прогонами, — шум, и дальше он не считается отличием.*

### Порядок разбора сравнения

1. **Статусы и ошибки** — смена статуса (200 → 500), редирект, USER_ID, новые JS-ошибки и ответы ≥ 400. Это главное.
2. **Отличается** — Claude открывает дифф-картинку и оба снимка и смотрит сам, плюс пропавшие и новые строки текста.
3. **В пределах шума** и «не снимали» — только упоминание.

### Особенности

- Текст сравнивается с точностью до чисел (цифры → `#`): таймер или «Найдено 12» шумом и останутся. Смена статуса между одинаковыми прогонами шумом не бывает.
- Снимки из-под админа — только локально: `.claude/docs/visual` не коммитится и не выкладывается, инструмент сам кладёт туда `.gitignore`.
- Опасные адреса (выход, `action=`, `sessid=`, удаление, `/bitrix/`) не снимаются; `"unsafe": true` — с согласия на конкретный адрес.
- Нужен установленный Google Chrome. Метки — латиницей: `after-10.5a`.

| Код | Что |
| --- | --- |
| 0 | норма |
| 1 | страницы не снялись, или в сравнении отличия сверх шума |
| 2 | аргументы или `pages.json`: опасный адрес, опечатка, метка с другого адреса |
| 3 | нет сессии входа или она истекла — снова `login` |
| 4 | защита выкладки: PhpStorm зальёт снимки на сервер |
| 5 | нет зависимостей или Chrome |

## Отчёт для заказчика `/kit:report`

С 2.12.0. Собирает из журнала, git и плана выкладки текст для задачи Битрикс24 или письма: что сделано, что выложено на сайт, что нужно подтвердить, открытые вопросы и что дальше. Пишет для заказчика: без хешей, путей, имён файлов, внутренних названий и подробностей разработки; пустые разделы не выводит.

период: дата из аргумента, иначе с прошлого отчёта, иначе с начала текущего этапа → сделано — шаги из коммитов за период (по ID в заголовке) и их строки в журнале → выложено — строки «Залито»; при автозаливке — шаги, закоммиченные в периоде → подтвердить — решения за период, которые касаются заказчика → дата отчёта — заметкой во входящие; следующий /kit:step-done пишет её в «Справочник»

## Удалённый репозиторий и работа с другого компьютера

С 2.5.0 git проекта можно держать в закрытом удалённом репозитории (GitHub, GitLab, корпоративный сервер). Тогда заболели или работаете из дома — достаточно `git clone`: вместе с кодом придут журнал, решения, план выкладки, правила и скрипты. Репозиторий создаёте вы — закрытым и пустым, вход тоже ваш; подключает его `/kit:project-init` (параметр «Удалённый репозиторий: origin»).

шаг проверен → один коммит (kit-commit.js) → первый раз: `secret-scan --history` → `git push -u origin HEAD`

- На другой машине: плагин, `git clone` в ту же папку (параметр «PHP» — путь на машине, и он в git), сервер выкладки в PhpStorm (`.idea` не в git), свой SSH-ключ, зависимости снимков заново, скиллы Битрикса — через `/kit:project-init`.
- Работать с одного компьютера за раз: при старте хук сверит ветку с удалённой, и Claude подтянет чужие коммиты, `/kit:step-done` отправит свои; разошлись — Claude остановится и спросит.
- Адрес с логином или токеном внутри не принимается; перед первой отправкой проверяется вся история — секрет из старых коммитов остановит отправку.

## Подготовка проекта `/kit:project-init`

Запускается только командой. В существующем проекте дополняет недостающее и ничего не перезаписывает. Порядок важен — особенно пункт 7.

1. **Разведка, только чтение.** git и его настройки, файлы kit, признаки старого формата (из правила хука), признаки Битрикса (`bitrix/`, `local/`, `urlrewrite.php`), `.idea`: автозаливка, серверы, домен из `webServers.xml`, File Watchers.
2. **Вопросы** — не больше четырёх за раз, найденное разведкой — первым с пометкой «(Рекомендую)»: режим и окружение; затем адрес сервера, задача, исключения, вотчеры; удалённый репозиторий и «Ставить скиллы Битрикса?» (с 3.0.0 — при каждом запуске); с 3.3.0 там же «Вести проект по системе Мэтта Покока?» — тоже при каждом запуске.
3. **Версия PHP.** `site-probe.js` читает `X-Powered-By` прода и находит такой же `php.exe` в OSPanel — для хука `php -l`.
4. **SSH.** Псевдонимы из `~/.ssh/config` (с `Include`, только строки `Host`/`HostName`/`User`, ключи не открываются), затем `ssh-probe.js` — одно подключение: папка сайта и PHP CLI нужной версии. **Ветка:** Новый хост — пользователь один раз входит сам; сменился отпечаток — стоп.
5. **Выкладка** (с 2.17.0) — когда окружение и SSH уже известны: окружение — один сервер, прод или дев; варианты «PhpStorm Always» / «Claude по SSH» (если SSH есть) / «вручную»; при автозаливке и «Claude по SSH» — вопрос «Документы на сервере» (при SSH — с 2.18.0).
6. **План на согласие** — таблица «что есть / что сделаю / что пропущу». Без согласия ничего не пишется.
7. **Автозаливка выключена, исключения PhpStorm — до любой записи.** На время настройки пользователь выключает автозаливку (Tools → Deployment → Automatic Upload, с 2.16.0) — записанное не уезжает на сервер. Исключения всё равно до любой записи: не выключили — `git init` и `settings.local.json` уехали бы автозаливкой. Затем сверка `--check`; при автозаливке — `.htaccess` и проверка снаружи.
8. **Git, если его нет.** `autocrlf=input`, `quotepath=false`, `.gitignore` по шаблону режима, `secret-scan --all` по всему, что попадёт в коммит, первый коммит `0.1` скриптом `kit-commit.js`. **Ветка:** Нашёлся секрет — исключить путь или убрать секрет; варианта «это не секрет» нет.
9. **Файлы kit.** `.claude/.htaccess`, `.claude/CLAUDE.md` из шаблона (или дописать только раздел параметров), журнал и план выкладки в `.claude/docs`. Шаблоны собираются во временной папке и пишутся одной записью, когда не осталось ни одного `{{…}}`.
10. **Проверка снаружи.** `check-closed.js` запрашивает каждый файл `.claude` по каждому адресу: 404, 403 и 401 — норма, «ОТКРЫТ» или редирект — стоп и разбор.
11. **Битрикс: скиллы** (с 2.7.0; с 3.0.0 — отдельным вопросом). Ответ «Да» — `bitrix-skills.js` ставит в `.claude/skills` свежие версии скиллов из bxmaximum/bitrix-framework-skills (без `bitrix24-*`) и bitrix-tools/best-practice — 46 штук, уже поставленные обновляет; «Нет» — не трогает. В правила проекта — строка «код на Битриксе — по этим скиллам». В git и на сервер скиллы не попадают.
12. **Система Мэтта** (с 3.3.0). «Да» — `claude plugin install mattpocock-skills@claude-plugins-official --scope project` (или `enable`, если стоит выключенным) и `claude plugin disable superpowers@claude-plugins-official --scope project`; сверка `matt-skill.js --status`; нужен перезапуск сессии. Сессия в `.claude/worktrees/…` — команды `claude plugin` не запускаются (плагин встал бы на worktree): пользователя просят открыть сессию в основной папке. `install` не нашёл маркетплейс `claude-plugins-official` — с согласия `claude plugin marketplace add anthropics/claude-plugins-official` и повтор. «Нет» после «да» — плагин Мэтта выключается, superpowers включается обратно; глоссарий, ADR и папки тем остаются. Плагин не скачался — параметр всё равно «да», хук напомнит.
13. **Переезд на формат kit 3.0** (с 3.0.0), если хук нашёл старый формат: строка плана на каждый признак — `docs/` → `.claude/docs` (исключения, `.gitignore`, старые копии на сервере, таблица «файл → куда», перенос), журнал на части, столбец «Как проверено», новая таблица решений, старые «Окружение» и «Выкладка», строки «Код пишет» и «Коммит»; в конце — проверка хуком. Отказ — kit 3.0 в проекте шаги не закрывает.
14. **Закрытие.** При автозаливке пользователь включает её и заливает записанное, пока она была выключена (`.claude/.htaccess` — первым), затем проверка снаружи. `/kit:step-done` — шаг `0.2` закрывает этап 0: он только инициализация (с 2.16.0), рабочие шаги начинаются с `1.1`. Шаг переезда — очередной шаг текущего этапа, а без открытого этапа — первый шаг нового этапа «переезд на kit 3.0».

## Система Мэтта Покока `/kit:matt`

Для больших работ, которые не влезут в одну-две сессии. Система Мэтта (mattpocock/skills, лицензия MIT) — отдельный плагин `mattpocock-skills`; kit его не копирует и не переводит, а ставит на проект и задаёт правила его работы — так же, как уже живёт с superpowers. Включается только ответом «да» на вопрос `/kit:project-init` и параметром «Система Мэтта: да»; по ходу работы Claude её не предлагает. В проекте Мэтта superpowers выключен.

- **Мелкая задача** — без карты и тикетов: сделать и закрыть `/kit:step-done`. **Большая** — Claude вызывает навык `/kit:matt`; маршрут (карта `wayfinder`, или грилинг → `to-spec` → `to-tickets`, или сразу сделать) предлагает пользователю вопросом.
- **Общая сессия** — координатор: держит карту и очередь тикетов, на каждый тикет запускает исполнителя, принимает отчёт; сама тикеты не решает. **Исполнитель** — подчинённая сессия приложения Claude, если нужен пользователь, иначе фоновый субагент; задание — по шаблону навыка; исполнитель не коммитит и не вызывает `/kit:step-done`. Навыки Мэтта «только по команде» инструментом Skill Claude не вызывает (платформа откажет) — читает их файлом, путь выдаёт `matt-skill.js`; отказ всё же пришёл — пользователь вводит `/mattpocock-skills:<имя>` сам.
- **Приёмка.** Тикет = шаг kit `<этап>.<номер тикета>`; общая сессия закрывает его через `/kit:step-done` одним коммитом только с файлами тикета, в тикете — `Status: resolved`. Два этапа: подготовка (карта, спек, нарезка) и реализация (тикеты `<тема>-build/`). Шаг не по тикету, пока идёт этап Мэтта (мелкая задача, `/kit:project-init`), — `N.0а`, `N.0б`…: номера без буквы заняты тикетами.
- **Без пользователя** — только по его слову и не при «PhpStorm Always» на проде; перед включением — вопрос о режиме разрешений: Auto, Bypass или Manual, где первый тикет идёт при пользователе: правки `.claude` он разрешает до конца сессии, запуск скриптов kit и проверок проекта — «больше не спрашивать» (иначе работа встанет на первой записи в `.claude/docs` или на первом скрипте) — справка `reference/autonomous.md`. Тикет закрывается после проверок и ревью навыком `mattpocock-skills:code-review` в общей сессии без вопроса «Коммитить», с пометкой «принят без просмотра»; вопросы — в `## Comments` тикета; между тикетами — проверка лимитов; когда пользователь вернулся — разбор по одному тикету; в удалённый репозиторий такие коммиты уходят только после разбора (без пользователя `/kit:step-done` — без `--push`, даже если хук при старте велит отправить).
- **Файлы** — в папке документов: `work/<тема>/` (`map.md`, тикеты, `spec.md`), `work/<тема>-build/`, `GLOSSARY.md`, `adr/`; в корень проекта — ничего (страж `guard-matt.js`). Трекер — эти локальные файлы по справке `reference/tracker.md` (поля, статусы, ответ в тикете); `/setup-matt-pocock-skills` не нужен. Закрытие этапа реализации переносит обе папки темы в `archive/` вместе.

## Грабли и чем они закрыты

| Грабля | Что делает kit |
| --- | --- |
| `cd` меняет каталог всей сессии | guard-bash запрещает; в Bash можно `( cd … && … )`, в PowerShell — только абсолютные пути |
| исполнитель Мэтта коммитит сам (`implement` велит коммитить) | в проекте Мэтта guard-bash отказывает `git commit`, `merge` локальной ветки, `revert`, `cherry-pick`, `am`: коммит — только `/kit:step-done` (`kit-commit.js`), тикет принимает общая сессия |
| Мэтт заводит ветки и worktree (`prototype`, `wayfinder`, `implement-spec`): сессия остаётся на ветке, коммиты уходят туда, а при автозаливке файлы с диска ещё и уезжают на сервер | в проекте Мэтта при любой выкладке guard-bash отказывает создание веток и worktree в git, guard-matt — `EnterWorktree`, субагенту с `isolation: worktree` и подчинённой сессии с worktree |
| при автозаливке `git bisect`, `stash`, переход на старый коммит или `reset --hard` переписывают файлы на диске — старые версии уезжают на сервер (`diagnosing-bugs` предлагает бисекцию) | в проекте Мэтта при «PhpStorm Always» guard-bash отказывает перезапись рабочей копии (и `rebase`, `pull --rebase`, `restore --source`); бисекция — в копии через `git clone` во временную папку |
| Мэтт пишет `GLOSSARY.md`, `docs/adr/`, `.scratch/`, опросники и папки `teach` в корень, а на сайте это корень сайта | guard-matt отказывает запись в корень; место — папка документов (`GLOSSARY.md`, `adr/`, `work/<тема>/`) |
| `sed -i` портит `\` в неймспейсах PHP | guard-bash запрещает; PHP правится только через Edit |
| ошибка синтаксиса PHP уезжает на прод автозаливкой | php-lint после каждой правки; при Always черновик — во временной папке |
| журнал, скрипты, снимки или `.git` уезжают на сервер | Excluded Paths при каждом старте, `.claude` в «Не выкладывать», `.htaccess`, проверка снаружи `check-closed` |
| nginx отдаёт статику мимо `.htaccess` | `.claude` исключена целиком; снимки только локально, visual при риске — код 4 |
| секрет попадает в коммит | secret-scan до и после `git add`, значения маскируются; подстановки шаблонов (`$key`, `{{…}}`, `#API_KEY#`) не считаются секретом |
| кириллица в путях git | `core.quotepath=false` во всех командах |
| `$arResult` исчезает из сообщения коммита | только одинарные кавычки; заголовок проверяется символ в символ |
| Git Bash превращает `/путь` в `C:/Program Files/Git/…` | `MSYS_NO_PATHCONV=1` или PowerShell; `remote-php.js` ловит переписанный путь (код 4) |
| чужая подпись в коммите | подпись дословно из инструкций основного агента, скрипт свою не подставляет |
| изменяющий код выполнился дважды | SSH: код 3 = неизвестно, без повтора; файл-канал: `?run=`, одно открытие, вкладку не перезагружать |
| удалили не тот файл | строгий список, узкие маски, стоп-лист, сухой прогон, копия с md5 |
| зависший PHP обрывает вызов | 90 с + 10 с запаса меньше 120 с лимита Bash — приходит код 3, а не обрыв |
| подмена сервера | «REMOTE HOST IDENTIFICATION HAS CHANGED» — стоп; `StrictHostKeyChecking=no` и `accept-new` не используются |

| заболел — продолжить работу не с чего | удалённый репозиторий: коммит уходит после каждого шага, при старте сессии — сверка; дома — `git clone` |
| закрытие шага съедает время и контекст | скрипты вместо агента-модели (с 3.0.0): `kit-step.js`, `kit-journal.js`, `kit-commit.js`; ядро `/kit:step-done` — 14 КБ, ветки — в справках |

## Выпуск и обновление

- Установленный плагин — копия в кэше `~/.claude/plugins/cache/claude-kit/kit/<версия>`. Claude Code работает с копией, а не с папкой репозитория.
- Без повышения `version` в `plugin.json` и `marketplace.json` обновления не будет: `claude plugin update` ответит, что версия последняя.
- Порядок выпуска: версия → слияние в `master` → `claude plugin marketplace update claude-kit` → `claude plugin update kit@claude-kit` → перезапуск сессий. Push на GitHub — только с согласия.
- Зависимости снимков и сессии входа лежат в `%LOCALAPPDATA%\kit\visual` — вне кэша, поэтому обновления плагина их не трогают.
- Переход на новую мажорную версию — раздел README «Переход на …». С 3.0.0 — `/kit:project-init` в каждом проекте (переезд на формат kit 3.0): хук предложит его сам.
- Эта страница пересобирается при мажорном выпуске или когда выпуск добавляет или убирает команду, агента, хук, скрипт либо режим; общий спек заморожен на 2.18.0 — дальше спеки этапов и README.
- Проверить правки без выпуска: `claude --plugin-dir C:\OSPanel\home\claude-kit\plugins\kit`.
