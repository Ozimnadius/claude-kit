# Спецификация — выкладка «Claude по SSH» и один сервер на проект (прод или дев)

> Разделы kit поверх дизайна `superpowers:brainstorming`. Выбранный подход и отвергнутые — в «Решения» журнала (DECISIONS).

## Задача

- Номер: без задачи — идеи 1 (вариант «Claude по SSH») и 2 раздела «Новые идеи и замечания» `work/MyIdeas.md`, решения №31 и №32.
- Цель: в проекте с SSH Claude сам заливает правки шага на сервер — после просмотра пользователем, без PhpStorm и без ручной заливки списком; в историю git попадают только шаги, проверенные на сервере. Заодно у проекта один сервер — прод или дев.

**Откуда.** Сейчас kit умеет по SSH только выполнять команды (`/kit:server`, `remote-php.js`, `ssh-probe.js`); заливает файлы PhpStorm (автозаливка) или пользователь по списку `/kit:deploy-list`. Идея 2: в режиме «Claude по SSH» шаг идёт так — изменения, просмотр в панели, заливка на сервер, проверка, коммит и пуш (решение №32). Обсуждая вариант для окружения «дев + прод», пользователь решил (2026-10-15) убрать эту вилку совсем: проект ведёт один сервер — прод или дев; при деве перенос на прод — потом, целиком (с миграциями таблиц), вне kit. Это меняет часть решения №34 (варианты вопроса о выкладке при «дев + прод»).

## Требования

### Окружение: один сервер на проект

- Т-1. `/kit:project-init`, первый вызов, вопрос «Окружение»: «Прод — шаги идут на прод и проверяются там» / «Дев — шаги идут на дев; перенос на прод — вне kit». Варианта «дев + прод» нет. Параметр `Окружение: прод | дев`.
- Т-2. Проект ведёт один сервер — сервер окружения: заданы только его адрес и SSH (`Прод` и `SSH прод` при «прод», `Дев` и `SSH дев` при «дев»), параметры второго — `—`. Второй вызов спрашивает «Адрес сервера» (прода или дева — по окружению; догадка — из `rootFolder` `.idea/webServers.xml`, как сейчас); третий вызов — только удалённый репозиторий (вопроса об адресе дева нет). `site-probe.js`, SSH-разведка, `check-closed.js` и «сервер автозаливки» п. 4.0 / 4.5 / 4.8 — этот один сервер.
- Т-3. Сервер по умолчанию — из «Окружения»: при `Окружение: дев` `remote-php.js`, `kit-exec.js`, `/kit:visual` (адрес сайта), `ssh-deploy.js` и `deploy-list.js` работают с девом без флага; при любом другом значении — с продом, как раньше. Флаг `--env прод|дев` по-прежнему перекрывает. `/kit:server`: сервер — по «Окружению»; заданы оба SSH (старый проект) и пользователь не сказал где — спросить (как сейчас).
- Т-4. Старые проекты (`Окружение: дев+прод`, `Выкладка: вручную; дев — PhpStorm Always`) работают как до 2.17.0: сервер по умолчанию — прод, правило автозаливки на дев, `/kit:deploy-list` — полный список для прода. Повторный `/kit:project-init` в таком проекте спрашивает (AskUserQuestion) «прод» или «дев» и правит параметры только с согласия.

### Вопрос о выкладке

- Т-5. Вопрос «Как файлы попадают на сервер» (раздел «Выкладка» — после SSH, как с 2.16.0) — одинаковый для прода и дева: «PhpStorm Always» / «Claude по SSH» / «вручную списком файлов». «Claude по SSH» — только если SSH-разведка сервера окружения прошла (код 0) и параметр `SSH …` задан.
- Т-6. Первым с «(Рекомендую)» — значение параметра «Выкладка» из существующего раздела; иначе `PhpStorm Always`, если в `.idea/deployment.xml` автозаливка (`autoUpload="Always"` / `myAutoUpload` = `ALWAYS`); иначе «Claude по SSH», если SSH есть; иначе «вручную». Параметр «Выкладка»: `PhpStorm Always` | `Claude по SSH` | `вручную`.
- Т-7. «Документы на сервере» спрашивается только при «PhpStorm Always» (как сейчас): при «Claude по SSH» `.claude` на сервер не уезжает никогда, параметр — `нет`. Автозаливка PhpStorm выключается в п. 4.0 и включается в п. 4.8 только при «PhpStorm Always»; при «Claude по SSH» и «вручную» остаётся выключенной — сказать в плане на согласие и в итоге.
- Т-8. Шаблоны:
  - `templates/CLAUDE.md` — `Окружение: прод | дев`; в разделе «Окружение» — строка только сервера окружения; вариант пункта «Выкладка» для «Claude по SSH» (правки шага заливает `/kit:step-done` после просмотра скриптом `ssh-deploy.js` — всё, что изменилось с последней заливки, и удаления; затем проверка на сервере и коммит; автозаливка PhpStorm выключена); вариант пункта «Код пишет Claude» в «Как работаем» (запись в проект → `/kit:step-done`: просмотр, заливка, проверка на сервере, коммит);
  - `templates/deploy-prod.md` — заголовок «Выкладка на прод» / «Выкладка на дев», таблица «Залито на прод» / «Залито на дев» по окружению, вариант «Общих правил» для «Claude по SSH».

### Скрипт заливки `ssh-deploy.js`

- Т-9. Вызов из корня проекта:
  ```
  node ssh-deploy.js [--env прод|дев] [--base <коммит>] [--timeout сек]         — список, без подключения
  node ssh-deploy.js [--env прод|дев] [--base <коммит>] [--timeout сек] --go    — залить, удалить, сверить md5
  ```
  Сервер — `--env`, иначе по «Окружению» (Т-3); куда — параметр `SSH прод` / `SSH дев` (`хост:/папка`, разбор — `parseTarget` из `lib/ssh.js`).
- Т-10. База — с чего считать изменения: `--base` → последняя строка таблицы «Залито на прод» / «Залито на дев» плана выкладки (по окружению): хеш в «Коммит», а при «Выкладка: Claude по SSH» пустая ячейка — коммит шага по ID из «Шаг» (последний коммит с заголовком `<ID>: …`) → первый коммит репозитория (копия сервера). Строка без хеша и без такого коммита пропускается — берётся предыдущая. Поиск по ID — только в режиме SSH: там строку пишет тот же шаг, что делает коммит, и его дерево — ровно залитое; при ручной выкладке строку без хеша могут записать позже самой заливки, и база по ID потеряла бы файлы, поэтому там строка без хеша, как и раньше, пропускается.
- Т-11. Список — всё, что изменилось от базы до текущего состояния папки: `git diff --name-status --no-renames <база>` (закоммиченное и незакоммиченное отслеживаемое) и `git ls-files --others --exclude-standard` (новые файлы). Убираются — те же правила, что у `deploy-list.js`: `.git`, `.idea`, `/.claude`, `/kit-exec.php`, папка журнала вне `.claude`, «Не выкладывать». Удалённые в git — в «Удалить». Залить — только обычные файлы; что не файл (папка-подмодуль) — в вывод «пропущено», код 1.
- Т-12. Без `--go` — вывод: база и откуда она взята, «Залить (N)», «Удалить (M)», сервер (`хост:папка`); подключения нет. Список пуст — «нечего заливать», код 0 и с `--go` (подключения нет).
- Т-13. `--go` — одно подключение (`runSsh` из `lib/ssh.js`, `sh -s`, сценарий — на stdin):
  1. `cd` в папку сайта; нет — ошибка; нет `base64` или `md5sum` — ошибка, ничего не записано;
  2. каждый файл: `mkdir -p` его папки, содержимое — `base64 -d` во временный `<файл>.kit-tmp`, затем `cat <tmp> > <файл>` и `rm -f <tmp>` (у существующего файла остаются права и владелец; оборванная передача не оставляет файл наполовину записанным);
  3. удаления — `rm -f`;
  4. md5 залитых файлов (`md5sum` по stdin файла — пути в выводе не разбираются); скрипт сверяет с локальными.

  Итоги по файлам — по номеру файла в сценарии, а не по пути.
- Т-14. Вывод `--go`: «Залито и сверено: N», «Удалено: M», ошибки по файлам; последней строкой — готовое значение поля `Файлы` блока DEPLOY.
- Т-15. Коды: 0 — всё залито и сверено (или нечего заливать); 1 — часть не вышла (ошибка записи или удаления, md5 не совпал, нет папки сайта, `base64` или `md5sum`, пропущенное «не файл»); 2 — SSH для сервера не задан или параметр неверный; 3 — нет подключения, обрыв, вышло время; 4 — аргументы, git, недопустимый путь (абсолютный, с `..`, с управляющими символами) — до подключения, на сервер ничего не ушло.
- Т-16. Повтор безопасен: та же заливка ещё раз даёт тот же результат; при кодах 1 и 3 её можно просто запустить снова. Таймаут по умолчанию — 100 с (меньше предела инструмента Bash в 120 с), `--timeout` — до 600.
- Т-16а (финальное ревью). Удаляется на сервере только то, чего нет на диске: файл, убранный из git через `git rm --cached`, остаётся (вывод «Не удаляю — файл есть локально»). Служебные папки superpowers (`.superpowers`, `.worktrees`, `docs/superpowers`) не заливаются никогда. Откат шага — `ssh-deploy.js [--go] -- <пути>`: только эти пути, по текущему состоянию папки (есть на диске — залить, нет — удалить; исключённый из выкладки или недопустимый путь — код 4).
- Т-17. Общий код — `scripts/lib/deploy.js`: правила исключений, база (таблица по окружению, пустой «Коммит» → коммит по ID шага), список изменений. `deploy-list.js` переходит на него без изменения вывода; таблица — по окружению; при «Выкладка: Claude по SSH» — полный список с пометкой «заливает `/kit:step-done` (`ssh-deploy.js`)».

### Шаг в `/kit:step-done`

- Т-18. При «Выкладка: Claude по SSH» и непустом списке `ssh-deploy.js` порядок шага:
  1. исходное состояние, данные для docs-keeper — как сейчас; до команды проверяется только локальное (`php -l`, тесты);
  2. просмотр в панели (п. 3а): перед вопросом — сухой прогон `ssh-deploy.js` (что залить и удалить, на какой сервер); вопрос — «Залить на сервер» / «Есть вопросы — оставлю комментарии» / «Не заливать пока»;
  3. заливка — `ssh-deploy.js --go`; код 1 или 3 — причину пользователю, повтор безопасен; не вышло — стоп, коммита нет; код 2 — SSH не задан: стоп, предложить `/kit:project-init`;
  4. проверка на сервере: «Код пишет Claude» — Claude проверяет сам по правилам проекта (страница, десктоп и мобильная ширина); «пользователь» — AskUserQuestion «Работает» / «Не работает — опишу»; не прошла — правка (часть шага), затем снова п. 2;
  5. docs-keeper — после проверки: в CHECK — сверка md5 и проверка на сервере; блок DEPLOY — `Файлы` из вывода скрипта, `Коммит` пустой (это коммит шага — его найдут по ID), `Проверка`;
  6. коммит и отправка — без нового вопроса (ответ «Залить на сервер» их включает); панель закрывается после коммита.
- Т-19. Особые случаи: список пуст (шаг меняет только документы) — шаг как обычно, вопрос «Коммитить»; «Коммит: сразу» — без панели: список — в чат, затем заливка, проверка, docs-keeper, коммит; «Не заливать пока» — стоп, как «Не коммитить пока». Изменения, не относящиеся к шагу, в порядке SSH уезжают на сервер вместе с ним — вопрос «В этот шаг» / «Остановиться» вместо «оставить как есть»; файл, убранный из коммита, на сервер всё равно уезжает. Отказ от шага после заливки — вернуть файлы локально и сервер теми же путями (`ssh-deploy.js --go -- <пути>`), без коммита (финальное ревью).
- Т-20. docs-keeper: строка DEPLOY — в таблицу по «Окружению» (`дев` — «Залито на дев», иначе «Залито на прод»; нет таблицы — добавить раздел); COMMITS заполняет пустые ячейки «Коммит» только у строк от `ssh-deploy.js` — по колонке «Шаг» (при ручной выкладке пустой «Коммит» не значит «коммит шага» — защита Т-10; уточнено финальным ревью).
- Т-20а (финальное ревью). `/kit:project-init`: при «Claude по SSH» в проекте, который уже вёлся, — сухой прогон и точка отсчёта заливки (DEPLOY с `Коммит: HEAD`) с согласия пользователя: иначе первый шаг зальёт всё от первого коммита и может затереть правки, сделанные на сервере.

## Предположения

- На сервере Linux: `sh`, `base64`, `md5sum` (coreutils или BusyBox) — есть у хостингов с SSH.
- Пути проекта — это пути от корня сайта (как у `deploy-list.js` и `md5-check.js`).
- Шаг — до единиц мегабайт: base64 (+33 %) одним потоком ssh укладывается в 100 с.
- OpenSSH для Windows передаёт stdin без искажений — `remote-php.js` уже отдаёт так код PHP.
- `cat > файл` сохраняет права и владельца существующего файла; новые файлы — по umask пользователя SSH, как при заливке PhpStorm по SFTP. Пока `cat` пишет файл (доли секунды), запрос к сайту может увидеть его неполным — как и при заливке PhpStorm.
- Правки в путях, которые игнорирует git (`bitrix/`, `upload/`), скрипт не видит — их заливают отдельно (`/kit:server`, с согласия).

## Дизайн

**Окружение.** Параметр «Окружение» становится выбором сервера: `прод` или `дев`. Вспомогательная функция `serverEnv(params)` (в `lib/project.js` — её берут и скрипты без SSH, например `/kit:visual`) отдаёт `'дев'` только при значении ровно `дев`, иначе `'прод'` — так старое `дев+прод` остаётся продом. Её используют `remote-php.js`, `kit-exec.js`, `lib/visual/config.js`, `lib/deploy.js` как значение `--env` по умолчанию. Адрес — «Прод» или «Дев», SSH — «SSH прод» или «SSH дев», таблица плана — «Залито на прод» или «Залито на дев».

**`lib/deploy.js`** (из `deploy-list.js`):
- `skipRules(info)` — как сейчас;
- `baseFromPlan(planPath, env, cwd)` — последняя строка таблицы `Залито на <env>` с хешем; пустой «Коммит» → `git log --format=%h%x09%s` и первый заголовок, начинающийся с `<Шаг>: `; не нашлось — строка выше;
- `resolveBase(cwd, info, env, baseArg)` → `{ base, source }` — аргумент → план → первый коммит;
- `changes(cwd, base, rules, { worktree })` → `{ upload, del }`: без `worktree` — `git diff <база>..HEAD` (как `deploy-list`), с `worktree` — `git diff <база>` и неотслеживаемые файлы.

**`ssh-deploy.js`** — сценарий для `sh -s`:

```
cd '<папка>' || { echo 'KIT_ERR нет папки сайта'; exit 0; }
command -v base64 >/dev/null 2>&1 && command -v md5sum >/dev/null 2>&1 || { echo 'KIT_ERR нет base64 или md5sum'; exit 0; }
mkdir -p '<папка файла 1>' && base64 -d > '<файл 1>.kit-tmp' <<'KIT_B64'
<base64 строками по 76 символов>
KIT_B64
if [ $? -eq 0 ] && cat '<файл 1>.kit-tmp' > '<файл 1>'; then echo 'KIT_PUT 1'; else echo 'KIT_FAIL 1'; fi
rm -f '<файл 1>.kit-tmp'
…
rm -f -- '<удалённый 1>' && echo 'KIT_DEL 1' || echo 'KIT_FAILDEL 1'
…
printf 'KIT_MD5 1 %s\n' "$(md5sum < '<файл 1>' | cut -c1-32)"
```

**Отвергнуто:**
- `sftp -b` пакетом — папки создаются по уровням, кириллица и пробелы в путях на Windows ломаются, md5 — вторым подключением, сложнее тестировать;
- `scp` по файлу — подключение на каждый файл (1–3 с), удалений и `mkdir` нет;
- архив `tar` в поток ssh — на Windows нужен `tar.exe` (кириллица в списке файлов) или свой упаковщик с длинными путями;
- окружение «дев + прод» с заливкой шага на дев и продом по списку — пользователь убрал вилку: один сервер на проект, перенос на прод — вне kit;
- отметка «что уже на сервере» в файле на сервере или в ссылке git — таблица плана выкладки видна пользователю и уже есть;
- заливка вне `/kit:step-done` (отдельной командой) — не нужна: несданное уйдёт со следующим шагом, база считается от последней отметки.
