# Сверка Аспро (aspro-merge): «правим файлы как есть, после обновления сверка сама + Claude» — устройство и обоснование

Инструмент — **aspro-merge** («сверка Аспро»). Основание — разбор обновлятора Аспро и окружения ядра Битрикса и сравнение схем
доработок (обёртки и события, полная копия шаблона, правка файлов как есть).

Этот документ — устройство и обоснование. **Источник правды по командам, параметрам и поведению — README инструмента** (в плагине —
`tool/README.md` рядом со скилом, на сайте — `local/tools/aspro-merge/README.md`); процедура для Claude — скил `aspro-merge`
(`SKILL.md`), инструкция для команды — [GUIDE.md](GUIDE.md). Документ сверен с инструментом 17.10.2026; схема проверена на
тестовом стенде с «Аспро: Оптимус» 1.7.20 → 1.7.21 **двумя настоящими обновлениями** — в режиме «копия» и в режиме «на месте»
(разделы «Проверка настоящим обновлением»).

## Для кого и зачем

Команда правит сайт прямо на проде и ставит обновления Аспро на проде через админку. Нужно, чтобы:

- доработка была **обычной правкой файла** — без обёрток, событий, вставок по маркерам и без манифеста;
- обновление Аспро не теряло доработки и доходило до сайта;
- рутину делал сайт сам, а смысловую часть (конфликты, проверка, отчёт) — Claude по скилу.

## Режимы (выбираются сами по наличию папок, оба равноправны)

| Область | Режим «копия» | Режим «на месте» |
| --- | --- | --- |
| Шаблон сайта | есть `local/templates/<шаблон>` (L): правим L, вендорский `bitrix/templates/<шаблон>` (V) не трогаем | нет L: правим прямо V |
| Компоненты Аспро | есть `local/components/aspro/<компонент>`: правим копию | правим `bitrix/components/aspro/<компонент>` |
| Публичная часть (`ajax/`, `auth/`, `include/…` — файлы, которые есть в эталоне WP) | — | всегда «на месте» |

**Эталоны** (чистые файлы вендора текущей версии, лежат в модуле и обновляются вместе с ним):
W — `bitrix/modules/<модуль>/install/wizards/<партнёр>/<решение>/site/templates/<шаблон>`, WP — `…/site/public/ru`,
C — `bitrix/modules/<модуль>/install/components/<партнёр>`.

**Сравнение режимов** (по двум настоящим обновлениям 1.7.21, таблица для команды — в [GUIDE.md](GUIDE.md#как-выбрать-режим)).
Режимы равноправны, но не одинаковы. **При обновлении копия надёжнее**: обновлятор её не трогает, сбой события не стоит потери
правок (сайт работает на прежней копии), откат мгновенный (копия возвращается к прежнему виду). Правка «на месте» привычнее, но
обновлятор перезаписывает доработанные файлы, и до конца шага (а при сбое события — до ручного `apply`) доработки держатся только на
автоматическом слиянии; откат возвращает файлы «как оставил обновлятор», то есть без доработок. В окне между установкой и решением
конфликта по умолчанию оба режима ведут себя одинаково — в конфликтном файле прежняя наша версия; только «на месте» настройкой
`conflict_keep = theirs` можно держать до решения версию вендора. Рекомендация: новые сайты — копия; где уже правят
`bitrix/templates`, можно оставить «на месте».

**Область правок** (осознанное ограничение; расширять не планируется). Доработки допустимы только в шаблоне сайта, шаблонах
компонентов в нём, компонентах Аспро и публичных файлах Аспро. Папки `bitrix/js|css|tools/aspro.*`, гаджеты, админку Аспро и модуль
сверка не ведёт: их правят только обновлятор и вендор, правка там будет перезаписана и останется лишь в бэкапе обновлятора. Сверка
рассчитана на один сайт (многосайтовость — по коду, не проверена). На рабочем сайте пакеты обновлений и снимки страниц в корне не
держат (на машине разработчика такие папки — в `.gitignore`). Это прямо сказано в скиле и в GUIDE.md.

**Доработанный файл** = файл рабочей папки, отличающийся от эталона версии, на которой его правили. Списка доработок никто не ведёт —
он вычисляется. Сгенерированные сайтом файлы шаблона (`themes/*`, `bg_color/*`, `css/custom.min.css`, `js/custom.min.js`,
`.styles.php`, `description.php`) не считаются ни доработкой, ни изменением вендора; `css/custom.css` и `js/custom.js` —
пользовательские и сверяются как обычные. Свои исключения — `exclude*` в настройках.

## Снимок (база для слияния)

Обновлятор перезаписывает эталоны без бэкапа, поэтому старую версию вендора храним сами — **снимок версии**:

- архив текстовых файлов эталонов W, WP, C текущей версии (`etalon.zip` + `etalon.json`);
- список файлов рабочих папок с хешами (видно, что правили, что удалили; ловит правки V в режиме «копия») и копии доработанных
  файлов — «наша» версия, не зависим от бэкапов обновлятора, которые бывают устаревшими (`state.zip` + `state.json`; текстовые
  доработки и изменённые двоичные файлы до 4 МБ);
- страницы «до» (`pages.json`, `snapshot --urls`) — для сравнения в `verify --urls`.

Снимок для текущей версии создаётся **сам**: агентом раз в сутки (если его нет и нет открытой сверки), при завершении сверки
(`finish`) и предохранителем перед установкой. Повторный вызов на той же версии эталон не пересоздаёт — обновляет только список
доработанных файлов (и страницы «до», если `--urls`). Пока сеанс открыт, снимок не делается.

**Хранилище** — в нём платный код вендора и наши доработки, по HTTP оно отдаваться не должно:

1. `store` в настройках — лучший вариант (папка вне веб-корней);
2. иначе `<над DOCUMENT_ROOT>/aspro-merge/<папка сайта>/<модуль>/`; если папка над корнем сама похожа на корень сайта —
   имя со случайной частью и предупреждение;
3. если над корнем писать нельзя — `/bitrix/backup/aspro-merge-<16 случайных символов>/` (для nginx нужно правило deny;
   `status` с `base_url` проверяет запросом, что хранилище не отдаётся).

В папках хранилища — `.htaccess` с запретом и пустой `index.php`; выбор запоминается в `bitrix/backup/aspro-merge.store.php`.
Хранятся 3 последних снимка и 3 последних завершённых сеанса (`keep_versions`); база открытого сеанса не удаляется. Файлы снимка
не называются `_*.back*` (такие удаляет обновлятор). Хеши в снимках и сеансах — git blob SHA-1 (как `git hash-object`).

## Сверка (сеанс)

Сеанс открывается, когда версия модуля стала новее версии, на которой в последний раз снимали состояние сайта (`seen.json` —
переживает откат сайта из резервной копии). База сеанса — снимок версии **до** обновления (при обновлении через несколько версий —
самый ранний). Применение на каждом шаге считается заново от базы и зафиксированных «наших» версий, а не от уже записанных
файлов; принятые решения переживают следующие шаги (вендор привёз тот же файл — решение записывается снова; файл изменился —
решение сливается с новой версией и идёт на проверку).

Для каждого файла, который вендор поменял (эталон снимка ↔ текущий эталон), и для файлов рабочих папок:

| Случай | Что делает инструмент |
| --- | --- |
| файл не доработан | «копия»: новая версия вендора кладётся в копию; «на месте»: обновлятор её уже записал |
| доработан, трёхстороннее слияние чистое | результат записывается (база — снимок, наша — версия на начало сеанса, их — новый эталон); PHP — только после `php -l` |
| слилось чисто, но `php -l` не прошёл или в веб-запросе нечем проверить (нет PHP CLI) | на месте наша версия, на разбор; без PHP CLI — «выполните `merge.php apply` в консоли» |
| наше отличие — только отступы, переводы строк, пробелы у скобок и `;`, `,`, `=` | берётся версия вендора (пробел внутри строки, между словами или в CSS-селекторе — доработка, она сливается) |
| вендор сменил только переводы строк | остаётся наша версия |
| наша версия уже совпадает с новой вендорской | ничего |
| конфликт | до решения: «копия» — всегда прежний файл копии; «на месте» — по `conflict_keep`: `ours` (по умолчанию) — **наша** версия, возвращается из снимка (доработка работает, исправления вендора в файле — нет), `theirs` — версия вендора, как её оставил обновлятор (без доработки). То же для двоичных, `*.min.*` и слияний, не прошедших `php -l`. Что стоит и чем грозит, прямо сказано в уведомлении, `status` и `report.md`. В папке сеанса — тройка `base`/`ours`/`theirs`/`merged` (с маркерами)/`ours.diff`/`theirs.diff`; ждёт Claude |
| двоичный (или больше 4 МБ) файл доработан и изменён вендором | «на месте» — возвращается наша версия; на разбор (выбрать `ours` или `theirs`) |
| новый файл вендора | «копия»: копируется в копию; если там уже свой с тем же именем — на разбор |
| вендор удалил файл | не доработан — удаляется из копии; доработан — остаётся («на месте» — возвращается), на разбор |
| файла не было на сайте при снимке (удалили как доработку), а обновлятор его вернул | «на месте» в шаблоне и компонентах — снова удаляется; в публичной части — остаётся; на разбор |
| доработан `*.min.js`/`*.min.css` | на разбор: слить исходник, `.min` пересобрать или взять вендорский |
| файл на сайте не равен новому эталону (точечная правка обновлятора) | на разбор, файл не трогается |
| эталон изменился, а обновлятор файл на сайт не переносил | для справки, ничего не пишется |
| в копии файла нет | ничего, если в копии нет каталога шаблона компонента, к которому он относится (ядро возьмёт файл из установленной папки); иначе — файлы шаблона сайта вне `components/` (`js/`, `css/`, `lang/`) и файлы внутри каталога шаблона, который в копии есть, ядро берёт только из копии — новая версия вендора кладётся в копию (1.7.21: `js/app.js`) |
| «копия» отстала: наша версия равна прежней версии вендора (бэкап обновлятора, эталон прежнего снимка) | берётся новая версия вендора (`stale-copy`); заметно ближе к прежней версии, чем к базе, — слияние от неё |
| файл правили на сайте во время открытого сеанса | правка становится «нашей» версией и идёт на разбор; на той же версии не перезаписывается |
| «копия», а установленную папку в снимке правили напрямую | база неоднозначна — на разбор, ничего не пишется (в тройке ещё `installed-old`) |
| режим области сменился между снимком и обновлением | в этой области ничего не применяется, всё на разбор |
| снимка версии до обновления нет | аварийная сверка по бэкапам обновлятора (`apply --no-snapshot`; событие открывает её само) |

**Состояния записей сеанса** (`status`, `session.json`, `report.md`): `ok` — уже как надо; `applied` — применено
автоматически; `auto` — ждёт `apply`; `conflict` — конфликт; `review` — на разбор; `resolved` — решено, ждёт `apply-resolved`;
`done` — решение применено; `error` — ошибка. Итог по файлу — его состояние, а не первоначальное действие плана.

## Запись и проверки

- Перед любой записью — архив отката (`rollback/NNN.zip` сеанса); `merge.php rollback` возвращает сайт к состоянию «как оставил
  обновлятор». Файлы с маркерами конфликта и не прошедшие `php -l` на сайт не пишутся.
- Запись атомарная (временный `.am-tmp-<случайно>` и переименование), права сохраняются, переводы строк и BOM — как у файла
  вендора (у двоичных — побайтно). `resolve` так же приводит `resolved` к стилю вендора, поэтому `resolved` собирают от `theirs`.
  После записи сбрасывается кеш Битрикса.
- `php -l` — через PHP CLI: в консоли — текущий PHP; в веб-запросе — `php_cli` из настроек, иначе PHP CLI той же версии, что PHP
  сайта: рядом с `PHP_BINARY` (`php.exe` рядом с `php-cgi.exe`, `php8.2` для `php-fpm8.2`), в `PHP_BINDIR`, в `PATH`, в типичных
  местах панелей. Разбор `token_get_all` не ловит ошибки компиляции, поэтому без PHP CLI слияния PHP-файлов в событии
  откладываются до консоли.
- `verify`: нерешённое; записанные файлы на месте и не менялись после записи; маркеры, BOM, `php -l`; изменения доработки и
  вендора есть в итоге — сравнение по словам, а не строкам целиком (эвристика — пометки «ПОСМОТРЕТЬ»: строки выводятся целиком;
  строка, где строка вендора объединена с нашей вставкой, и висячий CR — различие переводов строк — потерей не считаются);
  признаков исправлений вендора (экранирование, подпись параметров, `sessid`…) в итоге не меньше, чем у вендора; наша версия
  не откатывает исправления, бывшие у вендора уже до обновления (`count((array)…)`, Secure logout, `.live()` — копия отстала,
  а автослияние такое сохраняет молча; с 1.2.0); файлы с версией
  вендора (взятые инструментом и записанные обновлятором в недоработанные) равны новому эталону, записанные решения на месте;
  поиск маркеров по всем
  рабочим папкам (`--no-scan` — без него); `--urls` — страницы сайта (коды, ошибки PHP, маркеры, размер против страниц «до»;
  изменение больше 20% — «ПОСМОТРЕТЬ»). Пометки «ПОСМОТРЕТЬ» сохраняются в `session.json` и `report.md`. Для `--urls` нужен
  `base_url` — без адреса это проблема «страницы не проверены» (код 2), а не молчаливый пропуск. У завершённого сеанса `verify`
  только читает: `session.json` и `report.md` не меняются.
- `finish` — сначала `verify`: нерешённое или проблемы — сеанс не завершается (`--force` — принудительно). Затем снимок новой
  версии (страницы «после» из последнего `verify --urls` кладутся в него как `pages.json` — база для следующего `verify --urls`;
  если их сняли до последней записи на сайт — не кладутся, и `finish` советует `snapshot --urls`; `finish --urls` снимает их
  заново),
  бэкапы обновлятора этого обновления (`_<файл>.back<версия>`, `_<папка>_back<версия>.zip`) уносятся с сайта в архив
  `backups.zip` папки сеанса — по HTTP они отдают исходный код Аспро (`--keep-backups` — оставить); своё уведомление
  (`ASPRO_MERGE`) снимается, в журнал событий — запись «сверка завершена». Бэкапы прежних версий `status` показывает
  предупреждением с оговоркой «с согласия человека» и правилом веб-сервера (nginx и Apache), запрещающим `_*.back*` и
  `_*_back*.zip`; уносит их (и все прочие `_*.back*`) `archive-backups`. `notices` показывает все уведомления админки (похожие
  на обновление и сверку — помечены; например, `MYSITE_ASPRO_SYNC` прежней схемы), `notices --drop=<тег>` снимает.
- `diff <файл> [--against=theirs,ours,base,etalon,resolved]` — итог на сайте против новой версии вендора (что в файле наше) и
  против нашей версии до обновления (что принесло обновление); если обновлятор оставил на сайте не то, что в эталоне, — ещё и
  против эталона. Сеанс — открытый или последний, только чтение; переводы строк и BOM не сравниваются. Заменяет `git diff` там,
  где git нет или нет тега перед обновлением.
- `uninstall [--dry] [--delete-store --yes] [--force] [--remove-foreign-agents]` — снимает через ядро своё уведомление, агент и
  опцию-кеш `main:aspro_merge_agent` и печатает по шагам, что удалить руками: сначала строку в `init.php` (если раньше удалить
  файл подключения, `require_once` уронит сайт), затем файл подключения, папку инструмента, настройки, указатель хранилища;
  хранилище (путь и размер) — оставить или удалить `--delete-store --yes`. Пока подключение в `init.php` есть, агент и опция
  остаются (интеграция проверяет таблицу агентов и добавила бы агент снова) — после удаления строки команду запускают ещё раз.
  Посторонние агенты сверки (ниже) показывает, снимает только с `--remove-foreign-agents`. При открытом сеансе — только показ
  (`--force` — всё равно); `--dry` — только показ. Без этой команды после удаления файлов в базе оставался бы агент, который
  раз в сутки вызывает несуществующий класс.
- **Агент.** Признак «агент есть» — сама запись в таблице агентов: интеграция при заходе в админку и после обновления модуля
  ищет `AsproMergeSite::agent();` (`CAgent::GetList` по точному имени) и добавляет его, если нет (удалили, база из копии).
  Опция `main:aspro_merge_agent` — только кеш проверки (время последней находки): пока ей меньше часа, хиты админки базу не
  опрашивают; после обновления модуля база проверяется всегда; «Y» прежних версий кешем не считается. **Посторонние агенты
  сверки** — имя похоже на агент сверки (как `LIKE '%AsproMerge%'` / `'%aspro_merge%'`, без учёта регистра), но не наше:
  остатки прежних версий под другими именами. `status`, `uninstall` и `agents` их называют; снимают — только с явным флагом
  (`agents --drop-foreign`, `uninstall --remove-foreign-agents`) и с согласия человека. Конкретных старых имён инструмент не
  знает — только правило похожести.

Смысловые связи между файлами (вендор меняет формат данных сразу в шаблоне, JS и ajax) движок не видит: каждый файл может слиться
чисто, а связка — сломаться. Инструмент подсказывает часть связок (общие имена в изменениях вендора в разных файлах — подсказка, а
не вывод); ловят их скил (контракты — первыми, поиск потребителей), `verify --urls`, вторая проверка и проверка страниц.

## Когда что запускается

## Консоль

`php local/tools/aspro-merge/merge.php <команда> [параметры] [--json]` — ядро Битрикса не нужно; для сброса кеша, уведомлений,
журнала событий и агентов оно поднимается в отдельном процессе (не поднялось — кеш чистится удалением папок).

`status` · `snapshot [--urls] [--force] [--rebuild]` · `changes [--no-snapshot]` · `apply [--no-snapshot]` · `resolve <файл> [<итог>|ours|theirs|keep|delete]` ·
`apply-resolved` · `diff <файл> [--against=…]` · `rollback [--force]` · `verify [--urls] [--no-scan]` ·
`finish [--force] [--keep-backups] [--urls]` · `archive-backups` · `notices [--drop=<тег>]` · `agents [--drop-foreign]` ·
`export [--out=<zip>] [--all]` · `import <zip> [--no-apply]` ·
`uninstall [--dry] [--delete-store --yes] [--force] [--remove-foreign-agents]` · `version` · `help` ·
`selftest [--demo=<папка>] [--seed=<n>] [--n=<число>]` · `hook-update [--modules=<модули>] [--time-limit=<с>]` / `hook-guard` /
`hook-agent` (то же, что событие, предохранитель и агент). Все параметры — в README инструмента и справке `merge.php`.

**Версия и поставка.** Версия инструмента — одна константа (`AsproMerge\Tool::VERSION`); файл подключения знает свою
(`AsproMergeSite::VERSION`), они выпускаются вместе. `version` (сайт не нужен) и `status` показывают обе и предупреждают о
расхождении. В поставке (плагин) файл подключения лежит рядом с инструментом — `integration/aspro_merge.php`. Обновление
инструмента — замена файлов между сверками (при открытом сеансе — сначала `finish` или `rollback`); хранилище, снимки, сеансы и
настройки сайта лежат вне папки инструмента и сохраняются.

Коды выхода: 0 — всё хорошо, 2 — нужен разбор, 1 — ошибка. Настройки — `local/aspro-merge.config.php` (образец —
`config.example.php`; без файла всё определяется само, кроме `base_url` для `--urls`).

## Чего команде НЕ делать

Подробно и простым языком — [GUIDE.md](GUIDE.md#как-дорабатывать).

- Не править `bitrix/js|css|tools/aspro.*`, гаджеты, админку Аспро и модуль: обновлятор перезапишет, правка останется только в бэкапе.
- В режиме «копия» не править вендорский `bitrix/templates/<шаблон>` и не пользоваться страницей Аспро «Разработчикам» (она пишет в V).
- Не удалять файлы из копии: «нет в копии» для инструмента — «взять у вендора».
- Не запускать мастер решения повторно (перезаписывает шаблон и публичную часть без бэкапов).
- Не откладывать сверку после обновления: до неё в конфликтных файлах не действуют исправления вендора (сайт на смеси версий), а
  следующее обновление удаляет старые бэкапы.
- Не заливать на сервер старые копии файлов из редакторов после сверки — это откатит слияние.
- Не удалять хранилище и снимки: без снимка версии до обновления база для слияния — только бэкапы обновлятора.
- Не удалять файлы инструмента без `uninstall` (останется агент, вызывающий несуществующий класс).
- Не держать на рабочем сайте в корне пакеты обновлений и снимки страниц.
