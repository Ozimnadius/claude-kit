# Закрытие шага

Закрывай только проверенный шаг: `php -l`, результат на сервере или в браузере — что положено по правилам проекта. Не проверен — сначала проверь.

Все команды — из корня проекта, без `cd`.

## 1. Исходное состояние

1. Убедись, что это kit-проект: есть файл журнала (параметр «Журнал» в разделе «Параметры для агентов» файла `.claude/CLAUDE.md`; по умолчанию `.claude/docs/progress.md`, в проекте, который ещё не переехал, — `docs/progress.md`). Журнала нет — остановись и предложи `/kit:project-init`. Папка журнала — **папка документов** (`.claude/docs`): в ней `work/`, `archive/` и снимки `visual/`.
2. Запомни `HEAD` до закрытия шага:
   ```
   git rev-parse HEAD
   ```
3. Изменения шага:
   ```
   git -c core.quotepath=false status --porcelain=v1
   ```
   `-c core.quotepath=false` обязателен: без него кириллические пути приходят восьмеричными escape-последовательностями, и git-keeper их не добавит.
   FILES — файлы, которые изменил этот шаг. Если в статусе есть изменения, которые к шагу не относятся или о которых ты не знаешь, — спроси пользователя через AskUserQuestion, что с ними делать (в этот коммит / оставить как есть). Пути, которые git-keeper не пропустит (`.idea/`, секреты, параметр «Не коммитить»), в FILES не включай. Правило «Не коммитить» со `/` (`bitrix/`) — путь от корня проекта: копии шаблонов в `local/templates/…/components/bitrix/…` под него не попадают.

## 2. Данные для docs-keeper

Собери из разговора:
- `STEP` — ID шага (аргумент команды, если передан), `STATUS`, `SUMMARY` (одна строка: что сделано), `CHECK` (одна строка: как проверено — команды, страницы, ширины, итог; при `✅` обязателен), `NEXT` (ID и одна строка);
- по необходимости `STAGE`, `DECISIONS`, `DOCS`, `BUGS`, `PROD_TODO`, `DEPLOY` (`Файлы`, `Коммит`, `Удалить`, `Проверка`, `Чек-лист`), `NOTES`, `RULES` (с причиной изменения).

`DECISIONS` — по строке на решение: `ГГГГ-ММ-ДД | решение | почему | что отвергли (или —) | пользователь / агент`.
- Решения пользователя — его ответы на вопросы и прямые указания на этом шаге.
- Решения агента — только те, что трудно откатить или что влияют на следующие шаги: выбор подхода, библиотеки, места хранения, отказ от варианта. Не больше 1–3 за шаг; мелкие технические выборы не пиши.
- «Почему» и «что отвергли» — из разговора. Причина решения пользователя неизвестна — спроси его через AskUserQuestion, не придумывай. Решение отменяет прежнее — начни текст с «Заменяет №N» (номер из таблицы «Решения» журнала).

**Входящие ответы** — что пользователь отвечал на вопросы с прошлого закрытия шага (их пишет хук, сжатие контекста их не стирает):
```
node "${CLAUDE_PLUGIN_ROOT}/scripts/decision-inbox.js" --list
```
Запомни N из последней строки «записей: N» (п. 5 уберёт ровно их). Процедурные ответы пропусти: «закрывать?», «начинать?», «отправить?», подтверждения и выбор порядка работы — это не решения. Остальное, чего ещё нет в DECISIONS, добавь: выбранный вариант — решение, его описание («выбрано: …») — основа «почему», «другие» — что отвергли, «кто» — пользователь. Свой ответ («(свой ответ)») — по смыслу: встречный вопрос или уточнение — не решение. Заметки («заметка: …», например «Отчёт заказчику: …» от `/kit:report`) — в `NOTES` дословно.

На шаге снимали или сравнивали снимки (`/kit:visual`) — в NOTES: метки, какое сравнение и итог (совпадает / в пределах шума / что отличается, статусы и ошибки), путь к `report.html`. Снимки `<папка документов>/visual/` в FILES не включай (только локально, git-keeper их не пропустит); изменённый `.claude/scripts/visual/pages.json` — включай.

Шаг создал документ в `work/` папки документов (план, спек, чек-лист, материалы) — строка в `DOCS`: `work/<имя> — <о чём> — в работе, этап N`; документ на все этапы (спек, замечания пользователя) — статус `постоянный`; документ стал ненужным — статус `устарел — <чем заменён>`. Документы кладут в `work/` папки документов, а не в её корень и не в другие папки проекта.

### Закрытие этапа — сверка

Шаг закрывает этап, если передан `STAGE` (начинается новый этап), номер этапа в `NEXT` (часть ID до первой `.`) отличается от номера в `STEP` или `NEXT` пустой или `—` при `STEP` вида `N.M`. ID не вида `N.M` (`Р6а`) — только по `STAGE`. Тогда до docs-keeper сверь задуманное со сделанным:

1. **С чем сверять.** Раздел «Документы» журнала: строки `work/…` со статусом `в работе, этап <номер закрываемого этапа>` — спек (разделы «Требования», «Критерии готовности»), план (задачи). Пункты — требования Т-N и критерии или задачи плана. Таких документов нет — пункты только из таблицы этапа: шаги не `✅` (⏳, ⏸) — расхождения; все `✅` — «расхождений нет», без вопросов.
2. **Таблица сверки** — в ответе пользователю: `| Пункт | Шаги | Итог |`, итог — сделано / частично / нет / не просили (сделано сверх задуманного). Опирайся на таблицу этапа и коммиты; не уверен — «частично» с пояснением, не «сделано».
3. **Расхождения** (частично, нет) — один AskUserQuestion, список — в тексте вопроса: «В «Баги на потом» (Рекомендую)» / «На следующий этап» / «Не делаем — решением»; разное для разных пунктов — через «Другое». «В Баги» — строки `BUGS`; «Не делаем» — строки `DECISIONS` (почему — из ответа; нет причины — спроси); «На следующий этап» — в блок `RECONCILE`.
4. **Итог** — блок для docs-keeper (строка под таблицей этапа):
   ```
   RECONCILE: ГГГГ-ММ-ДД | этап N | сверено с: <документы или «таблица этапа»> | пунктов M, сделано K | расхождения: <пункт — куда; …> или нет | на следующий этап: <пункты> или —
   ```

### Закрытие этапа — архив

Шаг закрывает этап (условие — в «Сверке» выше) — прочитай раздел «Документы» журнала: строки `work/…` со статусом `в работе, этап <номер закрываемого этапа>` — кандидаты в архив (`постоянный` кандидатом не бывает). Нет — ничего не спрашивай. Есть — AskUserQuestion, список файлов — в тексте вопроса: «Все в archive/ (Рекомендую)» / «Оставить в work/»; часть — через «Другое». Оставленные в `work/` — строка `DOCS` со статусом `в работе, этап <номер следующего этапа>`: при закрытии следующего этапа их предложат снова. Выбранное в архив перенеси обычным перемещением, без git:
```
New-Item -ItemType Directory -Force '<папка документов>/archive' | Out-Null
Move-Item -LiteralPath '<папка документов>/work/<имя>' -Destination '<папка документов>/archive/<имя>'
```
Папка-документ (`work/design/`) переносится целиком; имя в `archive/` занято — спроси пользователя, файлы не перезаписывай. В `DOCS` — `archive/<имя> (было work/<имя>) — <о чём> — готово, этап N (ГГГГ-ММ-ДД)`; в FILES — **оба** пути, старый и новый: git-keeper добавит их одной командой `git add -A -- …`, и git увидит переименование — коммит шага остаётся одним. Документ не был в git (`git ls-files <старый путь>` пусто) — в FILES только новый путь: `git add` по неотслеживаемому старому пути остановил бы git-keeper.

`COMMITS` — хеши прошлых шагов из истории git:
```
git log --format="%h %s" -50
```
ID коммита — часть заголовка до первого `: `. Передай пары `ID=хеш` за последние шаги (у одного ID несколько коммитов — все через запятую). docs-keeper заполнит только пустые ячейки «Коммит».

## 3. docs-keeper

Вызови агента `kit:docs-keeper` (Agent, subagent_type `kit:docs-keeper`) с блоками:
```
STEP: …
STATUS: …
SUMMARY: …
CHECK: …
NEXT: …
COMMITS: …
<необязательные блоки>
```
Дождись отчёта: в нём «Сейчас», цитаты добавленных строк и список изменённых файлов.

**Сверь отчёт с файлом** (Grep по журналу), не доверяя отчёту на слово: строка шага `STEP`, каждый номер багов из `BUGS` (с новым статусом), каждая строка `DECISIONS` (номер из отчёта и начало текста решения), каждая строка `DOCS`, строка «Сверка …» из `RECONCILE` под таблицей этапа, при `✅` — строка `- [x] <STEP>` в плане этапа из реестра (если в плане есть чек-лист; изменённый план — в FILES). Чего-то нет в файле — вызови docs-keeper ещё раз только с недостающим и не переходи к git-keeper, пока файл не сойдётся с блоками. В отчёте «не записано: нет "почему"» — допиши причину (из разговора или спроси пользователя) и передай только эти строки.

## 4. git-keeper

Вызови агента `kit:git-keeper` (subagent_type `kit:git-keeper`):
```
FILES:
<файлы шага из п. 1.3>
<файлы из отчёта docs-keeper>
<старые и новые пути документов, перенесённых в архив>
MESSAGE: <STEP>: <суть шага одной строкой>
BODY: <CHECK дословно>
COAUTHOR: <строка Co-Authored-By>
KIT_ROOT: ${CLAUDE_PLUGIN_ROOT}
```
FILES не должен быть пустым; пути — по одному в строке, как есть, без кавычек (кавычки расставит git-keeper).

**COAUTHOR** — строка `Co-Authored-By: …` из твоих собственных системных инструкций о подписи коммитов, дословно. Таких инструкций нет — блок COAUTHOR не передавай.

## 5. Проверка

```
git rev-list --count <HEAD из п. 1.2>..HEAD
git log -1 --format=%s
git log -1 --format=%B
git -c core.quotepath=false status --porcelain=v1
```
- новых коммитов ровно **1**;
- заголовок (`--format=%s`) совпадает с MESSAGE целиком, символ в символ, а не только префиксом `<STEP>:` — пропавшие `$arResult`, `$APPLICATION` или обратные кавычки означают, что git-keeper взял сообщение в двойные кавычки;
- строка COAUTHOR есть в сообщении дословно (если передавалась);
- BODY (если передавался) есть в сообщении дословно (`--format=%B`): git-keeper на haiku бывает, меняет окончания слов («частям» → «частях»). Отличается — скажи пользователю, что передано и что в коммите; историю не чини, шаг на этом не останавливается;
- файлов шага в статусе больше нет.

Проверка прошла, а в п. 2 входящих было N > 0 — убери разобранные (пришедшие позже останутся до следующего шага):
```
node "${CLAUDE_PLUGIN_ROOT}/scripts/decision-inbox.js" --clear N
```

Что-то не так (0 или 2 коммита, заголовок не совпал с MESSAGE, чужая подпись, лишние файлы) — входящие не трогай и сообщи пользователю, что именно и какие команды это показали. Историю сам не чини: никаких `reset`, `amend`, `rebase`. Сам коммит не делай ни при каких обстоятельствах — ни в обход git-keeper, ни «чтобы доделать»: сообщи о проблеме и остановись.

## 5а. Отправка в удалённый репозиторий

Только если в «Параметрах для агентов» задан `Удалённый репозиторий` (не `—`) и проверка п. 5 прошла. `<имя>` — значение параметра, `<ветка>` — вывод `git symbolic-ref --short HEAD`. Параметра нет — пункт пропусти: коммит остаётся только локально.

1. Первая отправка — ветки там ещё не было:
   ```
   git rev-parse --verify --quiet refs/remotes/<имя>/<ветка>
   ```
   Код не 0 — сначала проверь всю историю ветки на секреты и запрещённые пути:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/secret-scan.js" --history
   ```
   Код 1 — сразу не отправляй:
   - среди находок есть секреты (всё, кроме «запрещённый путь»: пароль, вебхук, ключ) — не отправляй: покажи находки (значения замаскированы, впереди — хеш коммита) и скажи, что секрет остался в истории: убрать его из истории или начать новый репозиторий с текущего состояния — решает пользователь; историю сам не переписывай;
   - находки только «запрещённый путь» (в истории были файлы вроде `.idea/…` или `docs/visual/.gitignore`) — покажи список и спроси через AskUserQuestion: «Отправить как есть» / «Не отправлять». В вопросе предупреди: `.settings.php`, `.settings_extra.php`, `dbconn.php`, `.env`, `*.key`, `*.pem` обычно хранят пароли и ключи — если такие есть в списке, рекомендуй «Не отправлять».

   Код 2 — не отправляй, покажи ошибку.
2. Отправка:
   ```
   git push -u <имя> HEAD
   ```
   Откроется окно входа (Git Credential Manager) — входит пользователь; пароли и токены не вводи и не вписывай в адрес.
3. Не вышло:
   - `rejected`, `fetch first`, `non-fast-forward` — на удалённом есть коммиты, которых здесь нет (работали с другого компьютера, или репозиторий создан не пустым): стоп, скажи пользователю и спроси через AskUserQuestion, что делать. `--force`, `pull`, `rebase` и слияния — только после его явного выбора;
   - нет сети, вход не выполнен, репозиторий не найден, вышло время — коммит остаётся локально: причина — одной строкой (последняя строка вывода git). Не повторяй: неотправленное уйдёт со следующим шагом, а при старте сессии хук напомнит.

## 6. Ответ пользователю

Коротко: хеш и заголовок коммита, отправлен ли он (`<имя>/<ветка>` или почему нет), раздел «Сейчас» из отчёта docs-keeper. Хеш попадёт в журнал при следующем `/kit:step-done` — запоминать его не нужно.

Записаны решения агента — отдельным списком «Решения агента на этом шаге (можно возразить)»: номер, решение, почему. Нет — списка не выводи. Пользователь возразил — новое решение («Заменяет №N») запишет следующий `/kit:step-done`.

## Если агенты не подхватились

Типов агентов `kit:docs-keeper` / `kit:git-keeper` нет — запусти агента general-purpose: в запрос — полный текст файла `${CLAUDE_PLUGIN_ROOT}/agents/docs-keeper.md` (или `${CLAUDE_PLUGIN_ROOT}/agents/git-keeper.md`) без заголовка `---` и те же блоки; модель — из заголовка файла (`sonnet` / `haiku`). Для git-keeper передай KIT_ROOT обязательно: в тексте, переданном так, `${CLAUDE_PLUGIN_ROOT}` не раскроется.
