# Закрытие шага

Закрывай только проверенный шаг: `php -l`, результат на сервере или в браузере — что положено по правилам проекта. Не проверен — сначала проверь.

В режиме «Claude по SSH» (параметр «Выкладка») до команды проверяется только локальное — `php -l`, тесты: на сервер шаг уезжает внутри команды (п. 3б), там же проверка на сервере.

Все команды — из корня проекта, без `cd`.

## 1. Исходное состояние

1. Убедись, что это kit-проект: есть файл журнала (параметр «Журнал» в разделе «Параметры для агентов» файла `.claude/CLAUDE.md`; по умолчанию `.claude/docs/progress.md`, в проекте, который ещё не переехал, — `docs/progress.md`). Журнала нет — остановись и предложи `/kit:project-init`. Папка журнала — **папка документов** (`.claude/docs`): в ней `work/`, `archive/` и снимки `visual/`.
2. Запомни `HEAD` до закрытия шага:
   ```
   git rev-parse HEAD
   ```
3. Изменения шага:
   ```
   git -c core.quotepath=false status --porcelain=v1
   ```
   `-c core.quotepath=false` обязателен: без него кириллические пути приходят восьмеричными escape-последовательностями, и `git add` по ним файл не найдёт.
   FILES — файлы, которые изменил этот шаг. Если в статусе есть изменения, которые к шагу не относятся или о которых ты не знаешь, — спроси пользователя через AskUserQuestion, что с ними делать (в этот коммит / оставить как есть). Пути, которые скрипт коммита не пропустит (`.idea/`, секреты, параметр «Не коммитить»), в FILES не включай. Правило «Не коммитить» со `/` (`bitrix/`) — путь от корня проекта: копии шаблонов в `local/templates/…/components/bitrix/…` под него не попадают.
4. **Выкладка: Claude по SSH** — что уедет на сервер, сухой прогон из корня проекта:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/ssh-deploy.js"
   ```
   В выводе есть файлы в «Залить» или «Удалить» — шаг идёт порядком **SSH**: просмотр (п. 3а) → заливка и проверка на сервере (п. 3б) → docs-keeper (п. 3) → коммит и отправка (п. 4–5а). «Нечего заливать» (шаг меняет только документы) — обычный порядок. Код 2 (SSH не задан) — стоп: предложи `/kit:project-init`; код 4 — покажи вывод и стоп.
   В выводе блок «Пропущено — не файл» (код 1: подмодуль или вложенный git-репозиторий) — повтор не поможет: AskUserQuestion «Добавить в «Не выкладывать» (Рекомендую)» / «Остановиться». Добавить — допиши путь в параметр «Не выкладывать» `.claude/CLAUDE.md` (это часть шага, файл — в FILES) и повтори сухой прогон.
   В порядке **SSH** заливка берёт всю папку проекта: изменения, не относящиеся к шагу (п. 3), уедут на сервер вместе с ним, поэтому вариант «оставить как есть» здесь не годится — спроси через AskUserQuestion «В этот шаг (уедут на сервер и в коммит)» / «Остановиться — разберусь с ними».

## 2. Данные для docs-keeper

Собери из разговора:
- `STEP` — ID шага (аргумент команды, если передан), `STATUS`, `SUMMARY` (одна строка: что сделано), `CHECK` (одна строка: как проверено — команды, страницы, ширины, итог; при `✅` обязателен), `NEXT` (ID и одна строка);
- по необходимости `STAGE`, `DECISIONS`, `DOCS`, `BUGS`, `PROD_TODO`, `DEPLOY` (`Файлы`, `Коммит`, `Удалить`, `Проверка`, `Чек-лист`), `NOTES`, `RULES` (с причиной изменения).

`DECISIONS` — по строке на решение: `ГГГГ-ММ-ДД | решение | почему | что отвергли (или —) | пользователь / агент`.
- Решения пользователя — его ответы на вопросы и прямые указания на этом шаге.
- Решения агента — только те, что трудно откатить или что влияют на следующие шаги: выбор подхода, библиотеки, места хранения, отказ от варианта. Не больше 1–3 за шаг; мелкие технические выборы не пиши.
- «Почему» и «что отвергли» — из разговора. Причина решения пользователя неизвестна — спроси его через AskUserQuestion, не придумывай. Решение отменяет прежнее — начни текст с «Заменяет №N» (номер из таблицы «Решения» журнала).

**Входящие ответы** — что пользователь отвечал на вопросы с прошлого закрытия шага (их пишет хук, сжатие контекста их не стирает):
```
node "${CLAUDE_PLUGIN_ROOT}/scripts/decision-inbox.js" --list
```
Запомни N из последней строки «записей: N» (п. 5 уберёт ровно их). Процедурные ответы пропусти: «закрывать?», «начинать?», «отправить?», подтверждения и выбор порядка работы — это не решения. Остальное, чего ещё нет в DECISIONS, добавь: выбранный вариант — решение, его описание («выбрано: …») — основа «почему», «другие» — что отвергли, «кто» — пользователь. Свой ответ («(свой ответ)») — по смыслу: встречный вопрос или уточнение — не решение. Заметки («заметка: …», например «Отчёт заказчику: …» от `/kit:report`) — в `NOTES` дословно.

На шаге снимали или сравнивали снимки (`/kit:visual`) — в NOTES: метки, какое сравнение и итог (совпадает / в пределах шума / что отличается, статусы и ошибки), путь к `report.html`. Снимки `<папка документов>/visual/` в FILES не включай (только локально, скрипт коммита их не пропустит); изменённый `.claude/scripts/visual/pages.json` — включай.

Шаг создал документ в `work/` папки документов (план, спек, чек-лист, материалы) — строка в `DOCS`: `work/<имя> — <о чём> — в работе, этап N`; документ на все этапы (спек, замечания пользователя) — статус `постоянный`; документ стал ненужным — статус `устарел — <чем заменён>`. Документы кладут в `work/` папки документов, а не в её корень и не в другие папки проекта.

### Закрытие этапа — сверка

Шаг закрывает этап, если передан `STAGE` (начинается новый этап), номер этапа в `NEXT` (часть ID до первой `.`) отличается от номера в `STEP` или `NEXT` пустой или `—` при `STEP` вида `N.M`. ID не вида `N.M` (`Р6а`) — только по `STAGE`. Тогда до docs-keeper сверь задуманное со сделанным:

1. **С чем сверять.** Раздел «Документы» журнала: строки `work/…` со статусом `в работе, этап <номер закрываемого этапа>` — спек (разделы «Требования», «Критерии готовности»), план (задачи). Пункты — требования Т-N и критерии или задачи плана. Таких документов нет — пункты только из таблицы этапа: шаги не `✅` (⏳, ⏸) — расхождения; все `✅` — «расхождений нет», без вопросов.
2. **Таблица сверки** — в ответе пользователю: `| Пункт | Шаги | Итог |`, итог — сделано / частично / нет / не просили (сделано сверх задуманного). Опирайся на таблицу этапа и коммиты; не уверен — «частично» с пояснением, не «сделано».
3. **Расхождения** (частично, нет) — один AskUserQuestion, список — в тексте вопроса: «В «Баги на потом» (Рекомендую)» / «На следующий этап» / «Не делаем — решением»; разное для разных пунктов — через «Другое». «В Баги» — строки `BUGS`; «Не делаем» — строки `DECISIONS` (почему — из ответа; нет причины — спроси); «На следующий этап» — в блок `RECONCILE`.
4. **Итог** — блок для docs-keeper (строка под таблицей этапа):
   ```
   RECONCILE: ГГГГ-ММ-ДД | этап N | сверено с: <документы или «таблица этапа»> | пунктов M, сделано K | расхождения: <пункт — куда; …> или нет | на следующий этап: <пункты> или —
   ```

### Закрытие этапа — архив

Шаг закрывает этап (условие — в «Сверке» выше) — прочитай раздел «Документы» журнала: строки `work/…` со статусом `в работе, этап <номер закрываемого этапа>` — кандидаты в архив (`постоянный` кандидатом не бывает). Нет — ничего не спрашивай. Есть — AskUserQuestion, список файлов — в тексте вопроса: «Все в archive/ (Рекомендую)» / «Оставить в work/»; часть — через «Другое». Оставленные в `work/` — строка `DOCS` со статусом `в работе, этап <номер следующего этапа>`: при закрытии следующего этапа их предложат снова. Выбранное в архив перенеси обычным перемещением, без git:
```
New-Item -ItemType Directory -Force '<папка документов>/archive' | Out-Null
Move-Item -LiteralPath '<папка документов>/work/<имя>' -Destination '<папка документов>/archive/<имя>'
```
Папка-документ (`work/design/`) переносится целиком; имя в `archive/` занято — спроси пользователя, файлы не перезаписывай. В `DOCS` — `archive/<имя> (было work/<имя>) — <о чём> — готово, этап N (ГГГГ-ММ-ДД)`; в FILES — **оба** пути, старый и новый: скрипт коммита добавит их одной командой `git add -A -- …`, и git увидит переименование — коммит шага остаётся одним. Документ не был в git (`git ls-files <старый путь>` пусто) — в FILES только новый путь: `git add` по неотслеживаемому старому пути остановил бы скрипт коммита.

`COMMITS` — хеши прошлых шагов из истории git:
```
git log --format="%h %s" -50
```
ID коммита — часть заголовка до первого `: `. Передай пары `ID=хеш` за последние шаги (у одного ID несколько коммитов — все через запятую). docs-keeper заполнит только пустые ячейки «Коммит».

## 3. docs-keeper

Порядок **SSH** (п. 1.4) — этот пункт выполняется после п. 3б: CHECK — с итогом заливки («Залито и сверено…») и проверки на сервере; блок DEPLOY — `Файлы:` — строка «DEPLOY Файлы:» из вывода `ssh-deploy.js --go` без этих слов, `Проверка:` — как проверено на сервере; `Коммит` — не передавай: это коммит шага, ячейка останется пустой, скрипты найдут его по ID шага, а хеш впишет следующий `/kit:step-done` через COMMITS.

Вызови агента `kit:docs-keeper` (Agent, subagent_type `kit:docs-keeper`) с блоками:
```
STEP: …
STATUS: …
SUMMARY: …
CHECK: …
NEXT: …
COMMITS: …
<необязательные блоки>
```
Дождись отчёта: в нём «Сейчас», цитаты добавленных строк и список изменённых файлов.

**Сверь отчёт с файлом** (Grep по журналу), не доверяя отчёту на слово: строка шага `STEP`, каждый номер багов из `BUGS` (с новым статусом), каждая строка `DECISIONS` (номер из отчёта и начало текста решения), каждая строка `DOCS`, строка «Сверка …» из `RECONCILE` под таблицей этапа, при `✅` — строка `- [x] <STEP>` в плане этапа из реестра (если в плане есть чек-лист; изменённый план — в FILES). Чего-то нет в файле — вызови docs-keeper ещё раз только с недостающим и не переходи к коммиту, пока файл не сойдётся с блоками. В отчёте «не записано: нет "почему"» — допиши причину (из разговора или спроси пользователя) и передай только эти строки.

**Журнал по частям** (рядом с журналом есть папка `journal/`): решения сверяй в `journal/decisions.md`, баги — в `journal/bugs.md`, заметки — в `journal/reference.md`. Шаг закрывает этап — после сверки перенеси раздел этапа в его файл:
```
node "${CLAUDE_PLUGIN_ROOT}/scripts/journal-split.js" --stage <N>
```
Код 2 — стоп, покажи ошибку (скрипт ничего не записал). Код 0 — `journal/stages/stage-NN.md` и журнал — в FILES. Журнал в одном файле (папки `journal/` нет) — ничего не переносится.

## 3а. Просмотр перед коммитом

Параметр «Коммит: сразу» — пункт пропусти (порядок **SSH**: список из п. 1.4 — в чат, затем сразу п. 3б). Нет параметра или любое другое значение — коммит только после просмотра пользователем (с 2.15.0):

1. **Покажи изменения.** Есть инструмент `mcp__ccd_view__show_pane` (приложение Claude; инструменты панелей бывают отложенными — загрузи через ToolSearch `select:mcp__ccd_view__show_pane,mcp__ccd_view__close_pane,mcp__ccd_view__get_layout`) — сначала `mcp__ccd_view__get_layout`: запомни, есть ли `diff` в `open_panes`; затем открой панель изменений: `pane` — `diff`, `diff_scope` — `uncommitted`. Инструмента нет (терминал, IDE) — покажи в чате `git -c core.quotepath=false diff --stat -- <пути>` и список новых файлов.
2. **Коротко в чате:** что сделано (SUMMARY), файлы шага с числом добавленных и удалённых строк, заголовок будущего коммита; как спросить: клик по строке в панели, комментарий, отправка всех комментариев — Ctrl+Enter.
3. **Вопрос** через AskUserQuestion: «Коммитить» (задан «Удалённый репозиторий» — «Коммитить и отправить») / «Есть вопросы — оставлю комментарии» / «Не коммитить пока». Ответ — процедурный, в DECISIONS не идёт. Порядок **SSH** — вместо «Коммитить» вариант «Залить на сервер» (в его описании: после проверки на сервере — коммит, а при заданном «Удалённом репозитории» — и отправка; без нового вопроса), вместо «Не коммитить пока» — «Не заливать пока»; перед каждым таким вопросом — свежий сухой прогон `ssh-deploy.js` (после правок по комментариям список мог измениться) и в чате — что уедет: сервер, «Залить (N)», «Удалить (M)».
4. **Комментарии** приходят сообщением: файл, строка, текст. Ответь на каждый. Правишь по ним код — это часть шага: проверь заново, как положено по правилам проекта; изменились SUMMARY или CHECK — передай docs-keeper только исправленную строку шага (в порядке **SSH** docs-keeper ещё не вызывался — ничего не передавай: исправленное уйдёт в его вызов после п. 3б). Затем снова п. 1.
5. Просят не коммитить какой-то файл — убери его из путей коммита: он останется незакоммиченным, скажи об этом в ответе. В порядке **SSH** такой файл уезжает на сервер всё равно (заливка берёт папку проекта) — скажи об этом; не заливать его можно, только вернув его к прежнему виду до заливки (с согласия).
6. «Не коммитить пока» — остановись: правки и журнал остаются, входящие не трогай. Пользователь потом скажет коммитить — продолжи с п. 3а, docs-keeper заново не вызывай. «Не заливать пока» (порядок **SSH**) — так же, но docs-keeper ещё не вызывался: продолжи с п. 3а, а docs-keeper вызови после п. 3б, как обычно.
7. **Закрой панель**, которую открыл, — `mcp__ccd_view__close_pane` с `pane` — `diff`: после «Не коммитить пока» сразу, после «Коммитить» (в порядке **SSH** — «Залить на сервер») — когда коммит (и отправка) прошли или остановились. Пока идёт разговор по комментариям — не закрывай. По п. 1 панель уже была открыта — не закрывай: её открыл пользователь.

## 3б. Заливка по SSH и проверка на сервере

Только порядок **SSH** (п. 1.4), после ответа «Залить на сервер» (при «Коммит: сразу» — сразу после п. 2).

1. **Заливка** — из корня проекта:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/ssh-deploy.js" --go
   ```
   Код 0 — дальше. Код 1 (часть не вышла: не записан, md5 не совпал, на сервере нет `base64` или `md5sum`) или 3 (нет подключения, обрыв, вышло время) — покажи причину пользователю; повтор безопасен (та же заливка даёт тот же результат) — AskUserQuestion «Повторить заливку» / «Остановиться». Код 1 только из-за «Пропущено — не файл» — повтор не поможет: как в п. 1.4, «Добавить в «Не выкладывать» (Рекомендую)» / «Остановиться». Остановились — коммита нет, правки остаются. Код 2 или 4 — покажи вывод и стоп.
2. **Проверка на сервере** — по правилам проекта: «Код пишет: Claude» — проверь сам (страница, десктоп и мобильная ширина — что положено); «пользователь» — AskUserQuestion «Работает» / «Не работает — опишу».
3. **Не прошла** — правка (это часть шага), локальные проверки, затем снова п. 3а: просмотр → заливка → проверка. Ответ «Не работает» и правки — не решения, в DECISIONS не идут.
4. **Прошла** — п. 3 (docs-keeper с итогом заливки и проверки), затем п. 4 без нового вопроса: ответ «Залить на сервер» включает коммит и отправку.
5. **Отказ от шага** — проверка не прошла, а пользователь просит откатить, а не править: сначала запомни пути из вывода `--go` («Залить» и «Удалить»), затем верни их локально к прежнему виду (с согласия: правки — `git checkout -- <путь>`, новые файлы шага — удалить, удалённые — вернуть из `HEAD`) и верни сервер теми же путями:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/ssh-deploy.js" --go -- <пути>
   ```
   Что есть на диске — зальётся в прежнем виде, чего нет — удалится на сервере. Просто откатить файлы локально нельзя: после этого скрипт скажет «Нечего заливать», а на сервере останется отвергнутая версия. Коммита у шага нет, docs-keeper не вызывай; скажи пользователю, что сервер возвращён.

## 4. Коммит

Один коммит шага — скриптом, одной командой **Bash** (не PowerShell) из корня проекта. Сообщение — heredoc с кавычками `<<'KIT_MSG'`: Bash вставляет текст как есть, `$`, обратные кавычки и `\` не подставляются, перепечатки нет.
```
node "${CLAUDE_PLUGIN_ROOT}/scripts/kit-commit.js" -- "<путь1>" "<путь2>" … <<'KIT_MSG'
<STEP>: <суть шага одной строкой>

<CHECK дословно>

<строка Co-Authored-By>
KIT_MSG
```
- Пути: файлы шага из п. 1.3, файлы из отчёта docs-keeper, старые и новые пути документов, перенесённых в архив; каждый — отдельным аргументом в двойных кавычках, как их выводит `git -c core.quotepath=false status --porcelain=v1`.
- Строка `Co-Authored-By: …` — из твоих собственных системных инструкций о подписи коммитов, дословно; таких инструкций нет — строки и пустой строки перед ней нет.
- Скрипт сам проверяет запрещённые пути и секреты (`secret-scan.js`), добавляет только эти пути, делает один коммит и сверяет сообщение коммита с поданным побайтно.

Код 0 — коммит сделан. Код 1 — остановила проверка путей или секретов: покажи вывод пользователю (значения замаскированы); индекс скрипт оставил как есть — после исправления запусти ту же команду. Код 2 — ошибка (git, хук, неверный путь): покажи вывод, коммита нет. Код 3 — коммит есть, но самопроверка нашла расхождение: покажи вывод, историю не чини.

## 5. Проверка

```
git rev-list --count <HEAD из п. 1.2>..HEAD
git -c core.quotepath=false status --porcelain=v1
```
- код скрипта 0, новых коммитов ровно **1**;
- файлов шага в статусе больше нет.

Сообщение побайтно сверил скрипт (строка «сообщение совпало с поданным»); заголовок для ответа пользователю — первая строка его отчёта.

Проверка прошла, а в п. 2 входящих было N > 0 — убери разобранные (пришедшие позже останутся до следующего шага):
```
node "${CLAUDE_PLUGIN_ROOT}/scripts/decision-inbox.js" --clear N
```

Что-то не так (код скрипта не 0, 0 или 2 коммита, лишние файлы) — входящие не трогай и сообщи пользователю, что именно и какие команды это показали. Историю сам не чини: никаких `reset`, `amend`, `rebase`. Сам коммит в обход скрипта не делай ни при каких обстоятельствах: сообщи о проблеме и остановись.

## 5а. Отправка в удалённый репозиторий

Только если в «Параметрах для агентов» задан `Удалённый репозиторий` (не `—`) и проверка п. 5 прошла. `<имя>` — значение параметра, `<ветка>` — вывод `git symbolic-ref --short HEAD`. Параметра нет — пункт пропусти: коммит остаётся только локально.

1. Первая отправка — ветки там ещё не было:
   ```
   git rev-parse --verify --quiet refs/remotes/<имя>/<ветка>
   ```
   Код не 0 — сначала проверь всю историю ветки на секреты и запрещённые пути:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/secret-scan.js" --history
   ```
   Код 1 — сразу не отправляй:
   - среди находок есть секреты (всё, кроме «запрещённый путь»: пароль, вебхук, ключ) — не отправляй: покажи находки (значения замаскированы, впереди — хеш коммита) и скажи, что секрет остался в истории: убрать его из истории или начать новый репозиторий с текущего состояния — решает пользователь; историю сам не переписывай;
   - находки только «запрещённый путь» (в истории были файлы вроде `.idea/…` или `docs/visual/.gitignore`) — покажи список и спроси через AskUserQuestion: «Отправить как есть» / «Не отправлять». В вопросе предупреди: `.settings.php`, `.settings_extra.php`, `dbconn.php`, `.env`, `*.key`, `*.pem` обычно хранят пароли и ключи — если такие есть в списке, рекомендуй «Не отправлять».

   Код 2 — не отправляй, покажи ошибку.
2. Отправка:
   ```
   git push -u <имя> HEAD
   ```
   Откроется окно входа (Git Credential Manager) — входит пользователь; пароли и токены не вводи и не вписывай в адрес.
3. Не вышло:
   - `rejected`, `fetch first`, `non-fast-forward` — на удалённом есть коммиты, которых здесь нет (работали с другого компьютера, или репозиторий создан не пустым): стоп, скажи пользователю и спроси через AskUserQuestion, что делать. `--force`, `pull`, `rebase` и слияния — только после его явного выбора;
   - нет сети, вход не выполнен, репозиторий не найден, вышло время — коммит остаётся локально: причина — одной строкой (последняя строка вывода git). Не повторяй: неотправленное уйдёт со следующим шагом, а при старте сессии хук напомнит.

## 6. Ответ пользователю

Коротко: хеш и заголовок коммита, отправлен ли он (`<имя>/<ветка>` или почему нет), раздел «Сейчас» из отчёта docs-keeper. Хеш попадёт в журнал при следующем `/kit:step-done` — запоминать его не нужно.

Записаны решения агента — отдельным списком «Решения агента на этом шаге (можно возразить)»: номер, решение, почему. Нет — списка не выводи. Пользователь возразил — новое решение («Заменяет №N») запишет следующий `/kit:step-done`.
