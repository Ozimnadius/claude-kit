# Инициализация проекта (kit)

Работай в корне проекта, без `cd`. Все вопросы — только через AskUserQuestion; вариант, найденный разведкой, ставь первым с пометкой «(Рекомендую)». Ничего не перезаписывай: существующие файлы только дополняются, и только после согласия пользователя.

Шаблоны — в `${CLAUDE_PLUGIN_ROOT}/skills/project-init/templates/`. Перед шагами про PhpStorm, Битрикс и SSH прочитай справки `${CLAUDE_PLUGIN_ROOT}/skills/project-init/reference/phpstorm.md`, `${CLAUDE_PLUGIN_ROOT}/skills/project-init/reference/bitrix.md` и `${CLAUDE_PLUGIN_ROOT}/skills/project-init/reference/ssh.md`.

## 1. Разведка (только чтение)

- **git:** есть ли `.git`; `git config --get core.autocrlf`, `git config --get core.quotepath`; число коммитов (`git rev-list --count HEAD`) и первый коммит; `git remote -v` — имя и адрес удалённого репозитория (логин или токен в адресе, если есть, пользователю не показывай — маскируй).
- **Файлы kit:** `.claude/CLAUDE.md` (есть ли раздел `## Параметры для агентов`), журнал и план выкладки (`.claude/docs/progress.md`, `.claude/docs/deploy-prod.md`), `.claude/.htaccess`, `.gitignore` (игнорирует ли git папку документов: `git check-ignore -q .claude/docs/progress.md` — код 0 значит игнорирует; шаблоны до 2.3.0 игнорируют `/.claude/*`), проектные копии старых агентов kit `.claude/agents/docs-keeper.md` и `.claude/agents/git-keeper.md` (с 3.0.0 у kit агентов нет), служебные файлы Claude Code в `.claude/` (`settings.local.json` и т. п.).
- **Формат kit 3.0** — правило хука в контексте «Журнал или параметры в старом формате (<признаки>) — …»: признаки через «; », каждый — пункт переезда (п. 4.7). Правила нет — формат текущий, переезда нет.
- **Старая раскладка** — параметр «Журнал» указывает в `docs/` или есть `docs/progress.md`: состав `docs/` (`git -c core.quotepath=false ls-files docs` и неотслеживаемое — например `docs/visual/`), `docs/.htaccess`; переезд — п. 4.7.
- **Битрикс:** `bitrix/`, `local/`, `local/templates/`, `urlrewrite.php`, `.settings.php` — признаки режима «bitrix»; стоят ли скиллы Битрикса — `.claude/skills/bitrix-framework/SKILL.md` (п. 4.6). Кандидаты рабочих папок в `bitrix/` (вопрос «Где правят файлы») — если `bitrix/` есть в проекте: `bitrix/templates/<шаблон>` (кроме шаблонов ядра — `.default`, `landing24`, `learning`, `mail_user`, `bitrix24` и др. — и шаблонов с копией `local/templates/<шаблон>`), `bitrix/components/<пространство>` (кроме `bitrix`), `bitrix/js|css/<пространство>.*` того же пространства, `bitrix/php_interface/init.php`, если нет `local/php_interface/init.php`; нет `bitrix/` в проекте — их печатает `ssh-probe.js` (раздел «SSH»). Параметр «Не коммитить» с `bitrix/ (кроме …)` — уже выбранные рабочие папки.
- **Система Мэтта:** параметр «Система Мэтта»; стоит ли плагин на проект — `node "${CLAUDE_PLUGIN_ROOT}/scripts/matt-skill.js" --status` (печатает `установлен <версия>, включён` / `установлен <версия>, выключен` / `не установлен`).
- **PhpStorm** (только читать; исключения в `deployment.xml` дописывает только `phpstorm-exclude.js`, п. 4.0):
  - `.idea/deployment.xml` — `autoUpload`, `autoUploadExternalChanges`, `serverName`, список `excludedPath`;
  - `.idea/webServers.xml` — Grep с `-o` по `rootFolder="[^"]*"|url="[^"]*"` — выводить только совпавшую часть; файл целиком не открывать. Из `rootFolder` (например `/www/alpha.example.com`) — догадка домена `alpha.example.com`;
  - `.idea/watcherTasks.xml` — включённые File Watchers (`name`, `isEnabled`).

## 2. Вопросы

Все вопросы — только через AskUserQuestion: не больше 4 вопросов за вызов, в каждом 2–4 варианта; «Другое» добавляется само и не считается за вариант.

Первый вызов (2 вопроса):
1. Режим: 1С-Битрикс / общий.
2. Окружение — один сервер, куда идут шаги и где их проверяют: «Прод» / «Дев — перенос на прод потом, целиком, вне kit». Варианта «дев + прод» нет (с 2.17.0). Существующий раздел с `Окружение: дев+прод` (старый формат) — первым «Дев», если «Выкладка» — `вручную; дев — PhpStorm Always`, иначе «Прод»; новые «Окружение», «Выкладка» и `—` у второго сервера — пункты переезда в плане на согласие (п. 4.7).

Как файлы попадают на сервер — не здесь, а после SSH (раздел «Выкладка» ниже): вариант «Claude по SSH» зависит от SSH.

Второй вызов — не больше 4 вопросов, в каждом 2–4 варианта:
1. Адрес сервера (прода или дева — по окружению): `https://<домен из rootFolder>` (Рекомендую) и `https://www.<домен>`; догадки нет — «Сервера пока нет» / «Введу адрес в «Другое»». Параметр — «Прод» или «Дев» по окружению, второй — `—`.
2. Задача: «Без задачи» / «Есть — номер и название в «Другое»».
3. Исключения деплоя сверх обязательных (мультивыбор, 3 варианта): «`.gitignore`», «`local/modules`», «Больше ничего». В тексте вопроса: `.idea`, `.git` и `.claude` исключаются всегда (документы из `.claude` — по вопросу «Документы на сервере», раздел «Выкладка») — `.claude` закрывает правила, документы `.claude/docs` (журнал, планы, снимки `/kit:visual` из-под админа), скрипты `/kit:server`, `settings.local.json` и `.claude/worktrees` (git worktree Claude Code — полная копия сайта); служебные папки superpowers (`.superpowers`, `.worktrees`, `docs/superpowers`) хук тоже исключает всегда; уже исключённые в `deployment.xml` — перечисли. Выбранное идёт в «Не выкладывать» и в `--also` для `phpstorm-exclude.js`.
4. Только режим «bitrix» и если в `watcherTasks.xml` есть включённые вотчеры: оставить / убрать (вотчеры срабатывают и на правки Claude — см. справку phpstorm.md).

Третий вызов — удалённый репозиторий, скиллы Битрикса и система Мэтта:
1. Удалённый репозиторий: «Удалённый репозиторий для работы с другого компьютера — git проекта с журналом отправляется туда после каждого шага». Варианты: найденный разведкой remote (`origin` — первым с «(Рекомендую)»; параметр `Удалённый репозиторий` уже задан — он первым), «Создам закрытый репозиторий — адрес впишу в «Другое»», «Не нужен». В тексте вопроса: репозиторий создаёт пользователь (GitHub, GitLab или сервер, где разрешает работодатель) закрытым и **пустым** — без README и лицензии: в непустом уже есть своя ветка (на GitHub — `main`), проект ляжет рядом с ней, а `git clone` на другом компьютере принесёт не его; вход — он же (окно входа откроется при проверке репозитория). Параметр уже задан и такой remote есть — вопрос не задавай.
2. Только режим «bitrix», при каждом запуске — «Ставить скиллы Битрикса?»: «Да (Рекомендую)» — свежие версии из репозиториев (`bitrix-skills.js`), уже поставленные обновляются до последних; «Нет» — не ставить, уже поставленные не трогать. В тексте вопроса: 46 скиллов (bxmaximum/bitrix-framework-skills без `bitrix24-*` и bitrix-tools/best-practice), стоят ли уже (разведка); в git их не кладём, между запусками `/kit:project-init` они не обновляются; описания скиллов занимают контекст каждого хода. Ответ — п. 4.6.
3. При каждом запуске, любой режим — «Вести проект по системе Мэтта Покока?»: «Да — большой проект» / «Нет»; параметр «Система Мэтта» уже «да» — «Да — большой проект» первым. Без «(Рекомендую)»: решает объём работы, который знает пользователь. В тексте вопроса: для больших проектов — грилинг (вопросы до кода) с глоссарием и ADR, карта решений, спек, тикеты; каждый тикет делается в свежей сессии, общая сессия принимает их через `/kit:step-done`; «Да» — плагин mattpocock-skills ставится на этот проект, superpowers в нём выключается, нужен перезапуск сессии; сейчас — строка `--status` из разведки. Ответ — п. 4.6а.

Сразу после вопросов (до плана на согласие), если адрес сервера задан, — в любом режиме:

Скрипт только читает. Версию PHP и путь `C:\OSPanel\modules\PHP-X.Y\php.exe` из вывода используй везде, где шаблоны ждут `{{ВЕРСИЯ_PHP}}`/`{{PHP_EXE}}`. Модуля нет в OSPanel или версия скрыта — спроси пользователя (или узнай после SSH-разведки ниже: `ssh-probe.js` печатает версии PHP на сервере; либо через `/kit:server`, `echo PHP_VERSION;`); параметр «PHP» — путь к `php.exe` или `—`. Параметр в существующем `.claude/CLAUDE.md` уже задан и отличается от найденного — меняй только с согласия.

### SSH — после site-probe, до плана на согласие

Для сервера окружения, если его адрес задан. Справка — `reference/ssh.md`.

1. Псевдонимы из `~/.ssh/config` и файлов, которые он подключает строками `Include` (сначала Grep `-i` по `^\s*Include\s+\S` — строки целиком, в них только пути: относительный путь — от `~/.ssh/`, `~` — домашняя папка, маски — через Glob; вложенные `Include` — до глубины 2) — только строки `Host`, `HostName`, `User`: Grep `-i` по `^\s*(Host|HostName|User)(\s*=\s*|\s+)\S` — строки целиком, без `-o` (в этих строках секретов нет; `IdentityFile` и прочее не попадают); шаблоны с `*`, `?`, `!` в варианты не брать; ключи и другие файлы `~/.ssh` не открывай (файлы из `Include` — только ради этих строк). Вопрос через AskUserQuestion, по вопросу на сервер, до 3 псевдонимов: в существующем разделе параметров `SSH …` уже задан — первым он с «(Рекомендую)» (решение пользователя важнее догадки); псевдоним, у которого `HostName` совпал с доменом сервера, — следом с пометкой «HostName совпал с доменом» (параметра нет — первым с «(Рекомендую)»); последний вариант — «SSH нет»; `user@host` — через «Другое».
2. Разведка (только чтение, одно подключение):
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/ssh-probe.js" <хост> --url <адрес сервера> [--php X.Y] [--dir <rootFolder без ведущего «/»>]
   ```
   X.Y — версия PHP из site-probe; `--dir` — `rootFolder` из `.idea/webServers.xml` (разведка п. 1, например `www/site`; ведущий `/` в Bash переписывает Git Bash). Скрипт ищет папку по домену из адреса, по `--dir` и перебором `~/www/*`, `/home/bitrix/ext_www/*` — папка бывает названа не по домену.
   - Код 3 — не пустил, причина — в выводе. `Host key verification failed` без строки `REMOTE HOST IDENTIFICATION HAS CHANGED` (новый сервер) — попроси пользователя один раз войти самому (`ssh <хост>`, ответить `yes`) и повтори. Есть `REMOTE HOST IDENTIFICATION HAS CHANGED` — стоп: отпечаток сервера сменился (переустановка сервера или подмена) — скажи пользователю сверить отпечаток у хостера; старую запись удаляет он сам (`ssh-keygen -R <хост>`), Claude — нет; «войти и ответить `yes`» здесь не годится; повтори, когда он ответит, что отпечаток сверен и запись исправлена, а до тех пор параметр `—`. Остальные причины — параметр `—`, а шаги из справки `reference/ssh.md` — в итог пользователю.
   - Код 1 — скрипт разведки не доработал (вывод неполный, причина — в выводе ошибок): покажи причину пользователю; найденное используй как в п. 3, недостающее спроси.
   - Код 4 — хост недопустим (пробел, `-` в начале, порт): переспроси; порт — только через `~/.ssh/config`.
3. Код 0: папка сайта — единственная строка `Папка: … [bitrix]` (режим bitrix; в общем режиме — единственная найденная); найдено несколько, а с пометкой `[по адресу]` или `[по --dir]` — одна, — она. Иначе (несколько или ни одной) — вопрос: найденные — вариантами (с пометкой — первыми, с «(Рекомендую)»), свой путь — через «Другое». Строки под папкой («где правят — кандидаты», «шаблоны ядра» — их не предлагай) — для вопроса «Где правят файлы». PHP — строка с `[совпадает]` → «PHP на сервере»; такой нет или версия сайта неизвестна — вопрос со списком найденных версий (выбранная версия идёт и в параметр «PHP», если site-probe версию не нашёл).
4. Параметры: `SSH прод` или `SSH дев` (по окружению) — `<хост>:<папка>`, у второго сервера — `—`; `PHP на сервере: <путь>`; SSH нет — `—`. Уже заданные значения меняй только с согласия.
5. «SSH нет»: режим bitrix с адресом — скажи пользователю, что `/kit:server` будет работать через файл-канал `kit-exec.php` (при первом запуске он войдёт администратором во встроенном браузере Claude), а строка `/kit-exec.php` попадёт в `.gitignore`; иначе выполнить на сервере будет негде — покажи раздел «Как включить SSH у хостинга» справки `reference/ssh.md`.

### Выкладка — после SSH, до плана на согласие

Окружение и SSH уже известны — вопрос «Как файлы попадают на сервер» (на сервер окружения — прод или дев): «PhpStorm Always» / «Claude по SSH» / «вручную списком файлов». «Claude по SSH» — только если SSH-разведка этого сервера прошла (код 0) и параметр `SSH …` задан; иначе варианта нет. В описании варианта: правки шага заливает `/kit:step-done` после просмотра (скрипт `ssh-deploy.js` — всё, что изменилось с последней заливки, и удаления), затем проверка на сервере и коммит; автозаливка PhpStorm остаётся выключенной.

Первым с «(Рекомендую)» — значение параметра «Выкладка» из существующего раздела (старое `вручную; дев — PhpStorm Always` — как «PhpStorm Always»); иначе по разведке: `autoUpload="Always"` / `myAutoUpload` = `ALWAYS` в `.idea/deployment.xml` — «PhpStorm Always»; нет, а SSH есть — «Claude по SSH»; иначе «вручную списком файлов». Выбрано «Claude по SSH» или «вручную», а в `deployment.xml` Always — автозаливку выключат в п. 4.0 и в конце не включат (п. 4.8): скажи об этом в плане на согласие.

Следующим вызовом — при «PhpStorm Always» и «Claude по SSH» — вопрос «Документы на сервере»: «Нет — `.claude` целиком не выкладывается» / «Да — документы уезжают на сервер». Первым с «(Рекомендую)» — значение параметра из существующего раздела, иначе «Нет». В тексте вопроса: «да» — на сервер уезжают `.claude/docs` (журнал, планы; без снимков `visual`), `.claude/CLAUDE.md` и `.claude/.htaccess`, например чтобы открывать их по FTP: при «PhpStorm Always» — автозаливкой (остальное в `.claude` — `scripts`, `skills`, `settings.local.json`, `kit-inbox.jsonl`, `worktrees` — хук исключает поимённо), при «Claude по SSH» — заливкой `/kit:step-done` перед коммитом шага (`ssh-deploy.js --docs`, `.htaccess` — первым; остальное в `.claude` не уезжает); снаружи папку закрывает `.htaccess`. При «вручную» вопрос не задавай: ручная выкладка `.claude` не везёт, параметр — `нет`.

### Где правят файлы — только режим «bitrix», после SSH, до плана на согласие

По шаблону `bitrix/` в git не попадает: правки там не коммитятся, и `ssh-deploy.js` их не заливает. Если правят прямо в `bitrix/`, эти папки — рабочие, им нужны исключения (справка `reference/bitrix.md`, «Рабочие папки в `bitrix/`»).

Вопрос «Где ещё правят файлы — кроме `local/` и публичной части?» (мультивыбор). Варианты — кандидаты из строки «где правят — кандидаты в bitrix/» вывода `ssh-probe.js` (выбранной папки сайта), а если `bitrix/` есть в проекте — из разведки (п. 1): до 3 вариантов (больше — объедини: «компоненты и js/css решения `<пространство>`»), последний — «Больше нигде». Первым с «(Рекомендую)» — действующий `bitrix/php_interface/init.php`, если он среди кандидатов (в описании: `local/php_interface/init.php` на сайте нет — свои обработчики и подключения пишут сюда); папки из «Не коммитить: bitrix/ (кроме …)» существующего раздела — тоже первыми. В тексте вопроса: выбранное уйдёт в git (исключения в `.gitignore` и «Не коммитить») и на сервер — как остальные файлы; после обновления ядра или решения эти папки скачивают с сервера заново; шаблоны с копией в `local/templates` правят в копии — их здесь нет. Кандидатов нет (SSH нет и `bitrix/` в проекте нет) — вопрос «Правят ли файлы прямо в `bitrix/`?»: «Нет — только `local/` и публичная часть» (Рекомендую) / «Да — папки впишу в «Другое»».

Ответ «Больше нигде» или «Нет» — `/bitrix/*` без исключений. Иначе — исключения в `.gitignore` (п. 4.1), «Не коммитить» и строка «Рабочие папки в `bitrix/`» в разделе «Код» правил (п. 4.3); папок нет в проекте — скачать до коммита шага 4.8 (справка, «Файлы»).

## 3. План на согласие

  ```
  claude plugin install mattpocock-skills@claude-plugins-official --scope project
  ```
  Плагин стоит, но выключен (`установлен …, выключен`) — вместо установки:
  ```

  ```
  Затем superpowers в этом проекте выключается:
  ```
  claude plugin disable superpowers@claude-plugins-official --scope project
  ```
  Superpowers не установлен или уже выключен — `disable` ответит ошибкой (справка `--help` её текст и код не описывает): это не сбой, иди дальше. Сверка: `node "${CLAUDE_PLUGIN_ROOT}/scripts/matt-skill.js" --status` → `установлен …, включён`. Плагин не скачался (сеть) — причину пользователю; параметр всё равно `да`, при старте сессии хук напомнит запустить `/kit:project-init` ещё раз.
- **«Нет», а параметр был «да».** Сначала `--status`: плагин Мэтта не установлен или уже выключен — `disable` для него не вызывай (ответит ошибкой), а `enable` superpowers выполни в любом случае. Мэтт выключается, superpowers возвращается (superpowers не установлен — ошибка `enable` не сбой, иди дальше):

  Глоссарий, ADR и папки `work/<тема>/` не трогай. «Нет» и параметр уже `нет` (или его не было) — ничего не меняется.
- Строку итога (что поставлено, включено или выключено) — в `SUMMARY` шага 4.8; плагины менялись — в итог пользователю (раздел 5): перезапустите сессию.

### 4.7 Переезд на формат kit 3.0 — только если в контексте есть правило хука о старом формате

kit 3.0 понимает один формат проекта; старый переводится одним запуском. Каждый признак из правила хука (п. 1) — строка плана на согласие (п. 3). Отказ — kit 3.0 в проекте шаги не закрывает: хук при каждом старте снова предложит переезд, скрипты закрытия шага отвечают кодом 2. Правки `.claude/CLAUDE.md`, журнала и `journal/decisions.md` покажи; пункты — по порядку:
1. **журнал не в .claude/docs** — перенос `docs/` в `.claude/docs` (подраздел ниже).
2. **журнал одним файлом** — на части, без отдельного вопроса (в журнале остаются «Сейчас», оглавление этапов, «Документы», «Прод: не забыть» и текущий этап, остальное — в `journal/`, текст переносится строка в строку):
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/journal-split.js" --migrate
   ```
   Код 2 — покажи ошибку (журнал не тронут) и остановись: переезд без частей не закончить. Код 0 — журнал и новые файлы `journal/…` — в пути коммита шага 4.8.
3. **нет столбца «Как проверено»** — в таблицу текущего этапа (последний раздел `## Этап N` журнала) вставь столбец «Как проверено» после «Что сделано»: в шапку, в разделитель и пустую ячейку в каждую строку. Столбец «Коммит», если он есть, остаётся: kit 3.0 его не заполняет.
4. **старая таблица решений** — под последней таблицей `journal/decisions.md` допиши пустую строку, строку `С kit 2.8 — с обоснованием:`, пустую строку и шапку `| № | Дата | Шаг | Решение | Почему | Что отвергли | Кто |` с разделителем; старые строки не трогай.
5. **Окружение: дев+прод** — новое значение — ответ на вопрос «Окружение» (раздел 2): `прод` или `дев`; адрес и SSH — у этого сервера, у второго — `—`.
6. **Выкладка: вручную; дев — PhpStorm Always** — `Окружение: дев` и `Выкладка: PhpStorm Always` по ответам на вопросы «Окружение» и «Как файлы попадают на сервер» — это и есть подтверждение.
7. Строки «Код пишет» и «Коммит» — убрать по п. 4.3.

Проверка после переезда — хук из корня проекта: `echo '{}' | node "${CLAUDE_PLUGIN_ROOT}/scripts/session-start.js"` — в выводе нет строки «в старом формате»; есть — доделай пункт по признаку из неё.

#### Перенос `docs/` в `.claude/docs`

Только если разведка нашла журнал в `docs/`. Строго по порядку, каждый пункт после предыдущего:
1. **Исключения.** `node "${CLAUDE_PLUGIN_ROOT}/scripts/phpstorm-exclude.js" --check` — код 0 (нет `deployment.xml` — тоже можно). Код 1 — сначала п. 4.0: иначе перенесённое уехало бы на сервер.
2. **`.gitignore`.** `git check-ignore -q .claude/docs/progress.md`: код 0 (игнорируется) — покажи и с согласия допиши строки шаблона `!/.claude/docs/`, `!/.claude/docs/**`, затем `/.claude/docs/visual/` (после строк-исключений; строку `/docs/visual/`, если есть, замени ею) и проверь снова — нужен код 1. Без этого скрипт коммита не добавит новые пути (`git add` отказывает для игнорируемых), а старые пропали бы из индекса.
3. **Старые копии на сервере.** Адрес сервера известен (автозаливка или ручная выкладка `docs/`) — **до** переноса:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/check-closed.js" <адрес> --dirs docs
   ```
   Файлы с 403/401 лежат на сервере — в DEPLOY `Удалить` на шаге 4.8 (путь от корня сайта, «переехал в `.claude/docs`, на сервере не нужен»); удаляет `/kit:server` через `delete-list.php` (копия, сухой прогон, согласие) или пользователь. «ОТКРЫТ» — стоп и разбор, как в п. 4.0.
4. **Таблица «файл → куда»** — покажи и согласуй (спорное — через AskUserQuestion): журнал и план выкладки — в корень `.claude/docs/`; остальное — в `work/` (текущее) или в `archive/` (этап, к которому документ относится, по журналу закрыт); папки (`design/`, `screenshots/`) — целиком; `docs/visual/` — в `.claude/docs/visual/`, только локально, мимо git (его `.gitignore` переезжает с ним); `docs/.htaccess` не переносится (папку закрывает `.claude/.htaccess`) — удалить, в пути коммита — как удалённый.
5. **Перенос** — обычным перемещением, без git:
   ```
   New-Item -ItemType Directory -Force '.claude/docs/work', '.claude/docs/archive' | Out-Null
   Move-Item -LiteralPath 'docs/<имя>' -Destination '.claude/docs/<куда>/<имя>'
   ```
   Затем (правки показать): в `.claude/CLAUDE.md` — «Журнал: .claude/docs/progress.md», «План выкладки: .claude/docs/deploy-prod.md» — это часть переезда, без неё журнал останется искать старый путь: пользователь против правки параметров — не переносить вовсе; старые пути `docs/…` в тексте — с его согласия; в «Не выкладывать» `.claude/scripts`, `.claude/settings.local.json`, `.claude/worktrees`, `docs/visual`, `docs` заменяются одной записью `.claude` (прочее — как было). Пустую `docs/` удалить.
6. **Закрытие** — вместе со всем запуском на шаге 4.8: DOCS — строки реестра по таблице п. 4 (`work/…` — `в работе, этап N`, документы на все этапы (спек, замечания) — `постоянный`, ненужные — `устарел — …`; `archive/…` — `готово, этап N (ГГГГ-ММ-ДД)`); DEPLOY — `Удалить` из п. 3; пути коммита — старые и новые пути, `.gitignore`, `.claude/CLAUDE.md`. После коммита: `git -c core.quotepath=false show --stat -M HEAD` — переименования (`docs/… => .claude/docs/…`), а не удаление и добавление; `git check-ignore -q .claude/docs/progress.md` — код 1.

### 4.8 Закрыть шаг

**Сначала — автозаливка**, только при «PhpStorm Always»:
1. Пользователь включает автозаливку: PhpStorm Tools → Deployment → Automatic Upload. Сверь `.idea/deployment.xml`: `autoUpload="Always"` / `myAutoUpload` = `ALWAYS`; нет — попроси File → Save All и сверь ещё раз.
2. Записанное этим запуском, пока автозаливка была выключена, на сервер не уехало, а её включение его не зальёт. Список «что залить» — файлы, которые этот запуск записал или изменил и которые не исключены из выкладки: при «Документы на сервере: да» — `.claude/.htaccess` — первым (до документов, иначе они на сервере открыты), затем `.claude/CLAUDE.md` и `.claude/docs` (снимки `visual` хук исключает); `.gitignore` — если менялся и не исключён. Список пуст — п. 2–3 пропусти. Пользователь заливает их сам: правый щелчок по файлу или папке в PhpStorm → Deployment → Upload to <сервер автозаливки>; затем AskUserQuestion: «Залил» / «Залью позже» (тогда — в итог пользователю и в NOTES).
3. Проверка снаружи по серверу автозаливки:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/check-closed.js" <адрес сервера автозаливки>
   ```
   Исключённые файлы `.claude` — 404; документы при «Документы на сервере: да» — 403 (залиты и закрыты `.htaccess`). Код 1 — стоп и разбор, как в п. 4.5. Итог — в CHECK шага.

**Точка отсчёта заливки** — только при «Claude по SSH» в проекте, который уже вёлся (коммитов больше одного): сухой прогон `node "${CLAUDE_PLUGIN_ROOT}/scripts/ssh-deploy.js"` — что уехало бы первым шагом. «Нечего заливать» — ничего не делай. Список есть, а в таблице «Залито на …» нет строки с хешем — первый шаг зальёт всё это от первого коммита и может затереть правки, сделанные прямо на сервере (через админку). Сначала сверка по md5, ничего не записывает: `node "${CLAUDE_PLUGIN_ROOT}/scripts/ssh-deploy.js" --md5` (параметры SSH уже записаны в п. 4.3). Код 0 — всё совпало: точка отсчёта без вопроса. Код 1 — AskUserQuestion, различия — в тексте вопроса: «Сервер новее — скачать отличающиеся и записать точку отсчёта» (Рекомендую, если правили на сервере) / «Залить этот список первым шагом» / «Сначала сверю сам». Точка отсчёта — блок DEPLOY шага 4.8: `Файлы:` — строка «DEPLOY Файлы:» из вывода `--md5` (после скачивания — повтор `--md5`), `Коммит: <HEAD>`, `Проверка: md5 с сервером совпали (ssh-deploy.js --md5)`.

**Документы на сервер** — только при «Claude по SSH» и «Документы на сервере: да» (новый проект или параметр включён этим запуском), после точки отсчёта: все документы — одной заливкой, `.htaccess` первым:
```
node "${CLAUDE_PLUGIN_ROOT}/scripts/ssh-deploy.js" --go --docs --all
```
Код 0 — проверка снаружи: `node "${CLAUDE_PLUGIN_ROOT}/scripts/check-closed.js" <адрес сервера>` — документы — 403; итог — в CHECK шага. Коды 1 и 3 — причину пользователю, повтор безопасен; код 2 — нет `.claude/.htaccess`: создать (п. 4.2) и повторить. Дальше документы шагов заливает `/kit:step-done` перед коммитом шага (`ssh-deploy.js --docs`).

Выбрано «вручную» или «Claude по SSH», а автозаливку выключили в п. 4.0 — не включай; в итог пользователю: автозаливка выключена, выкладка — вручную (список изменений Claude покажет по git) или Claude по SSH (заливает `/kit:step-done` после просмотра).

`/kit:step-done`:
- Журнал создан в этом запуске — этап 0 только инициализация, и шаг 0.2 его закрывает: STEP `0.2`, SUMMARY — что создано, CHECK — как проверено (сканы, проверка снаружи, исключения, автозаливка), NEXT — первый рабочий шаг уже этапа 1 (спроси пользователя; по умолчанию «1.1 — изучение задачи»), STAGE `1 — <название>` (задача есть — её название; нет — спроси вместе с NEXT); сверка этапа 0 — без вопросов: все его шаги ✅. DECISIONS не передавай — они уже записаны в п. 4.4.
- Журнал уже был (в том числе при переезде, п. 4.7) — STEP `0.2` не используй: шаг запуска — очередной шаг текущего этапа. Этап в «Сейчас» не закрыт — спроси ID через AskUserQuestion (рекомендуй следующий свободный ID этого этапа), NEXT — «Следующий шаг» из «Сейчас» дословно. Открытого этапа нет (этап в «Сейчас» закрыт или этапов нет) — первый шаг нового этапа: `STAGE: <N+1> — <название>` (был переезд — «переезд на kit 3.0», иначе — что сделал запуск, например «настройка проекта»), STEP `<N+1>.1`, NEXT — «Следующий шаг» из «Сейчас» или `—`. Этап 0 и другие закрытые этапы не правятся: их разделы уже в `journal/stages/`, туда `kit-journal.js` не пишет. SUMMARY — что сделано (при переезде — его пункты), CHECK — как проверено (сканы, проверка снаружи, исключения; после переезда — проверка хуком), DECISIONS — ответы этого запуска (почему — «ответ при /kit:project-init», что отвергли — другие варианты вопроса, кто — пользователь).
- Параметр «Удалённый репозиторий» задан — `/kit:step-done` проверит историю и отправит коммит (`kit-commit.js --push`); окно входа — пользователь. Отправка не удалась — скажи почему; коммит остаётся и уйдёт со следующим шагом.

## 5. Итог пользователю

Коротко: что создано, что дополнено, что пропущено; автозаливка — включена и нужное залито (или что осталось залить) / выключена, выкладка вручную; какие действия остались за пользователем (File Watchers; если PhpStorm был открыт — убедиться, что новые строки видны в Excluded Paths, иначе File → Reload All from Disk; удаление старых копий `docs/` и агентов с сервера; вход по SSH-ключу, если его нет (справка reference/ssh.md); вход в GitHub/GitLab при первой отправке (если отправка не удалась); скиллы Битрикса поставлены, а Claude их не видит — перезапустить сессию).
