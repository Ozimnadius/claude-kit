# 1С-Битрикс: что проверить при старте проекта

## Версия PHP прода

- Заголовок `X-Powered-By: PHP/7.4.33` показывает `site-probe.js` (п. 4.5 скилла).
- Заголовок скрыт — `ssh-probe.js` (версии PHP на сервере) или `/kit:server`, код `echo PHP_VERSION;`.
- Синтаксис проверяем той же версией: `C:\OSPanel\modules\PHP-X.Y\php.exe -l` (параметр «PHP»; хук `php-lint` делает это после каждой правки). На PHP 7.x — никакого синтаксиса PHP 8 (`match`, `?->`, именованные аргументы, `str_contains`).

## Закрытие `.claude/` (и старой `docs/`)

- С 2.3.0 документы проекта лежат в `.claude/docs`, а `.claude` исключена из выкладки целиком (Excluded Paths дописывает хук kit `phpstorm-exclude.js`, для ручной выкладки — «Не выкладывать»). На сервер такие файлы не уезжают — это главная защита.
- `.htaccess` с `Require all denied` — страховка на случай ручной заливки папки целиком; действует, только если запрос доходит до Apache. На хостингах nginx + Apache статику (pdf, docx, xlsx, картинки, txt, zip…) часто отдаёт сам nginx — мимо `.htaccess` (найдено в epsilon 2026-09-22). Поэтому:
  - проверять **каждый файл** снаружи — `check-closed.js` (норма — 404 «нет на сервере» или 403);
  - в старой `docs/` (проект ещё не переехал) не держать статические форматы; если нужно — дописать `.php` к имени (`tz.docx.php`), тогда запрос идёт в Apache.
- Старые копии `docs/` и `.claude/` на сервере (выложенные до 2.3.0) сами не исчезают — `check-closed.js` находит их (403/ОТКРЫТ), удаление — через «Удалить с сервера».
- Проверять всегда снаружи, по настоящему адресу.

## `.min.css` / `.min.js`

Битрикс отдаёт `.min`-файл, только если он не старее исходника. Устаревшие `.min` Аспро (`template_styles.min.css`, `styles.min.css`) не трогать и не создавать: иначе Битрикс начнёт отдавать старый код.

## Секреты

Только в `/bitrix/.settings_extra.php` (своя секция), читать через конфиг-класс проекта. В git не класть: `/bitrix/*` в `.gitignore`, скрипт коммита `kit-commit.js` и `secret-scan.js` проверяют пути и строки.

`.settings.php` в любой папке (в том числе ядра — `bitrix/.settings.php`, `local/.settings.php`), `.settings_extra.php` и `dbconn.php` скрипт коммита не пропускает. Исключение (с 3.2.3) — `.settings.php` модуля D7 прямо в его папке: `bitrix/modules/<модуль>/.settings.php`, `local/modules/<модуль>/.settings.php`. В нём контроллеры (без секции `controllers` ядро не находит их), консольные команды и т. п., его получает каждый покупатель модуля — секретов там нет: он коммитится и заливается, как остальной код модуля; строки на пароли и токены `secret-scan.js` проверяет и в нём.

## Рабочие папки в `bitrix/` (с 3.2.0)

По шаблону ядро `bitrix/` в git не попадает: правки в нём не коммитятся, и `ssh-deploy.js` их не заливает. Но бывает, что правят прямо в `bitrix/`: шаблон сайта без копии в `local/templates` (режим «на месте» сверки aspro-merge), компоненты решения `bitrix/components/<пространство>`, иногда `bitrix/js|css/<решение>`; а на сайте без `local/php_interface/init.php` действует `bitrix/php_interface/init.php` (туда, например, aspro-merge пишет строку подключения). Такие папки — **рабочие**: они должны быть в git.

**`.gitignore`.** Git не возвращает файл, если игнорируется его папка, поэтому строка ядра — `/bitrix/*` (не `/bitrix/`; старое `/bitrix/` замени с согласия), а после неё — для каждой рабочей папки: каждая её папка-родитель ниже `bitrix/` — пара строк `!/<родитель>/` и `/<родитель>/*` (одна пара на родителя, даже если рабочих папок в нём несколько), затем сама папка `!/<путь>/` или файл `!/<путь>`. Пример — шаблон, компоненты и `init.php`:
```
/bitrix/*
# Рабочие папки в bitrix/ — в git (правят прямо там)
!/bitrix/templates/
/bitrix/templates/*
!/bitrix/templates/<шаблон>/
!/bitrix/components/
/bitrix/components/*
!/bitrix/components/<пространство>/
!/bitrix/php_interface/
/bitrix/php_interface/*
!/bitrix/php_interface/init.php
```
Бэкапы обновлятора внутри рабочих папок игнорируются и так — строкой `*.back*` (и `_*_back*.zip`, если есть).

**«Не коммитить».** `bitrix/` с теми же папками в «кроме»: `bitrix/ (кроме bitrix/templates/<шаблон>, bitrix/components/<пространство>, bitrix/php_interface/init.php), upload/ (кроме upload/docs/), *.back*`. Без «кроме» скрипт коммита не пропустит ни одного файла рабочих папок.

**Модули в `bitrix/modules/<модуль>`** (свой модуль или решение для Маркетплейса разрабатывают прямо там) — тоже рабочие папки, в «кроме» можно маской: `bitrix/modules/<пространство>.*`. `.settings.php` модуля коммитится и заливается вместе с ним (с 3.2.3), `bitrix/.settings.php` ядра — нет (раздел «Секреты»).

**Проверка** — `git check-ignore -q <файл>`: файл в каждой рабочей папке — код 1 (не игнорируется), что-нибудь другое в `bitrix/` (например `bitrix/.settings.php`) — код 0. «Не коммитить» проверяет `node "${CLAUDE_PLUGIN_ROOT}/scripts/secret-scan.js" --paths <те же файлы>` — код 0 для файлов рабочих папок.

**Файлы.** Рабочих папок нет в проекте (исходники скачаны без `bitrix/`) — до первого коммита (или коммита шага запуска) их скачивают с сервера: пользователь (Remote Host PhpStorm) или Claude по SSH с согласия, из корня проекта в Bash, без бэкапов обновлятора:
```
ssh <хост> "cd '<папка сайта>' && tar -cf - --exclude='_*.back*' --exclude='_*_back*.zip' <рабочие папки через пробел>" | tar -xf -
```
При «Claude по SSH» в проекте с коммитами скачанное — точка отсчёта заливки (`ssh-deploy.js --md5`, п. 4.8 скилла).

**После обновления ядра или решения** обновлятор меняет рабочие папки на сервере, а в проекте остаются старые версии: их скачивают заново и коммитят (при «Claude по SSH» — шагом без заливки, точка отсчёта: `/kit:step-done`, `reference/ssh.md`, «Файлы взяты с сервера»). Иначе правка такого файла зальёт поверх новой версии старую.

## Работа на сервере

Проверки и разовые скрипты на сервере — `/kit:server`: сначала SSH, если не задан или не пустил — файл-канал `kit-exec.php` (только Битрикс); нет ни того ни другого — включить SSH (`reference/ssh.md`); только чтение — сразу, изменения — с согласия пользователя (удаление — после сухого прогона).
