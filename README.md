# claude-kit

**[Как устроен плагин kit — схемы и все развилки →](.claude/docs/work/overview/overview.md)**

Маркетплейс Claude Code с двумя плагинами. **aspro** — сверка доработок сайта с обновлением решений Аспро (раздел [«Плагин aspro»](#плагин-aspro) ниже). **kit** — каркас работы над проектами (журнал, закрытие шага скриптами и один коммит на шаг, хуки правил процесса и `php -l`) и модуль для сайтов на 1С-Битрикс (инициализация проекта, работа на сервере по SSH, а на Битриксе без SSH — через файл `kit-exec.php`, проверки выкладки, снимки публичной части «до/после», скиллы Битрикса). Плагин и документация — на русском; рассчитан на Windows (Git Bash и PowerShell), PhpStorm и OSPanel, но работает и без них.

## Установка

Нужны [Claude Code](https://claude.com/claude-code) и Node.js ≥ 18.

```
claude plugin marketplace add Ozimnadius/claude-kit
claude plugin install kit@claude-kit
```

То же в сессии: `/plugin marketplace add Ozimnadius/claude-kit`, затем `/plugin install kit@claude-kit`. Дальше в папке проекта — `/kit:project-init`.

Из локальной копии репозитория (для разработки): `claude plugin marketplace add <папка репозитория>`.

## Обновление

```
claude plugin marketplace update claude-kit
claude plugin update kit@claude-kit
```

Затем перезапустить сессии Claude Code; после перехода на новую мажорную версию — раздел «Переход на 3.0» ниже. При установке плагин копируется в кэш `~/.claude/plugins/cache/claude-kit/kit/<версия>` — Claude Code работает с копией, а не с папкой репозитория; обновление смотрит на версию: без её повышения `claude plugin update` отвечает «already at the latest version».

## Переход на 3.0

Выпуск 3.0.0 (этап 36): закрытие шага стало кратно короче по времени и токенам, результат тот же — журнал, один коммит на шаг, просмотр перед коммитом.

**Что изменилось**
- **Закрытие шага — скриптами.** `kit-step.js` готовит шаг одной командой (файлы шага, ваши ответы на вопросы — готовыми строками решений, режим выкладки), `kit-journal.js` пишет журнал по блокам вместо агента docs-keeper, `kit-commit.js` делает коммит, убирает разобранные входящие (`--inbox`) и отправляет (`--push`). Текст `/kit:step-done` — короткое ядро (14 КБ вместо 36 КБ), ветки — в справках `reference/ssh.md`, `stage-close.md`, `push.md`.
- **Один формат проекта:** документы в `.claude/docs`, журнал по частям (`journal/`), таблица текущего этапа со столбцом «Как проверено», таблица решений с «Почему», «Окружение» — `прод` или `дев`, «Выкладка» — `PhpStorm Always`, `Claude по SSH` или `вручную`.
- **Хешей коммитов в журнале нет:** коммит шага находится по ID в заголовке (`36.3: …`). При автозаливке PhpStorm строки «Залито» в плане выкладки не ведутся — залитое совпадает с закоммиченными шагами.
- **Убрано:** режимы «Код пишет: пользователь» и «Коммит: сразу» (просмотр перед коммитом — всегда), команды `/kit:why` и `/kit:deploy-list`, агент docs-keeper.
- **Скиллы Битрикса** — отдельный вопрос `/kit:project-init` при каждом запуске: «Да» ставит свежие версии, «Нет» — не трогает.
- **Проверка на сервере** — правило хука, только если у окружения задан адрес сервера; страница проверяется одним пакетным вызовом браузера.

**Как перейти:** обновить плагин и в каждом проекте запустить `/kit:project-init` — хук сам предложит его при первом старте сессии («Журнал или параметры в старом формате (…)»). Один запуск переводит всё старое, по строке плана на каждый найденный признак: `docs/` → `.claude/docs`, журнал на части, столбец «Как проверено» в текущем этапе, новая таблица решений под старой, старые значения «Окружения» и «Выкладки», строки «Код пишет» и «Коммит». Закрытые этапы и их хеши остаются как есть. До переезда kit 3.0 в проекте шаги не закрывает: `kit-step.js` и `kit-journal.js` отвечают кодом 2 и тем же сообщением о переезде.

## Документы проекта (с 2.3.0)

```
.claude/docs/
  progress.md      журнал: «Сейчас», оглавление этапов, «Документы» (реестр), «Прод: не забыть», текущий этап
  journal/         части журнала (с 2.13.0): decisions.md, bugs.md, reference.md, stages/stage-NN.md — закрытые этапы
  deploy-prod.md   план выкладки
  work/            текущие планы, спеки, чек-листы, материалы задач
  archive/         готовое и устаревшее — туда их переносит /kit:step-done при закрытии этапа
  visual/          снимки /kit:visual — только локально
```

- **Журнал по частям** (с 2.13.0): в `progress.md` — только текущее, остальное — в `journal/`; закрытый этап `/kit:step-done` переносит в `journal/stages/` скриптом `journal-split.js` (строка в строку, с проверкой, что ничего не потерялось). С 3.0.0 kit понимает только журнал по частям: журнал одним файлом переводит `/kit:project-init` при переезде на 3.0 (`journal-split.js --migrate`).
- `.claude` исключается из выкладки целиком: исключения PhpStorm (Excluded Paths) хук дописывает сам при каждом старте сессии — руками в настройки ходить не нужно; для ручной выкладки `.claude` стоит в «Не выкладывать». Так на сервер не уезжают ни журнал, ни планы, ни скриншоты (nginx отдаёт статику мимо `.htaccess`).
- Нужны документы и на сервере (например, открывать их по FTP) — параметр «Документы на сервере: да» (с 2.6.0): автозаливкой уезжают `.claude/docs` (кроме снимков `visual`), `.claude/CLAUDE.md` и `.claude/.htaccess`, всё остальное в `.claude` хук исключает поимённо; нет `.claude/.htaccess` — создаёт («Require all denied»). Если «Exclude items by name» в настройках выкладки PhpStorm отсекает документы (`*.md`, `docs`), хук предупредит — этот список меняете вы. После первой заливки проверьте снаружи, что `/.claude/` закрыта (`check-closed`). В режиме «Claude по SSH» (с 2.18.0) те же документы заливает `/kit:step-done` перед коммитом шага (`ssh-deploy.js --docs`, `.htaccess` — первым), первую заливку всех документов делает `/kit:project-init`; хук PhpStorm в этом режиме держит `.claude` исключённой.
- `.claude` — защищённая папка Claude Code: в режимах Manual и acceptEdits запись туда просит подтверждения (в вопросе есть «разрешить правки в `.claude` на эту сессию»); в auto решает классификатор, в bypassPermissions — без вопросов. Правило allow в settings.json это не снимает.
- Если PhpStorm открыт и новую строку в Excluded Paths не показал — File → Reload All from Disk.
- Проекты со старой `docs/` kit 3.0 не обслуживает: переезд в `.claude/docs` — часть перехода на 3.0 через `/kit:project-init` (правит `.gitignore`, переносит файлы по вашей таблице «файл → куда», меняет параметры, записывает старые копии `docs/` на сервере в «Удалить с сервера» — одним шагом и коммитом).

## История: что делали, как проверили, почему так решили (с 2.8.0)

- **«Решения»** в журнале — `№ | Дата | Шаг | Решение | Почему | Что отвергли | Кто`. «Почему» обязательно. Туда же — значимые решения агента (их `/kit:step-done` показывает отдельным списком, чтобы можно было возразить) и изменения правил проекта. Отменённое решение помечается «→ заменено №M».
- **Таблицы этапов** — с колонкой «Как проверено»; тело коммита шага — то же, что в ней. Хешей коммитов в журнале нет (с 3.0.0): коммит шага находится по ID в заголовке.
- Закрытые этапы и старые таблицы не переделываются: при переезде на 3.0 таблица текущего этапа получает столбец «Как проверено», а под старой таблицей решений появляется новая.
- **Сверка этапа** (с 2.10.0): при закрытии этапа `/kit:step-done` сверяет задуманное (требования спека, задачи плана, иначе — шаги этапа) со сделанным и показывает таблицу; расхождения — одним вопросом: в «Баги на потом», на следующий этап или «не делаем» с причиной в «Решениях». Итог — строка «Сверка …» под таблицей этапа.
- **Чек-лист в планах** (с 2.13.0): в начале плана этапа — строка на задачу (`- [ ] N.M — …`), при закрытии шага `kit-journal.js` ставит `[x]` — по плану сразу видно, что сделано.
- **Входящие ответы** (с 2.9.0): хук записывает каждый ваш ответ на вопрос Claude (вопрос, варианты с описаниями, выбор или свой текст) в локальный `.claude/kit-inbox.jsonl` — не в git и не на сервер. `kit-step.js` выдаёт их готовыми строками решений («почему» — описание выбранного варианта, «что отвергли» — другие варианты), `/kit:step-done` отбрасывает процедурные вопросы вроде «Закрывать шаг?», а `kit-commit.js --inbox` после проверенного коммита убирает разобранное. Решения не теряются, даже если контекст сессии сжался.

## Система Мэтта Покока для больших проектов (с 3.3.0)

Для больших работ, которые не влезут в одну-две сессии, kit умеет вести проект по системе [Мэтта Покока](https://github.com/mattpocock/skills) (навыки `grill-with-docs`, `wayfinder`, `to-spec`, `to-tickets`, `implement` и др., лицензия MIT). Система нужна не всегда, поэтому включается только по вашему ответу при настройке; по ходу работы Claude её не предлагает.

- **Вопрос.** `/kit:project-init` при каждом запуске спрашивает «Вести проект по системе Мэтта Покока?». Ответ — параметр «Система Мэтта: да|нет» в `.claude/CLAUDE.md`. Существующие проекты получают вопрос, когда догоняют настройку через `/kit:project-init`.
- **«Да».** На этот проект ставится плагин `mattpocock-skills` из `claude-plugins-official` (`--scope project`), а superpowers в нём выключается — работают только навыки Мэтта, всегда с префиксом `mattpocock-skills:`. После этого перезапустите сессию. Включение плагинов на проект лежит в `.claude/settings.json`, а он не в git: на другом компьютере при «да» без плагина хук при старте напомнит запустить `/kit:project-init`. Из сессии в worktree (`.claude/worktrees/…`) плагин не ставится — Claude попросит открыть сессию в основной папке проекта; маркетплейс `claude-plugins-official` не зарегистрирован — с вашего согласия Claude добавит его и повторит установку.
- **«Нет»** (или смена «да» на «нет»). Ничего не ставится; после «да» плагин Мэтта выключается, superpowers включается обратно, глоссарий, ADR и папки тем остаются.
- **Мелкая задача** идёт как обычно: сделать и закрыть `/kit:step-done`, без карты и тикетов.
- **Большая работа** — по навыку `/kit:matt` (Claude вызывает его сам): сессия становится общей — координатором. Маршрут предлагает Claude, как `ask-matt`: карта решений `wayfinder`, или грилинг → спек → тикеты, или сразу сделать.
- **Исполнители.** На каждый тикет общая сессия запускает исполнителя со свежим контекстом и коротким заданием: если нужны вы (грилинг, вопросы) — подчинённая сессия приложения Claude, иначе фоновый субагент. Исполнитель не коммитит и не вызывает `/kit:step-done` (тикет принимает только общая сессия), докладывает коротким отчётом. Навыки Мэтта «только по команде» (`wayfinder`, `to-spec`, `to-tickets`, `implement` и др.) Claude не вызывает, а читает их файлом (путь выдаёт `matt-skill.js`); вы можете и сами ввести `/mattpocock-skills:<имя>`.
- **Приёмка.** Тикет = шаг kit. Общая сессия закрывает его через `/kit:step-done`: просмотр изменений, ваше «Коммитить», один коммит только с файлами тикета, `Status: resolved`. Замечания — шагами с буквой (`N.Mа`). Шаг не по тикету, пока идёт этап Мэтта (мелкая задача, `/kit:project-init`), — `N.0а`, `N.0б`…: номера без буквы заняты тикетами.
- **Режим без пользователя** — только когда вы сами сказали «работай без меня». Перед включением Claude спросит о режиме разрешений: Auto, Bypass или Manual — тогда первый тикет идёт при вас: на запрос правки `.claude` вы отвечаете «разрешить до конца сессии», на запуск скриптов kit и проверок проекта — «больше не спрашивать» (иначе работа встанет на первой записи в `.claude/docs` или на первом скрипте). Тикеты идут подряд субагентами, после проверок и ревью (`mattpocock-skills:code-review`) закрываются без вопроса «Коммитить» с пометкой «принят без просмотра»; вопросы копятся в тикетах (`ready-for-human`). Между тикетами проверяется расход лимитов. Когда вы вернётесь — разбор по одному тикету; в удалённый репозиторий такие коммиты уходят только после разбора всех (шаги исправлений при разборе тоже не отправляются), даже если хук при старте предлагает отправить. При «Выкладка: PhpStorm Always», если окружение не «дев» (пустое — тоже прод), режим не включается; при «Claude по SSH» тикеты без пользователя на сервер не заливаются — заливка и проверка при разборе.
- **Где лежат файлы.** Карта, её тикеты и спек — `.claude/docs/work/<тема>/` (`map.md`, `issues/NN-<slug>.md`, `spec.md`), тикеты реализации — `.claude/docs/work/<тема>-build/`, глоссарий — `.claude/docs/GLOSSARY.md`, ADR — `.claude/docs/adr/NNNN-<slug>.md`. Трекер задач — эти локальные файлы по справке kit (`skills/matt/reference/tracker.md`). В корень проекта (на сайте это корень сайта) ничего не кладётся. На сервер документы уезжают по общему правилу «Документы на сервере». Спек и план kit (`spec-*.md`, `plan-*.md`) в проекте Мэтта не пишутся — их заменяют спек и тикеты Мэтта. Не используются `implement-spec` и `setup-matt-pocock-skills`.
- **Подстраховка хуками** (только в проектах Мэтта, сообщения с подсказкой, как правильно):
  - коммит в обход `/kit:step-done` не проходит — `git commit`, а также `merge` локальной ветки, `revert`, `cherry-pick`, `am`; слияние удалённой ветки по потоку kit (ветка разошлась с удалённой — с вашего согласия) и завершение такого слияния после конфликта работают;
  - ветки и worktree не проходят при любой выкладке — в git (`checkout -b`, `switch -c`, `branch <имя>`, `worktree add`, `stash branch`) и уход сессии, субагента или подчинённой сессии в worktree; сессии, открытой в worktree (`.claude/worktrees/…`), правила при старте велят попросить вас открыть сессию в основной папке, а шаги и коммиты там не делать;
  - при «PhpStorm Always» не проходит перезапись рабочей копии старыми версиями — `bisect`, `stash`, переход на другой коммит или ветку (`checkout`, `switch`), `reset --hard`, `restore --source`, `rebase`, `pull --rebase`: файлы с диска сразу уехали бы на сервер. Бисекция — в копии: `git clone <проект> <временная папка>`, затем `git -C <копия> bisect …` (или `( cd <копия> && git … )`); команды, у которых и репозиторий, и рабочая копия вне проекта, страж пропускает, коммиты и ветки — нет. Облачная копия субагента тоже не проходит;
  - запись в корень проекта файлов навыков Мэтта не проходит: `GLOSSARY.md`, `GLOSSARY-MAP.md`, `CONTEXT.md`, `CONTEXT-MAP.md`, `MISSION.md`, `RESOURCES.md`, `to-questionnaire-*.md`, `docs/adr/`, `docs/agents/`, `.scratch/`, уроки `lessons/*.html`, `learning-records/`, `.out-of-scope/`.
- **Версия плагина.** Правила kit проверены на плагине Мэтта 1.3.1: если установлена другая версия, пока идёт большая работа, Claude сверит их с навыком.

## Прод главный: `/kit:sync` (с 3.4.0)

Сайт на проде меняют не только через kit: клиент правит файлы по FTP и в админке, обновления ядра и решений (например, Аспро) переписывают шаблоны. Об этих правках git не знает, и следующая заливка нашего шага их затёрла бы. `/kit:sync` забирает в git то, что поменяли на сервере без нас: прод главный, git его догоняет.

- **Когда запускать.** Перед работой, если прод могли менять: командой `/kit:sync` или словами «синхронизируй с продом». Сам Claude синхронизацию не запускает — ни при старте сессии, ни перед заливкой; при старте сессии kit о проде молчит. Нужен kit-проект, где задан адрес сервера окружения («Прод» или «Дев») или «SSH прод» / «SSH дев»; иначе ответ — «синхронизировать не с чем». Сервер — по «Окружению»: прод или дев.
- **Что делает.** Каждый файл сайта сравнивается в трёх версиях: **база** — что точно было на сервере при последней заливке (последняя строка «Залито на …» плана выкладки, нет её — первый коммит; у файла, который уже забирала синхронизация, — её версия), **наш git** и **сервер** сейчас. На сервере как в базе — файл не трогается, и наши незалитые шаги не теряются. Изменили только на сервере — версия сервера забирается байт в байт. С 3.4.1 два случая — только по вашему ответу, одним вопросом со списком до любой записи. **Файла из git нет на сервере** — его могли никогда туда не заливать (README, заметки), поэтому синхронизация не удаляет его у нас сама: «Удалить у нас» (`--delete-ok`), «Оставить у нас» (`--keep-deleted`: итог назовёт их один раз, дальше синхронизация о них не спрашивает) или «Отложить»; таких больше 20 и больше 10 % файлов сайта — в вопросе ещё строка «проверь «SSH прод»»: скорее всего, он указывает не на ту папку или сайт переналили, поэтому рекомендуемый ответ — «Отложить» и проверка параметра. **Новый код на сервере** (`.php`, `.js`, `.htaccess`, `.user.ini` и другие скрипты) и любой новый файл в новой папке корня сайта — так выглядит и новая страница клиента, и подброшенный код: «Забрать» (`--new-ok`: ответ запоминается — файл, который не прошёл обычные проверки, например с секретом, назван один раз и заберётся без вопроса, когда пройдёт), «Не забирать» (`--new-skip`: файлы остаются на сервере, итог назовёт их один раз) или «Отложить». Новые картинки, стили и тексты в знакомых папках забираются без вопроса. Ответ действует только на тот список, о котором спросили: если, пока вы отвечали, на сервере появилось или пропало что-то ещё, синхронизация спросит заново. Передумали («Не забирать» / «Оставить у нас») — попросите Claude убрать путь из ответов в `.claude/kit-prod.json` и повторить `/kit:sync`. `--check` не спрашивает — пишет «нет на сервере: N (спросит синхронизация)». На сервере уже наше — ничего. CRLF и LF — одна версия. Всё забранное уходит одним коммитом (очень много файлов — несколькими подряд), без просмотра и вопросов: `Прод: изменения без kit на ГГГГ-ММ-ДД (N файлов)` (окружение дев — `Дев: …`), список файлов — в теле; при заданном «Удалённом репозитории» коммит отправляется. Итог — одна строка: сколько файлов изменено, добавлено и удалено без kit, а отдельно — наши прошлые доработки среди изменённых (клиент или обновление могли их затереть — проверьте), совмещённое, не забранное и ждущее удаления с сервера. Нечего забирать — «прод совпадает с git», коммита нет. `/kit:step-done` после синхронизации не нужен.
- **Что не забирается.** Ядро, загрузки и кеш (исключено `.gitignore`), «Не выкладывать», служебные файлы git (`.gitignore` и `.gitattributes` в любой папке) и исключённое у сервера автозаливки PhpStorm (Excluded Paths, например исходники SCSS) — вне синхронизации: не сверяются, не забираются, не удаляются и не возвращаются к git. Исключение — «Выкладка: Claude по SSH»: там исключённое в PhpStorm заливает `ssh-deploy.js`, поэтому оно сверяется как обычные файлы сайта, но то, чего нет на сервере, у нас не удаляется — итог называет его один раз. Архивы и бэкапы (`*.zip`, `*.tar.gz`, `*.tgz`, `*.sql`, `*.bak`, `*.old`, `*.orig`, `*.orig.*`, `*.orig2`, `_*.back*`; с 3.4.1 и копии стилей и кода: расширение на `_` — `*.cs_`, `*.ph_`, `*.js_`, — `*-orig`, например `style.css-orig`…), файлы больше 10 МБ, файл с секретом, запрещённое к коммиту (`dbconn.php`, `.settings.php` ядра, `.env`, `*.pem`, `*.key`… и «Не коммитить») и путь с недопустимым именем остаются на сервере и называются в итоге — один раз, при первой синхронизации, где появились. Чем грозит: в git у такого файла старая версия, и если наш шаг его правит, заливка затрёт серверную правку — перенесите её сами. Больше 50 МБ за раз — остановка до записи (по SSH — ещё до скачивания) и вопрос: забрать всё, не забирать самые тяжёлые папки (Claude допишет их в `.gitignore`) или отложить. По SSH при автозаливке PhpStorm, если среди забираемого есть исходники File Watchers, — вопрос до записи: пересборка перезапишет результат и PhpStorm зальёт его на сервер.
- **Совмещение и конфликт.** Файл менялся и у нас (в незалитом шаге или в незакоммиченной правке), и на сервере — синхронизация совмещает обе правки в рабочей копии, мимо своего коммита: результат вы видите в панели изменений и закрываете обычным шагом. Не совместилось само — файл в рабочей копии не тронут (без SSH — возвращён к версии в git), версии сервера и базы — во временной папке, остальное синхронизируется; по каждому такому файлу вопрос: «Совместить вручную» (Claude правит нашу версию по серверной), «Оставить нашу» (вопрос повторится при следующей синхронизации, пока наша версия не залита) или «Взять версию сервера».
- **Только посмотреть** (по SSH) — `/kit:sync --check`: что синхронизация заберёт и совместит, ничего не записывая. Без SSH так не выйдет: изменения сервера видны только после скачивания.
- **Без SSH** (задан только адрес сервера) — через FTP в PhpStorm. Есть незакоммиченные правки файлов сайта — сначала предупреждение: скачивание их затрёт, а правки файлов, которые скачивание не перезапишет (например, наш новый файл, которого нет на сервере), уйдут в коммит синхронизации как изменения сервера («Скачаю всё равно» / «Отложить»). Совмещение без SSH — только с закоммиченным. Затем Claude даёт список папок и файлов — их надо скачать с сервера с заменой (выделить в дереве проекта → Tools → Deployment → Download from …); ядро, загрузки и локальные настройки в список не входят. После ответа «Скачал» скачанное разбирается по тем же правилам: забранное — в коммит, наше незалитое, которое скачивание вернуло к старой версии, — обратно из git, файлы с «Не выкладывать» не трогаются. При автозаливке Always её надо выключить на время синхронизации (Tools → Deployment → Automatic Upload, затем File → Save All — PhpStorm записывает настройку не сразу) — иначе разбор не пойдёт: возвращённое из git уехало бы на сервер; после синхронизации включите её обратно. «Отложить» после скачивания (автозаливка, объём, новый код) оставляет скачанное в проекте незакоммиченным: разобрать его позже — попросите Claude разобрать скачанное (тот же запуск, что после «Скачал», с `--ftp-done`); простой `/kit:sync` сначала предупредит о правках в рабочей копии. Новое скачанное, что не забирается (архивы, больше 10 МБ, с секретом, новый код по ответу «Не забирать»), разбор не удаляет — оно лежит в рабочей копии вне git, итог его называет: удалите сами, если не нужно. Ограничение: удалённые на сервере файлы и новые вне перечисленных папок по FTP не видны.
- **«Отменить».** Синхронизация остановилась после записи файлов (коммит не прошёл, обрыв) — вопрос «Повторить» / «Отменить»: повтор доводит её до конца, отмена возвращает к git только записанное синхронизацией; наши правки и совмещённое не трогаются. Без SSH отмена не удаляет новые файлы — их положило скачивание, а не синхронизация: они остаются в рабочей копии вне git, строка отмены их называет (удалите сами, если не нужны). При автозаливке PhpStorm Always «Повторить» и «Отменить» сначала просят её выключить (Tools → Deployment → Automatic Upload, затем File → Save All), ничего не записав: возврат файлов к git уехал бы на сервер. Нет связи или вышло время до записи — «Повторить» / «Отложить».
- **Worktree.** В сессии в worktree синхронизация только сверяет основную папку проекта и говорит, есть ли что забрать, — ничего не пишет; синхронизация без SSH там не работает. Сама синхронизация — в основной папке. Исполнитель Мэтта её не запускает.
- **Заливка после синхронизации.** При «Claude по SSH» `ssh-deploy.js` в `/kit:step-done` не льёт обратно файлы, пришедшие синхронизацией, пока у нас они такие же, какими пришли с сервера («Не заливаю — уже на сервере, пришли синхронизацией»); шаг, который поменял такой файл или вернул его к старой версии, заливается как обычно. Так же — сверка `--md5`.
- **Требования к серверу** (по SSH): `sh`, GNU `find` с `-printf`, `md5sum`, `base64`, `xargs -0`, `cut`, `mktemp -d`. Чего-то нет — синхронизация не делается и называет, чего не хватает. Файлы сайта на сервере синхронизация не меняет.

```markdown
## Параметры для агентов

- Режим: bitrix
- Окружение: прод
- Выкладка: PhpStorm Always
- Прод: https://alpha.example.com
- Дев: —
- SSH прод: alpha:/var/www/user100/data/www/alpha.example.com
- SSH дев: —
- PHP на сервере: /opt/php74/bin/php
- PHP: C:\OSPanel\modules\PHP-7.4\php.exe
- Журнал: .claude/docs/progress.md
- План выкладки: .claude/docs/deploy-prod.md
- ID шага: N.M (например 0.3, 2.1)
- Не выкладывать: .idea, .git, .claude
- Документы на сервере: нет
- Не коммитить: bitrix/, upload/ (кроме upload/docs/), *.back*
- Секреты: —
- Удалённый репозиторий: origin
- Система Мэтта: нет
- Версия kit: 3.4.1
```

- **Окружение** — `прод` или `дев` (с 2.17.0): один сервер, куда идут шаги и где их проверяют; при деве перенос на прод — вне kit. Задан адрес и SSH только этого сервера; скрипты с `--env` по умолчанию берут его. Старое `дев+прод` с 3.0.0 — старый формат: его заменяет переезд (`/kit:project-init`).
- **Выкладка** — `PhpStorm Always` (автозаливка на сервер окружения), `Claude по SSH` (с 2.17.0: шаг заливает `/kit:step-done` после просмотра скриптом `ssh-deploy.js` — одно подключение, сверка md5, удаления; затем проверка на сервере и коммит) или `вручную`; старое `вручную; дев — PhpStorm Always` с 3.0.0 — старый формат (переезд: `Окружение: дев`, `Выкладка: PhpStorm Always`).
- **Прод / Дев** — адрес сервера окружения; без него правила «проверить результат на сервере» нет (с 3.0.0).
- **PHP** — абсолютный путь к `php.exe`; относительный путь или другой файл хук `php -l` не принимает и молчит, а файл-канал `kit-exec.js` без него не собирает файл (нужна проверка `php -l`).
- **SSH прод / SSH дев** — `хост:папка сайта`: псевдоним из `~/.ssh/config` (или `user@host`) и абсолютный путь к корню сайта на сервере; `—` — SSH нет: в режиме bitrix при заданном адресе `/kit:server` работает через файл `kit-exec.php`; в общем режиме выполнить на сервере негде — включить SSH. Порт — только через `~/.ssh/config`. Вход — только по ключу без пароля; настройка — `plugins/kit/skills/project-init/reference/ssh.md`.
- **PHP на сервере** — полный путь к PHP CLI нужной версии: команда `php` на хостинге бывает старой (на ispmanager — 5.4).
- **Пути** в «Не выкладывать» и «Не коммитить»: со `/` в любом месте — от корня проекта (`bitrix/` — только корневая папка, копии шаблонов в `local/templates/…/components/bitrix/` коммитятся), без `/` — имя в любом месте пути (`.idea`, `*.back*`). `(кроме …)` — исключения: `bitrix/ (кроме bitrix/templates/<шаблон>, bitrix/php_interface/init.php)` — рабочие папки в `bitrix/`, где правят прямо там (с 3.2.0; те же исключения — в `.gitignore`, `/bitrix/*` вместо `/bitrix/`; справка `plugins/kit/skills/project-init/reference/bitrix.md`).
- **`.claude/worktrees`** — git worktree, которые Claude Code (десктоп) создаёт внутри проекта (полная копия сайта); исключение `.claude` закрывает и их.
- **Служебные папки superpowers** (`.superpowers`, `.worktrees`, `docs/superpowers`) хук исключает из выкладки всегда (с 2.8.0), шаблоны `.gitignore` — из git.
- **Документы на сервере** — `да` или `нет` (по умолчанию; `/kit:project-init` спрашивает при автозаливке PhpStorm, с 2.15.2, и при «Claude по SSH», с 2.18.0): `да` — автозаливка PhpStorm везёт на сервер `.claude/docs`, `.claude/CLAUDE.md` и `.claude/.htaccess`, остальное в `.claude` остаётся исключённым; при «Claude по SSH» их заливает `/kit:step-done` (`ssh-deploy.js --docs`) (раздел «Документы проекта»).
- **Удалённый репозиторий** — имя remote в git (`origin`), куда `/kit:step-done` отправляет каждый проверенный коммит (первый раз — после проверки всей истории на секреты); `—` — не отправлять. Адрес хранится в `.git/config`; подключает `/kit:project-init`.
- **Система Мэтта** — `да` или `нет` (с 3.3.0): ответ на вопрос `/kit:project-init` «Вести проект по системе Мэтта Покока?» (раздел «Система Мэтта Покока для больших проектов»). `да` включает правила системы Мэтта при старте сессии, стражи `guard-bash.js` и `guard-matt.js` и навык `/kit:matt`; строки нет — как `нет`. Пока идёт этап Мэтта, шаг не по тикету — `N.0а`, `N.0б`…
- **Версия kit** — версия kit, которой проект последний раз настроен через `/kit:project-init` (с 3.1.0; ставит и обновляет он сам). При старте сессии хук сравнивает её с установленной: при любом расхождении — строка-напоминание вам («запустите `/kit:project-init`», а если проект новее плагина — «обновите плагин»); строки нет — тоже напомнит.

Параметров «Код пишет» и «Коммит» с 3.0.0 нет: код пишет Claude, коммит — всегда после просмотра; их старые строки никто не читает, `/kit:project-init` предложит убрать. Общий спек `spec-claude-kit.md` (в репозитории — `.claude/docs/archive/`, раздел 5) описывает kit до 2.18.0.

## Работа с другого компьютера (с 2.5.0)

Если git проекта лежит в закрытом удалённом репозитории (параметр «Удалённый репозиторий»), продолжить работу дома или на другой машине — это:

1. Claude Code, Node.js ≥ 18 и плагин — «Установка» выше (с GitHub).
2. `git clone <адрес>` — для сайтов в ту же папку, что на работе (например `C:\OSPanel\home\<сайт>`); если в параметре «Удалённый репозиторий» не `origin` — `git clone -o <имя> <адрес>`, иначе хук скажет, что такого remote нет. Параметр «PHP» — путь к `php.exe` на машине, и он в git. OSPanel в другой папке — `php -l` молча пропускается, а `kit-exec.php` не собирается.
3. PhpStorm: открыть папку и настроить сервер выкладки (`.idea` не в git); исключения `.idea`, `.git`, `.claude` хук допишет сам при первом старте сессии.
4. SSH к серверу — свой ключ этой машины (`plugins/kit/skills/project-init/reference/ssh.md`); Битрикс без SSH — файл-канал `kit-exec.php`.
5. `/kit:visual` — зависимости ставятся заново; эталоны `before` остались на первой машине — снять заново.
6. Скиллы Битрикса (`.claude/skills`) не в git — `/kit:project-init` поставит их заново (правило проекта напомнит).
7. Работать с одного компьютера за раз: при старте сессии хук сверит ветку с удалённой, и Claude до любой правки подтянет коммиты, сделанные на другой машине (`git pull --ff-only`), а `/kit:step-done` отправит свои. Ветки разошлись — Claude остановится и спросит.

Репозиторий создаёте вы (закрытым и пустым — без README), вход в GitHub/GitLab — тоже вы (окно Git Credential Manager при первой отправке). Секреты в репозиторий не попадают: `.gitignore`, скрипт коммита и `secret-scan.js`, а перед первой отправкой — проверка всей истории.

## Скиллы Битрикса (с 2.7.0)

В режиме 1С-Битрикс `/kit:project-init` при каждом запуске спрашивает «Ставить скиллы Битрикса?» и при ответе «Да» ставит в `.claude/skills` проекта свежие версии скиллов из открытых репозиториев [bxmaximum/bitrix-framework-skills](https://github.com/bxmaximum/bitrix-framework-skills) — без `bitrix24-*` (они для портала Битрикс24) — и [bitrix-tools/best-practice](https://github.com/bitrix-tools/best-practice): 46 скиллов (ORM, контроллеры, кеш, безопасность, компоненты, инфоблоки, магазин…). В правила проекта (`.claude/CLAUDE.md`, раздел «Код») ложится строка: код на Битриксе — по этим скиллам, начиная с `bitrix-framework`.

- Ставит скрипт `bitrix-skills.js` (`git clone --depth 1` и копирование `skills/<имя>/`), без `npx` и без папки `.agents`. Ответ «Да» при повторном запуске заменяет папки скиллов свежими версиями, «Нет» — не трогает поставленные; ваши собственные скиллы в `.claude/skills` не трогаются никогда. Между запусками `/kit:project-init` скиллы не обновляются.
- В git проекта скиллы не попадают (`.gitignore` kit берёт `/.claude/*`): чужие файлы, обновляются раз в месяц. На другом компьютере их ставит `/kit:project-init`.
- На сервер не уезжают: `.claude` исключена из выкладки, а при «Документы на сервере: да» хук исключает `.claude/skills` заранее, а `ssh-deploy.js --docs` берёт только `.claude/docs`, `CLAUDE.md` и `.htaccess`. `check-closed` их не обходит.
- Описания скиллов попадают в контекст каждой сессии проекта (около 2,5 тысячи токенов). Если сразу после установки Claude их не видит — перезапустить сессию.

## Работа на сервере без SSH (с 2.4.0)

- **Битрикс без SSH — файл `kit-exec.php`.** Claude собирает его из кода задачи (`scripts/kit-exec.js`, проверка `php -l`), кладёт в корень сайта, открывает во встроенном браузере Claude и читает вывод. Файл отдаёт результат только вошедшему администратору (`$USER->IsAdmin()`, остальным — 403), выполняет только вшитый код и только при `?run=<номер запуска>` из своей сборки; вы один раз входите администратором в браузере Claude (пароли вводите вы). При автозаливке PhpStorm файл уезжает сам, иначе его заливаете вы (Upload to…). По окончании работы Claude сам удаляет файл с сервера последним запуском (код `unlink(__FILE__)`, с вашего согласия) и проверяет, что файла там больше нет (404 или страница сайта без строки `KIT-RUN`); вручную (PhpStorm → Remote Host) файл удаляете только если у PHP не хватило прав; в git он не попадает (`/kit-exec.php` в `.gitignore`, в запретах скрипта коммита и secret-scan).
- **Согласие — как по SSH:** чтение выполняется сразу, любое изменение — только после вопроса в чате с точным кодом. Окна подтверждения в браузере больше нет; Командная PHP-строка через Claude in Chrome (до 2.4.0) удалена.
- **Не Битрикс и без SSH** — выполнить на сервере негде: включите SSH (`plugins/kit/skills/project-init/reference/ssh.md`, «Как включить SSH у хостинга»).
- Общий таймаут SSH (`remote-php.js --timeout`, по умолчанию 90 с), `Include` в `~/.ssh/config`, пути MSYS2 и `DOCUMENT_ROOT` в общем режиме — исправления шагов К13, К14, К16, К20.
- Проекты на Битриксе без SSH после обновления работают сразу, если задан параметр «PHP» (путь к локальному `php.exe`): `/kit:server` сам выберет файл-канал. Но строки «Работа на сервере» в `.claude/CLAUDE.md` и вводная строка раздела «Удалить с сервера» плана выкладки, написанные до 2.4.0, описывают прежний запасной канал: `/kit:server` скажет об этом и предложит заменить их на новый вариант (с вашего согласия). Строку `/kit-exec.php` в `.gitignore` допишет `/kit:project-init` (или Claude при первом запуске) — тоже с согласия.

## Снимки «до/после» (`/kit:visual`, с 2.2.0)

- Нужен установленный Google Chrome (браузеры Playwright не скачиваются) и один раз на машину — зависимости: Claude спросит и выполнит `node visual.js install` — `npm install` playwright-core, pixelmatch, pngjs (~15 МБ) в `%LOCALAPPDATA%\kit\visual\deps`. Обновления плагина их не трогают.
- Список страниц проекта — `.claude/scripts/visual/pages.json` (в git); снимки — `.claude/docs/visual/`, **только локально**: инструмент сам кладёт туда `.gitignore` и не снимает, если PhpStorm с автозаливкой Always не исключает папку снимков (снимки из-под админа, nginx отдаёт картинки мимо `.htaccess`); с 2.3.0 исключение дописывает хук.
- Вход администратора — окно Chrome, входите вы сами; сессия хранится в `%LOCALAPPDATA%\kit\visual\auth`, своя на каждый проект.
- В проектах, созданных до 2.2.0: исключения PhpStorm с 2.3.0 дописывает хук; в «Не выкладывать» — `.claude`.

## Переход с 1.x на 2.0

- Команда `/kit:bitrix-console` переименована в `/kit:server`: сначала SSH, иначе (с 2.4.0) файл `kit-exec.php`; до 2.4.0 — Командная PHP-строка в Chrome. В `docs/deploy-prod.md` и `.claude/CLAUDE.md` проектов заменить `/kit:bitrix-console` на `/kit:server`.
- В проектах добавить параметры `SSH прод`, `SSH дев`, `PHP на сервере`. Проще всего — три строки вручную по образцу из «Параметров проекта» выше (`—`, если SSH нет); или `/kit:project-init` допишет их с согласия (раздел «SSH»). Без них `/kit:server` в режиме bitrix работает через файл `kit-exec.php` (с 2.4.0; до 2.4.0 — через Командную PHP-строку в Chrome).
- После обновления плагина перезапустить сессии Claude Code.

## Перевод проекта со своими агентами на kit

1. `/kit:project-init` в проекте — допишет раздел параметров и недостающие файлы, ничего не перезапишет.
2. Удалить проектные копии старых агентов kit из `.claude/agents/` (ведение журнала и коммит): с 3.0.0 журнал ведёт скрипт `kit-journal.js`, коммит — `kit-commit.js`. Если `.claude/agents/` уезжала на сервер — удалить и там (раздел «Удалить с сервера» плана выкладки).
3. Убрать из `.claude/CLAUDE.md` строки о запуске агентов и о том, что делать, «если агенты не подхватились», — это теперь в плагине.

## Плагин aspro

Сверка доработок сайта на 1С-Битрикс с обновлением решений Аспро (Оптимус, Корпоративный сайт 3.0 и др.). Ставится отдельно от kit и
работает без него.

- **Как дорабатывают:** обычной правкой файлов шаблона — в копии `local/templates/<шаблон>` (режим «копия») или прямо в
  `bitrix/templates/<шаблон>` (режим «на месте»); так же компоненты Аспро и публичные файлы решения. Манифеста, обёрток и списка
  доработок нет: что доработано, инструмент вычисляет сам по снимку эталона вендора.
- **Как обновляют:** решение ставят в админке как обычно. Сайт сам перед установкой снимает снимок, после установки сливает
  очевидное (недоработанные файлы, трёхсторонние слияния без пересечений) и показывает уведомление. Затем в папке сайта —
  «сверь обновление Аспро»: Claude по скилу `aspro:aspro-merge` разбирает конфликты по смыслу (код вендора — основа, исправления
  безопасности не откатываются), проверяет страницы и пишет отчёт.
- **Что нужно на сайте:** PHP CLI 8.1+; git и Node.js на сервере не нужны. Без SSH — выгрузка троек для разбора и загрузка решений
  архивом.

```
claude plugin marketplace add Ozimnadius/claude-kit
claude plugin install aspro@claude-kit
```

Дальше в папке сайта: «внедри сверку Аспро» — Claude скопирует инструмент на сайт (`local/tools/aspro-merge`, файл подключения,
строка в `init.php`) и снимет первый снимок. Инструкция для команды —
[`plugins/aspro/skills/aspro-merge/docs/GUIDE.md`](plugins/aspro/skills/aspro-merge/docs/GUIDE.md), процедура Claude —
[`SKILL.md`](plugins/aspro/skills/aspro-merge/SKILL.md), команды инструмента — [`tool/README.md`](plugins/aspro/skills/aspro-merge/tool/README.md).
Обновление: `claude plugin update aspro@claude-kit`, затем в папке сайта «обнови инструмент сверки».

Лицензия: MIT; движок слияния `tool/lib/xmerge.php` — порт xdiff из git, LGPL-2.1-or-later (`tool/lib/LICENSE-xmerge.md`, полный
текст — `tool/lib/LICENSE-LGPL-2.1.txt`).

## Разработка

- Тесты: `npm ci` один раз (devDependencies `pngjs` и `pixelmatch` — для тестов сравнения снимков), затем `npm test` (`node --test tests/*.test.js`); PHP-тесты используют `C:\OSPanel\modules\PHP-7.2`, `PHP-7.4`, `PHP-8.2`, `PHP-8.3` и пропускаются, если их нет.
- Проверка манифестов: `claude plugin validate plugins/kit --strict`, `claude plugin validate plugins/aspro --strict` и `claude plugin validate . --strict`.
- Плагин aspro: `plugins/aspro/skills/aspro-merge/` (скил, инструмент, документы) правится здесь (с 1.2.0; прежней приватной
  лаборатории больше нет); проверка инструмента — его самопроверка `merge.php selftest`, её запускает `tests/aspro-plugin.test.js`
  (PHP 8.2 из OSPanel). PHP инструмента не править `sed` — только правкой файла (хук kit не пропустит). Выпуск: `version` в
  `plugins/aspro/.claude-plugin/plugin.json`, в записи `aspro` в `marketplace.json`, `AsproMerge\Tool::VERSION` и
  `AsproMergeSite::VERSION` (файл подключения) равны — `tests/aspro-plugin.test.js` это проверяет.
- Запуск без установки: `claude --plugin-dir <папка репозитория>\plugins\kit` (читает папку напрямую).
- Защита от утечек: `node tools/kit-denylist.js install` ставит хуки git, которые не пропустят в коммит (файлы и сообщение) слова из вашего локального списка `.git/info/kit-denylist` — имена клиентов, домены, учётки; список в репозиторий не попадает. `node tools/kit-denylist.js tree` — проверить все файлы.
- Выпуск: поднять `version` в `plugins/kit/.claude-plugin/plugin.json` и в записи плагина в `.claude-plugin/marketplace.json` (одинаково; тест `tests/manifest.test.js` это проверяет) — без новой версии `claude plugin update` изменений не увидит.
- Обзор со схемами — `.claude/docs/work/overview/` (`overview.md` для GitHub, `overview.html` для браузера, схемы в `img/`); собирается из `build/` командой `node .claude/docs/work/overview/build/build.js` — правки вносить туда, а не в собранные файлы. Обновляется только при мажорном выпуске или когда выпуск добавляет или убирает команду, агента, хук, скрипт либо режим; остальные выпуски трогают версии, README и журнал.
- Журнал разработки — `.claude/docs/progress.md`, общий спек — `.claude/docs/archive/spec-claude-kit.md` (заморожен на 2.18.0; дальше — спеки этапов и этот README), спеки и планы завершённых этапов — `.claude/docs/archive/` (реестр — раздел «Документы» журнала). Проекты, на которых проверялся плагин, в документах обезличены: alpha, beta, gamma…, домены `*.example.com`.
- Снимки вживую (Chrome и сайт) тестами не проверяются: `node plugins/kit/scripts/visual.js …` из корня проекта; `KIT_VISUAL_HOME` — другая папка на машине вместо `%LOCALAPPDATA%\kit\visual`, `KIT_VISUAL_DEPS` — папка с `node_modules` (так тесты берут зависимости из корня репозитория).
